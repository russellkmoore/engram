**Project:** Engram — v0.3 Identity + Surface (first frontend)
**Researched:** 2026-06-12
**Milestone context:** Adding a browser UI to an existing MCP-only backend. The MCP server Worker, WorkspaceDO, OAuth Resource Server pattern, and KV-backed identity records are all validated and deployed.

## 1. UI Framework — Recommendation: Hono JSX + HTMX (SSR-first, no SPA framework)

### Decision matrix

| Option | CF-native | DX quality | JS bundle | MCP Worker integration | Design quality ceiling | Solo-dev fit |
|--------|-----------|------------|-----------|----------------------|----------------------|-------------|
| **Hono JSX + HTMX** | Native (runs in workerd) | High — typed JSX, familiar syntax | ~2 KB (HTMX) + 0 KB extra runtime | Same Worker or sibling, direct env access | Good with Tailwind v4 | Best — no build toolchain friction |
| React SPA + Workers API | Native via Vite plugin | High — familiar ecosystem | 50–150 KB | Separate API Worker required | Excellent with shadcn/ui | Medium — Vite plugin is new, monorepo integration has caveats |
| Astro + Cloudflare adapter | Native via Pages/Workers | High — content-focused | Islands only | Requires API Worker | Good | Medium — over-engineered for app UI |
| React Router v7 (Remix) + CF adapter | Native | High | SSR + hydration | Separate from MCP Worker | Excellent | Medium — heavy footprint |
| Hono + React Islands (hono/jsx/dom) | Native | High | 2.8 KB Hono DOM vs 47 KB React | Same Worker | Excellent with shadcn/ui | High — best of both |
| Plain HTML + htmx | Native | Low — no types | ~14 KB (HTMX CDN) | Same Worker | Limited without framework | Low — maintenance pain |

**Recommendation: Hono JSX + HTMX for v0.3, with a forward-path to Hono + React Islands for the memory browser.**

Rationale:

- The consent/sign-in page and inbox UI are forms with server-rendered lists — HTMX `hx-post` / `hx-get` with partial HTML responses is the simplest implementation that has no client-side framework dependency.
- Hono v4.x (currently **4.12.x**, April 2026) ships first-class JSX support (`hono/jsx`), signed cookies (`hono/cookie`), JWT helpers (`hono/jwt`), and typed RPC — all running natively in workerd. No polyfills, no node shims.
- The memory browser and admin dashboard need reactive state. For those pages specifically, `hono/jsx/dom` provides React-compatible hooks with a 2.8 KB Brotli footprint, or you can drop in Alpine.js (~7 KB) for progressive enhancement without a full SPA.
- The React SPA path via `@cloudflare/vite-plugin` is the right long-term direction but currently has a documented conflict with `@tailwindcss/vite` in the same Vite config (GitHub issue tailwindlabs/tailwindcss#15399 / cloudflare/workers-sdk#9379 as of mid-2026), and monorepo npm workspaces support is explicitly noted as "limited" in CF docs. These are not blockers for a greenfield project but add friction when bolting onto an existing monorepo mid-milestone.

**What to avoid for v0.3:** Do not add Astro, Next.js, Remix, or SvelteKit. Each introduces a build pipeline that cannot share the existing wrangler.jsonc configs and defeats the single-platform simplicity constraint.

### Packages

```bash
# No new dependencies beyond what Hono already provides
# Hono is already in the monorepo at ~4.x (verify current version in packages/mcp-server)

# For client-side interactivity on memory browser / admin pages:
# OPTION A — zero framework, HTMX via CDN script tag in HTML (no npm)
# OPTION B — Hono JSX DOM (same package, different import path)
```

## 2. Hosting Model — Recommendation: Separate `engram-web` Worker with Workers Static Assets

### Pages vs Workers Static Assets

As of March 2026, Cloudflare has reached full feature parity between Pages and Workers Static Assets. The official guidance is: **new projects should use Workers Static Assets, not Pages.** The Cloudflare Vite plugin explicitly does not support Workers Sites (deprecated in Wrangler v4), and the CF migration guide advises Pages projects to migrate to Workers.

| Dimension | Workers Static Assets | Cloudflare Pages |
|-----------|----------------------|-----------------|
| Static file serving | Native, free requests | Native, free requests |
| Bindings (KV, DO, etc.) | Full Workers binding surface | Pages Functions only |
| Wrangler v4 support | First-class | Supported but not the forward path |
| Preview deployments | Via Workers Builds CI | Native per-branch |
| Monorepo support | Per-Worker wrangler.jsonc | Per-project config |
| Integration with existing Workers | `service_bindings` or HTTP | HTTP only |
| **Current CF recommendation** | **Use this for new projects** | Maintained, not the forward path |

**Verdict:** Workers Static Assets.

### Same Worker vs Separate Worker

**Recommendation: Separate `engram-web` Worker.**

The case for adding UI to the existing `engram-mcp-server` Worker:

- Fewer deployments, shared bindings
- The `OAuthProvider` `defaultHandler` already handles `/authorize`, `/`, `/health`

The case against (decisive):

- `engram-mcp-server` is the production-critical MCP endpoint with a deployed user (Russell). A UI bug that causes a Worker unhandled exception takes down MCP tool calls, not just the UI. Separation is a safety boundary.
- The OAuth provider's route dispatch order is: library routes first → `/mcp` apiHandler → `defaultHandler`. Adding UI routes to `defaultHandler` introduces accidental shadowing risk with library-owned paths.
- `workers-oauth-provider` v0.7.x (current as of June 4, 2026) is not designed to also serve a full app UI. Its `defaultHandler` is specifically the consent-step handler; mixing it with general HTTP routing is fighting the library's intended shape.
- A separate Worker makes the `engram-web` package independently deployable and independently testable, consistent with the existing monorepo per-package pattern.

**One exception:** The OAuth consent screen (the HTML form that appears when `mcp-remote` triggers the `/authorize` flow) SHOULD remain in `engram-mcp-server`'s `defaultHandler`, not in `engram-web`. This is because the OAuth provider dispatches `/authorize` to `defaultHandler` directly — a redirect to `engram-web` for consent and back would require passing OAuth parameters through cross-Worker redirects, adding complexity and a CSRF surface. The simpler path: `defaultHandler` renders the consent HTML inline (replacing the current v0.1 auto-approve). `engram-web` hosts the self-service sign-in flow (magic link request / verify / inbox / memories / admin), which is a separate session.

**`engram-web` Worker wrangler.jsonc shape:**

```jsonc
{
  "name": "engram-web",
  "main": "./src/index.ts",
  "compatibility_date": "2026-05-22",
  "compatibility_flags": ["nodejs_compat"],
  "assets": {
    "directory": "./dist/static",
    "binding": "ASSETS",
    "not_found_handling": "single-page-application"
  },
  "kv_namespaces": [
    { "binding": "ENGRAM_IDENTITIES", "id": "..." },
    { "binding": "ENGRAM_SESSIONS", "id": "..." },
    { "binding": "ENGRAM_MAGIC_TOKENS", "id": "..." }
  ],
  "send_email": [
    { "name": "EMAIL", "remote": true }
  ],
  "vars": {
    "MCP_SERVER_URL": "https://engram-mcp-server.russellkmoore.workers.dev"
  }
}
```

The `engram-web` Worker hosts: magic-link request/verify routes, session issue/validate middleware, inbox UI, memory browser, admin dashboard. It talks to the MCP Worker via `MCP_SERVER_URL` using the existing OAuth bearer token pattern, or directly to `WorkspaceDO` via a `service_binding` if low-latency DO access is needed for admin.

**Route map for `engram-web`:**

```
GET  /                  → redirect to /signin or /inbox (session check)
GET  /signin            → magic link request form (Hono JSX)
POST /signin            → send magic link email (CF Email Service)
GET  /signin/verify     → consume token → issue session cookie → redirect /inbox
GET  /inbox             → inbox UI (Hono JSX, session required)
GET  /memories          → memory browser (Hono JSX, session required)
GET  /admin             → admin dashboard incl. eval-budget view (Hono JSX, session required)
GET  /admin/budget      → Workers Analytics Engine neuron-spend (replaces eval-budget-summary.mjs)
```

## 3. Magic-Link Email Delivery — Recommendation: Cloudflare Email Service (`send_email` binding)

### What exists in 2026 for outbound email from Workers

| Option | Status | CF-native | Setup cost | Cost | Recommendation |
|--------|--------|-----------|------------|------|---------------|
| **CF Email Service `send_email` binding** | **Public beta (April 2026)** | Yes — Workers binding, no API key | Low — wrangler config only | 3,000/mo free on Workers Paid, then $0.35/1K | **Primary for v0.3** |
| Resend REST API | GA | No — external HTTP call + API key secret | Low — REST POST | 3,000/mo free tier, $20+/mo after | **Fallback if CF Email has reliability issues** |
| MailChannels free | **Deprecated August 2024** | Was free pass-through | — | Sunset | Do not use |
| SendGrid / Postmark | GA | No — external HTTP + API key | Low | Pay-per-use | Justified only if CF Email proves unsuitable |

**Critical fact:** Cloudflare Email Routing (the inbound system Engram uses for workspace identity hints) is **inbound-only**. It cannot send. The outbound path is exclusively CF Email Service binding or an external API.

**Use CF Email Service `send_email` binding.**

Justification:

- It is a Workers binding — no API key secrets, no external network dependency at the auth layer. The magic-link email send runs inside the same `workerd` process as the session issuance logic.
- 3,000 emails/month is included on Workers Paid. A magic-link flow with O(10) users across v0.3 will never approach this limit.
- The binding was in private beta for 7 months before public beta (April 2026), suggesting reasonable stability. The Workers Paid plan is already required for Engram (Durable Objects require it).
- The API is minimal: `env.EMAIL.send({ to, from, subject, html, text })` returns `{ messageId }`.

**Important caveat (MEDIUM confidence):** As of June 2026 the service is still labeled "public beta" in the docs. If deliverability proves unreliable during v0.3 development, fall back to Resend with a `RESEND_API_KEY` Worker secret — the swap is a single function change.

**wrangler.jsonc binding:**

```jsonc
"send_email": [
  {
    "name": "EMAIL",
    "remote": true
  }
]
```

**TypeScript usage:**

```typescript
await env.EMAIL.send({
  to: userEmail,
  from: "signin@yourdomain.com",
  subject: "Your Engram sign-in link",
  html: `<p><a href="${magicLinkUrl}">Click here to sign in</a> (expires in 15 minutes)</p>`,
  text: `Sign in to Engram: ${magicLinkUrl} (expires in 15 minutes)`,
});
```

**Domain requirement:** The `from` address must be on a domain managed in Cloudflare DNS. The `*.workers.dev` subdomain may not work as a sender domain. Russell should verify in the CF Email Service dashboard whether his custom domain is registered, or use a verified Cloudflare-managed domain. This is a prerequisite to investigate before Phase 1 of v0.3 executes.

## 4. Session / Cookie Handling — Recommendation: Hono Signed Cookies + KV Session Store

### Integration point with the existing OAuth Resource Server

The existing `engram-mcp-server` uses `@cloudflare/workers-oauth-provider` v0.7.x as an OAuth Resource Server — it issues JWTs consumed by `mcp-remote`. The browser UI is a **separate authentication surface**: the user authenticates via magic link, not via the `mcp-remote` OAuth flow. The web session does NOT share JWT tokens with the MCP OAuth flow. This is correct by design: the MCP tool session is a machine-to-machine OAuth token; the web session is a human browser session.

The `engram-web` Worker maintains its own session independently and uses the KV identity record (`ENGRAM_IDENTITIES`) for workspace/user lookups, which is the same source of truth as the MCP Worker.

### Pattern

**Signed session cookie → KV session record**

1. Magic link verified → generate random `session_id` (32 bytes, `crypto.getRandomValues`)
2. Write `{ user_id, workspace_id, expires }` to `ENGRAM_SESSIONS` KV with TTL
3. Set a `__session` cookie with `session_id` value, signed via Hono's `setSignedCookie` (HMAC-SHA-256, WebCrypto API — works in workerd without node:crypto)
4. On subsequent requests: `getSignedCookie` to verify signature, then KV lookup for session record

Hono provides `setSignedCookie` / `getSignedCookie` built-in (WebCrypto HMAC-SHA-256, no external dependency). `getSignedCookie` returns `false` on tampering — same tamper-detection pattern as the existing `timingSafeStringEqual` in `oauth.ts`.

**Why not JWT-only for the web session:**

- Cannot revoke a JWT without a denylist (magic links need revocability)
- KV session store is ~1 KV read per request — negligible cost and enables clean session invalidation at sign-out

**Cookie attributes:**

```typescript
await setSignedCookie(c, "__session", sessionId, env.SESSION_SECRET, {
  path: "/",
  httpOnly: true,
  secure: true,
  sameSite: "Lax",
  maxAge: 60 * 60 * 24 * 30, // 30-day session
});
```

**Session secret:** A Workers secret (`wrangler secret put SESSION_SECRET`), not a var. Must be a high-entropy string (minimum 32 bytes).

**Magic link token storage:** Separate KV namespace `ENGRAM_MAGIC_TOKENS` with `{ email, workspace_id, user_id }` value, 15-minute TTL. Token = 32-byte random hex in URL. Single-use: delete the KV entry on first use.

### Packages required

No new npm packages. All session handling uses:

- `hono/cookie` (already in Hono v4.x) — `setSignedCookie`, `getSignedCookie`
- `hono/jwt` (already in Hono v4.x) — available if JWT-based cross-service auth is needed later
- Workers KV (existing platform binding)
- WebCrypto (`crypto.getRandomValues`, `crypto.subtle`) — native to workerd

## 5. Styling / Component Approach — Recommendation: Tailwind CSS v4 + Radix Primitives (manual, not shadcn CLI)

### For a design-conscious solo build

| Option | Design quality | CF-Workers compatible | Install complexity | Component coverage | Recommendation |
|--------|---------------|----------------------|--------------------|-------------------|---------------|
| **Tailwind v4 + Radix primitives** | High | Yes (CSS build step only) | Medium | Full | **Use this** |
| shadcn/ui CLI (React + Tailwind v4) | High | Requires React SPA path | High (Vite + CF plugin conflict) | Full | Avoid in v0.3; viable if React SPA chosen later |
| Tailwind v4 only (no component lib) | Good | Yes | Low | DIY | Acceptable if scope is small |
| UnoCSS | Good | Yes | Low | DIY | No advantage over Tailwind v4 for this codebase |
| Pico CSS | Minimal | Yes | Very low | None | Not design-conscious enough |

**Use Tailwind v4 + hand-selected Radix UI primitives.**

Tailwind v4 install for Hono JSX (standalone CLI, not Vite plugin):

```bash
npm install -D tailwindcss
# Build step in package.json scripts:
# "build:css": "tailwindcss --input src/styles.css --output dist/styles.css"
```

In CSS entry:
```css
@import "tailwindcss";
/* custom theme overrides via @theme directive — no tailwind.config.js needed in v4 */
@theme {
  --color-brand: oklch(63% 0.2 258);
}
```

**Vite plugin conflict note (MEDIUM confidence):** There is an open issue (tailwindcss#15399, workers-sdk#9379) where `@cloudflare/vite-plugin` and `@tailwindcss/vite` conflict in the same Vite config due to the Vite Environment API. The workaround for Hono JSX apps: run Tailwind as a standalone CLI build step rather than through the Vite plugin. This is a one-liner in `package.json` scripts and the standard pattern for server-rendered Hono apps.

**Radix UI primitives** (`@radix-ui/react-*`) are headless, accessible, and designed for Tailwind composition. For v0.3's surfaces (a sign-in form, inbox list, memory browse table, simple admin dashboard), only a few are needed:

```bash
npm install @radix-ui/react-dialog @radix-ui/react-toast @radix-ui/react-dropdown-menu
```

**shadcn/ui approach:** shadcn is not an npm dependency but a code-generation tool. The components it generates are Radix + Tailwind files that live in your repo. If the React SPA path is adopted in v0.4+, `npx shadcn@latest init` and then `npx shadcn@latest add button dialog table toast` drops pre-styled Radix components into `packages/engram-web/src/components/ui/`. This is the forward-path once the Vite plugin conflict is resolved upstream.

For v0.3 with Hono JSX (no React), use Tailwind v4 utility classes + semantic HTML + Radix primitives where accessible behavior is needed (dialogs, dropdowns). The inbox and memory browser do not need heavy component abstractions.

## Integration with Existing OAuth Resource Server

The `engram-web` Worker does not replace or modify the `@cloudflare/workers-oauth-provider` setup. Integration points:

1. **OAuth consent screen (stays in `engram-mcp-server`):** The current `oauth.ts` auto-approves every OAuth request (the "v0.1 simplification" comment at line 229). In v0.3, `defaultHandler` in `engram-mcp-server` renders a real HTML consent page inline. This avoids cross-Worker redirect chains with OAuth parameters. The `engram-web` Worker is NOT in the MCP OAuth flow.

2. **Identity lookup (shared KV namespace):** `engram-web:/signin/verify` reads `ENGRAM_IDENTITIES` KV directly — the same namespace and schema as `engram-mcp-server`. The `IdentityRecordSchema` in `oauth.ts` should be extracted to `shared/types` so both packages can import it.

3. **WorkspaceDO access for inbox/memory browser:** For v0.3, `engram-web` calls MCP tools via HTTP (the existing `/mcp` endpoint) authenticated with a session-derived bearer token. Direct DO service binding is an optimization deferred to v0.4+.

4. **Magic link replaces `kv:bootstrap` terminal dance:** The v0.3 magic link flow writes a new `ENGRAM_IDENTITIES` record for a new user (or validates an existing one). The `kv:bootstrap` script remains available for CLI power users and CI. The magic link is the "zero-terminal" path replacing the 8-step dance from ENG-11.
