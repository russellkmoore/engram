# Feature Research — Engram v0.2 (Intelligence Layer)

**Domain:** MCP-native layered memory; intelligence layer (semantic + AI processing)
**Researched:** 2026-06-02
**Confidence:** MEDIUM-HIGH — patterns verified across mem0/Zep/Notion/RAG-Fusion literature; Engram-specific mapping is opinionated synthesis grounded in the v0.1 codebase (verbosity enum, conflict-detection scaffold, hybrid-rank weights all already shipped)
**Scope:** v0.2 only — the 4 features Russell named (conflict-detection inbox surfacing, query expansion, recall synthesis, hybrid-rank weight tuning). v0.1 FEATURES.md remains the canonical reference for table-stakes vs differentiators across the full arc.

---

## Executive Summary

The four v0.2 features fall into two very different complexity buckets, and the roadmap should reflect that:

1. **Recall synthesis + conflict-detection surfacing are TABLE STAKES NOW** in the 2026 AI-memory category. mem0 ships LLM-resolver (ADD/UPDATE/DELETE/NOOP) at write time; Zep's Graphiti invalidates contradicted edges with temporal endpoints; Notion AI synthesizes across pages in its Workspace Q&A. Engram shipping v0.2 without these would be a competitive regression vs the v0.1 baseline. Both have v0.1 scaffolds already in the codebase (`verbosity` param plumbed in `envelope.ts`; `conflict-detection.ts` with 3-category classifier + Zod schema). v0.2 work is **wiring + UX**, not greenfield invention.

2. **Query expansion is a DIFFERENTIATOR-ADJACENT OPTIMIZATION**, but the 2026 production literature is unambiguous: it has diminishing returns and meaningful latency/cost. The right pattern for Engram is **adaptive routing — single-pass embedding by default, expand only when retrieval confidence is low** (per the 2025-2026 Towards Data Science cost-control work and the 2026 RAG-Fusion industrial deployment paper). Multi-query everything is theatre. **Recommendation: ship simple multi-query (3 variants, parallel Vectorize, RRF) as the v0.2 baseline; defer HyDE and step-back to v0.3 if eval gates show wins.**

3. **Hybrid-rank weight tuning is a v0.2 RISK-OF-OVERFITTING task** that must be bounded to keep the milestone shippable. Russell's corpus (~50-100 memories, 1 user) is too small for learning-to-rank or Bayesian optimization (both want 500+ labeled judgments minimum per the JurisTCU and enterprise-search-labeler literature). The right approach is **hand-annotated relevance judgments (~30-50 query-memory pairs) + coarse grid search over the existing 4 weights, run inside the existing promptfoo eval harness**. Anything more is over-engineering for a single-user dev corpus and risks tuning to noise.

**Cross-feature dependency to flag for roadmapper:** Recall synthesis depends on query expansion *only weakly* (synthesis can run over any retrieved set, expanded or not). Conflict-detection inbox surfacing depends on the v0.1 conflict-detection scaffold being **wired into the triage flow** — currently the function exists but isn't called from `index.ts`'s queue consumer. Hybrid-rank tuning is **independent of all three** but should run *last* in the milestone because synthesis quality eval will catch ranking regressions for free.

**Anti-feature for v0.2 (most important call-out):** Do NOT build the inbox UI in v0.2 — that's v0.4 per FEATURES.md. v0.2 surfaces conflicts via the `EngramResponse` envelope's `context.conflicts` field and (optionally) a new `conflicts(passive=true)` MCP read. Building the UI now drags Web frontend complexity into an Intelligence Layer milestone and will eat the whole sprint.

## Per-Feature Analysis

### 1. Conflict-Detection Inbox Surfacing

**v0.1 state:** `triage-worker/src/conflict-detection.ts` exists with a working `CONFLICT_DETECTION_PROMPT`, a 3-category enum (contradiction / benign_update / unrelated), Zod-validated structured output, and a precision-gated eval harness (`conflict-precision.eval.test.ts`). What's missing: (a) the function isn't called from the queue consumer in `index.ts`, (b) results aren't written to the `conflicts` SQLite table, (c) the `EngramResponse.context.conflicts` field is never populated.

#### Table Stakes (every production AI-memory system has this)

| Behavior | Why it's table stakes | Industry reference |
|---|---|---|
| Detect contradictory facts at write time | mem0's LLM-resolver runs on every `add()`; Zep's Graphiti runs on every episode ingest | [mem0 arXiv 2504.19413](https://arxiv.org/html/2504.19413v1), [Zep arXiv 2501.13956](https://arxiv.org/html/2501.13956v1) |
| Persist conflicts as first-class records (not just logs) | Both mem0 and Zep store conflict relationships in their schemas; users need to query "what does the system think is conflicting?" | [mem0 architecture](https://memo.d.foundation/breakdown/mem0) |
| Surface conflicts in the response envelope (not just in a separate UI) | The calling LLM needs to know about conflicts at synthesis time, not via a poll | (Engram-specific — extends competitor pattern to MCP) |
| Confidence score per detected conflict | mem0 returns probability; Zep returns LLM rationale + timestamp | [Zep Graphiti pattern](https://www.falkordb.com/blog/building-temporal-knowledge-graphs-graphiti/) |
| Non-destructive resolution (don't delete, mark invalid) | Both mem0 (UPDATE not DELETE for most cases) and Zep (temporal invalidation, never destructive) preserve history | [Zep arXiv §3.3](https://arxiv.org/html/2501.13956v1), [Graphiti Neo4j post](https://neo4j.com/blog/developer/graphiti-knowledge-graph-memory/) |

#### Differentiators (where v0.2 can lead the category)

| Behavior | Why it differentiates | Implementation cost |
|---|---|---|
| **Human-in-the-loop inbox queue (not auto-resolve)** | mem0 auto-resolves via LLM (silent UPDATE/DELETE); this is fast but erodes trust the first time it deletes a real fact. Engram's CLAUDE.md core principle ("Engram should return insights, not data") plus the inbox table already in v0.1 schema is the trust-first alternative | LOW — table exists, surface via envelope |
| **Severity tiering (low/medium/high)** beyond mem0's binary | Schema already has `severity` field in `conflicts` table; CF AI can score this in the same call as classification | LOW — extend existing prompt |
| **Conflict expressed in plain-English description, not just IDs** | mem0 returns memory IDs; for an MCP client the calling LLM has to re-fetch both memories to explain. Engram should return `description: "Said meeting is Tuesday in memory X but Wednesday in memory Y"` ready for Claude to surface | LOW — already in prompt design |
| **Detected at *write* AND on demand (`conflicts(passive=true)` tool)** | mem0 only detects on add; Zep does both but conflates them. Engram's 9-tool surface includes `conflict` (per CLAUDE.md) and v0.3 ships `conflict(passive=false)` for active scan — v0.2 can ship `passive=true` (read pending conflicts) as a small extension | LOW — SELECT from `conflicts` table |

#### Anti-Features (DO NOT build for v0.2)

| Behavior | Why competitors have it | Why NOT for Engram v0.2 |
|---|---|---|
| **Auto-resolve via LLM (mem0's DELETE/UPDATE pattern)** | Fast, no human friction | Russell's job-search corpus is irreplaceable — silent deletes erode trust. Inbox-first is the right v0.2 default; v1.0+ can opt-in to auto-resolve per memory-type |
| **Inbox UI / web view** | Notion has rich review UIs | Per FEATURES.md, inbox UI is v0.4. v0.2 surfaces conflicts via MCP envelope only. Building the UI here drags React/Astro complexity into an Intelligence Layer milestone |
| **Proactive Slack/email alerts** | "You said X but also Y" is a great demo | v0.4 (after Slack connector). v0.2 has no notification surface yet |
| **Temporal validity tracking (Zep-style `valid_at`/`invalid_at`)** | Zep's signature feature | High complexity (adds 2 columns + every query becomes temporal); deferred to v0.3 or post-v1.0. v0.2 stores `detected_at`/`resolved_at` (already in schema) which is enough for inbox |
| **Cross-workspace conflict detection** | Would require traversing TeamDO ↔ ProjectDO | TeamDO/ProjectDO don't exist until v0.3. v0.2 conflicts are within `russell-personal` only |

#### Complexity: **MEDIUM** (wiring, not invention)

- Function exists, prompt exists, schema exists. Risk = forgotten edge cases in queue consumer (concurrent writes to same memory pair) and choosing which existing memories to compare new write against (vector similarity threshold).
- Largest unknown: **how many candidate pairs to compare per ingest?** Comparing every new memory against every existing memory is O(N) and burns Workers AI tokens. mem0's pattern: Vectorize top-K similar (K=5-10), run LLM only on those. This is the right pattern for Engram.

#### User-facing behaviors that observe this feature

1. Russell adds a job posting with salary $180K. Two weeks later he `remember()`s "Recruiter at same company said comp is $160K base + $25K bonus." → conflict appears in `EngramResponse.context.conflicts` on next `recall("X company comp")`.
2. Claude in a new conversation runs `recall("decisions about Y project")` and the envelope includes `conflicts: [{ description: "...", severity: "medium" }]` so Claude proactively asks Russell to clarify.
3. (v0.3+ — flagged for roadmapper) Russell runs `conflict(passive=true)` and gets the pending-review queue without triggering a new scan.

### 2. Query Expansion (Multi-Query / HyDE / RAG-Fusion / Step-Back)

**v0.1 state:** Single-pass embedding (`recall()` embeds query verbatim and runs one Vectorize search). No expansion. Hybrid-rank then reorders results.

#### The 2026 Production Reality (not the 2024 blog hype)

The 2024-early-2025 RAG literature was uniformly bullish on query expansion. The 2026 production literature has corrected:

- **RAG-Fusion 2026 industrial deployment paper** ([arXiv 2603.02153](https://arxiv.org/pdf/2603.02153)) explicitly: "Retrieval fusion does increase raw recall, but these gains are largely neutralized after re-ranking and truncation. Hit@10 decreased from 0.51 to 0.48 in several configurations."
- **The Towards Data Science cost-control analysis** ([Nov 2025](https://towardsdatascience.com/rag-is-burning-money-i-built-a-cost-control-layer-to-fix-it/)): query expansion adds 1 LLM call + 3-4× vector queries per request; the right pattern is **adaptive routing — expand only when a cheap weakness signal trips**.
- **Alex Chernysh's "Which Query Transformation Techniques Actually Help RAG?"** (Apr 2025): "Do not add another transformation step until you can name the failure mode it fixes and the latency you are willing to pay for it."

#### Table Stakes (just having *something* beyond naive single-pass)

| Behavior | Why it's table stakes | Industry reference |
|---|---|---|
| Multi-query expansion (LLM generates 3-4 paraphrases, parallel Vectorize, dedupe results) | mem0, Notion AI Workspace Q&A, every advanced-RAG tutorial since late 2024 | [LangChain MultiQueryRetriever](https://python.langchain.com/docs/how_to/MultiQueryRetriever/), [Mayank Pratap Singh advanced RAG](https://mayankpratapsingh022-introduction-to-rag.hashnode.dev/advanced-rag-enhancing-retrieval-with-parallel-queries-and-reciprocal-rank-fusion) |
| Reciprocal Rank Fusion (RRF) to merge multi-query results | Standard since RAG-Fusion paper; OpenSearch and Vespa both ship native RRF | [OpenSearch RRF post](https://opensearch.org/blog/introducing-reciprocal-rank-fusion-hybrid-search/), [RAG-Fusion repo](https://github.com/Raudaschl/rag-fusion) |
| Dedupe near-identical results across variants before rerank | Multi-query naturally produces duplicate hits; users hate seeing same memory 3×; trivial with embedding similarity | (Implicit in any production RAG) |

#### Differentiators (the v0.2-defensible position)

| Behavior | Why it differentiates | Implementation cost |
|---|---|---|
| **Adaptive expansion (expand only on low-confidence single-pass)** | Most competitors expand every query; doing it selectively is the 2026 best practice but rarely shipped because it requires a confidence threshold tuned per corpus | MEDIUM — needs the v0.2 eval harness to define "low confidence" (suggest: top-1 cosine < 0.65) |
| **Expansion variants are stored & visible in `meta`** | No competitor surfaces "I tried these 4 reformulations" — Engram's "insights not data" principle wants the calling LLM to know what was searched | LOW — extend `EngramResponse.meta` with `expanded_queries: string[]` |
| **Expansion respects memory-type filter** | If user filters `type: "job_application"`, expansion shouldn't generate variants that drift cross-type (e.g., "interview" → general HR terms) | MEDIUM — prompt engineering on the expansion call |

#### Comparison Table — Which Expansion Technique for Engram?

| Technique | What it does | Cost per query | Engram fit | Verdict for v0.2 |
|---|---|---|---|---|
| **Multi-query** | LLM generates N paraphrases; parallel vector search; RRF merge | +1 LLM call (~200 tokens), +N vector queries | Good — handles vocabulary mismatch ("comp" vs "salary" vs "package") which is real in Russell's job-search corpus | **SHIP — recommended baseline** |
| **HyDE** (Hypothetical Document Embeddings) | LLM generates a fake "ideal answer doc"; embed *that*; search | +1 LLM call (~300-500 tokens), +1 vector query | **Poor fit.** [Blockchain Council guide](https://www.blockchain-council.org/agentic-ai/rag-vs-hyde/) explicitly: "For well-specified, fact-bound domains (e.g., personal data retrieval), HyDE is prone to hallucination and should be replaced by direct retrieval-based RAG." Russell's corpus is fact-bound. | **SKIP for v0.2** — hallucination risk on personal facts |
| **RAG-Fusion** (multi-query + RRF + cross-encoder rerank) | Multi-query but with a heavyweight reranker | +1 LLM call, +N vector queries, +reranker call | Reranker on Workers AI = Cohere rerank-3 binding (exists). But adds 200-500ms latency and is overkill for a 50-100 memory corpus | **SKIP for v0.2** — defer reranker to v0.3 when corpus grows |
| **Step-back prompting** | LLM asks a broader meta-question first; retrieve against both | +1 LLM call, +1-2 vector queries | Best fit for `reflect()` (v0.3), not `recall()`. Engram already has `reflect` as a separate tool — don't muddy `recall` with step-back | **DEFER to v0.3** — surface inside `reflect`, not `recall` |
| **Single-pass + confidence routing** | Cheap default; expand only when top-1 cosine < threshold | $0 on most queries; +multi-query cost on hard queries | **The 2026 pattern.** Combine with multi-query above | **SHIP as the wrapper around multi-query** |

#### Anti-Features (DO NOT build for v0.2)

| Behavior | Why competitors have it | Why NOT for Engram v0.2 |
|---|---|---|
| **HyDE** | Cool name, lots of blog posts | Hallucinates against personal facts (Russell's corpus is exactly the wrong shape); see Blockchain Council ref above |
| **Cross-encoder reranking** (e.g., Cohere rerank-3) | RAG-Fusion paper recommends it | Workers AI does have BAAI/bge-reranker-base — but at 50-100 memories, the rerank score noise > signal. Wait until corpus > 1000 memories |
| **Query classification routing** (e.g., LLM picks expansion strategy per query) | Production RAG sometimes does this | Premature optimization at 1-user scale; the confidence-routing single signal is enough |
| **Always-expand-every-query (vanilla RAG-Fusion)** | Default in most tutorials | Burns 3-4× tokens for marginal recall gain on a small corpus; violates Engram token-budget constraint |
| **User-tunable expansion count** | Surface knobs are cool | Defeats "Engram opinionated by default" principle (per FEATURES.md anti-features) |

#### Complexity: **MEDIUM** (1 new LLM call + RRF math + threshold tuning)

The hard part is **the confidence threshold for adaptive routing.** Suggest: start at `top1_cosine < 0.65` triggers expansion; tune via promptfoo eval against ~30 hand-labeled queries.

#### User-facing behaviors that observe this feature

1. Russell asks `recall("comp at company X")` and gets results that the v0.1 search would miss (variants searched: "salary at X", "compensation at X", "X total comp package"). Returned in `meta.expanded_queries`.
2. Russell asks `recall("Acme Corp")` (high-confidence single-pass hit, cosine 0.91) → no expansion runs, latency stays low (~150ms), `meta.expanded_queries` is empty array.
3. Claude inspects `meta.expanded_queries` to explain to user what was actually searched ("I looked for X, Y, Z and found these...").

### 3. Recall Synthesis (Narrative Summary Across N Memories)

**v0.1 state:** `recall()` accepts `verbosity: "synthesis" | "chunks" | "both"` (per `envelope.ts`); default is `"chunks"`; when `"synthesis"` or `"both"`, the synthesis string is *passed in* by the caller of `buildRecallResponse()` — but the **AI call to generate that synthesis is not yet wired in tools.ts**. The envelope contract is solid; the synthesis generator is the v0.2 work.

#### Table Stakes (every AI-memory product synthesizes)

| Behavior | Why it's table stakes | Industry reference |
|---|---|---|
| Generate a coherent narrative from N retrieved memories | Notion AI Workspace Q&A, Mem.ai, Reflect all do this | [Notion AI synthesis](https://www.notion.com/product/ai), [Mem.ai cross-note synthesis](https://get.mem.ai/guides/note-app-tried-everything) |
| Cite source memories (memory IDs / titles) inside the synthesis | Without citations users can't trust the summary; both Notion and Mem.ai do this | [Notion AI Q&A](https://www.notion.com/help/guides/preserve-perfect-meeting-memory-with-ai-meeting-notes) |
| Handle empty result set gracefully (don't fabricate) | mem0 returns empty list; Engram's synthesis must say "no relevant memories" not invent one | (Anti-hallucination basic hygiene) |
| Token-budget-aware truncation when memory count is large | mem0 caps result set; Notion truncates context window | (Implicit in any LLM-summary system) |

#### The Three Synthesis Patterns (LangChain Canonical Naming)

These are the only three patterns in production literature. Choosing one is the v0.2 architectural call.

| Pattern | How it works | Token cost | Latency | Best for | Reference |
|---|---|---|---|---|---|
| **Stuff** | Put all retrieved memories into one prompt, one LLM call | 1 call, but prompt grows linearly with N | Fastest (1 round trip) | Small N (≤20 memories), fits in context | [LangChain summarization comparison](https://medium.com/@abonia/summarization-with-langchain-b3d83c030889) |
| **Map-reduce** | Summarize each memory independently (parallel), then summarize the summaries | N+1 calls, parallel; total tokens lower than stuff at large N | Faster than refine (parallel) but slower than stuff at small N | Large N (>50 memories), parallelizable infra | [LangChain map-reduce vs refine](https://www.toolify.ai/ai-news/langchain-summarization-mapreduce-vs-refine-methods-3395910) |
| **Refine** | Sequential: synthesize 1, then add 2 to the synthesis, then add 3... | N calls, sequential | Slowest by far (sequential) | When ordering matters and context must accumulate | [Baeldung summarization](https://www.baeldung.com/cs/langchain-text-summarize) |

#### Engram-Specific Recommendation: **STUFF**

For Russell's v0.2 corpus (50-100 memories, `recall()` returns top-K where K=5-10 default), **all retrieved memories will always fit in a single Llama 3.1 8B context window** (8K tokens; even 10 memories at 200 tokens each = 2K input tokens). Map-reduce introduces complexity for zero benefit at this scale. **Refine is wrong at any scale** for query-time synthesis (it's optimized for ordering-preserving full-doc summarization, not cross-memory synthesis).

If the corpus grows past 1000 memories AND top-K grows past 25, revisit map-reduce. That decision is post-v1.0 territory.

#### Differentiators (where v0.2 synthesis can lead)

| Behavior | Why it differentiates | Implementation cost |
|---|---|---|
| **Synthesis is opt-in (verbosity="chunks" default)** | mem0/Notion always synthesize and burn tokens. Engram already shipped opt-in in v0.1 envelope ("synthesis omitted" hint in `meta.gaps`). v0.2 just needs to honor it | LOW — already plumbed |
| **Synthesis includes coverage signal ("based on N memories; M others were related but lower-confidence")** | No competitor does this. It's the "Engram is honest about what it knows" principle from CLAUDE.md core | LOW — meta math in envelope builder |
| **Synthesis surfaces detected conflicts inline ("X says Tuesday, Y says Wednesday — unresolved")** | Cross-product of synthesis + conflict-detection features. Notion/mem.ai don't do this because they don't have conflict detection | LOW — once both features ship, integration is free |
| **Synthesis respects memory-type context (job_application synthesis ≠ meeting_note synthesis)** | Schema-as-data means we know the type; prompt can be type-aware | MEDIUM — prompt fragment per system type, or generic with type-aware sections |

#### Anti-Features (DO NOT build for v0.2)

| Behavior | Why competitors have it | Why NOT for Engram v0.2 |
|---|---|---|
| **Always-synthesize default** | Convenient for chat UIs | Token-budget violation; the opt-in pattern is already in v0.1 envelope and is the correct call for MCP-first |
| **User-customizable synthesis prompts per query** | Power-user feature | Explicit anti-feature in v0.1 FEATURES.md (line 137); surface area explosion, defeats "opinionated by default" |
| **Map-reduce / refine for synthesis** | LangChain ships them, so "real" RAG must need them | Premature for corpus < 1000 memories; complexity tax with zero quality benefit at v0.2 scale |
| **Streaming synthesis** | OpenAI chat completions stream by default | MCP transport doesn't stream well; latency budget allows ~2s synthesis as a single completion; adding streaming = transport complexity for marginal UX gain |
| **Multi-turn refinement** (user asks follow-up, synthesis updates) | Notion AI does this in its chat | That's chat, not memory recall. `reflect()` (v0.3) is the right tool for iterative deepening |
| **Citations as hyperlinks** | Notion has rich text | MCP returns text; calling LLM (Claude) handles rendering. Engram emits `[memory:id]` style references and lets Claude format |

#### Complexity: **LOW-MEDIUM** (1 new LLM call wired into existing envelope path)

The hard part is **prompt engineering for synthesis quality** — the eval gates (ENG-20 deferred AI-04/05/06 from Phase 5 per CLAUDE.md) exist exactly for this. Use promptfoo against the F1 reference corpus (per spike findings).

#### User-facing behaviors that observe this feature

Had screening call with recruiter Jane Doe on 2026-03-22. On-site scheduled for 2026-04-05 but rescheduled to 2026-04-12. Note: conflict detected — two memories give different on-site dates."`

### 4. Hybrid-Rank Weight Tuning

**v0.1 state:** `packages/mcp-server/src/hybrid-rank.ts` exists with `HYBRID_WEIGHTS = { cosine: 1.0, recency: 0.15, type_match: 0.2, scope_match: 0.15 }` (per CLAUDE.md "What Goes Where" footnote). These are hand-picked defaults, not empirically tuned.

#### The Single Most Important Constraint: **Corpus Size**

The 2026 hand-annotated-relevance literature is consistent — meaningful weight tuning requires roughly the following minimum query-document judgment counts:

| Approach | Minimum labeled judgments | Source |
|---|---|---|
| **Hand grid search** (4 weights × 5 values each = 625 configs) | ~30-50 hand-labeled queries × top-10 results = ~300-500 judgments | [Augmented Relevance Datasets paper](https://arxiv.org/pdf/2504.09816) |
| **Bayesian optimization** (4 weights, continuous) | ~500-1000 judgments | [JurisTCU dataset: 150 queries / 2250 judgments](https://arxiv.org/pdf/2503.08379) |
| **Learning-to-rank** (e.g., LambdaMART) | 5000-10000 judgments | [Enterprise search labeler dataset: 923 pairs / 228 queries](https://arxiv.org/abs/2601.03211) |

**Russell's v0.2 reality: 50-100 memories, 1 user.** Even hand-labeling all of them across ~30 queries = 300 judgments. That's the floor for grid search and the ceiling for what's feasible in a v0.2 milestone.

#### Table Stakes (just having an evaluation harness)

| Behavior | Why it's table stakes | Industry reference |
|---|---|---|
| A reproducible relevance eval (queries + expected results) | Without it, every weight change is vibes-based | [Practical RAG Evaluation paper Nov 2025](https://arxiv.org/pdf/2511.09545) |
| Hit@K metric (did the right memory show up in top K?) | Standard IR metric; OpenSearch RRF post uses it | [OpenSearch hybrid search guide](https://opensearch.org/blog/introducing-reciprocal-rank-fusion-hybrid-search/) |
| NDCG@10 or MRR (does the right memory rank near the top, not just appear?) | Standard IR metric | [RAG-Fusion paper](https://github.com/Raudaschl/rag-fusion) |
| Baseline weights checked into config (not magic numbers in code) | v0.1 already has `HYBRID_WEIGHTS` as a named constant | (Engram already at table stakes) |

#### Recommended Tuning Approach for v0.2 (the **only** approach worth shipping in this milestone)

**Step 1: Hand-label 30-50 query-memory pairs** (1-2 hours of Russell's time).
- Format: `{ query: "...", expected_top_3: ["memory_id_1", "memory_id_2", "memory_id_3"] }`
- Source queries: Russell's actual recall history from v0.1 production (the Worker is already deployed; check logs/analytics).

**Step 2: Coarse grid search** over the 4 weights.
- Each weight: `[0.0, 0.1, 0.25, 0.5, 1.0]` = 5 values × 4 weights = **625 configurations**
- Score each config against the labeled set (NDCG@10 or Hit@3)
- Workers AI is not in the loop; this is pure SQL + cosine math
- Runtime: a few minutes locally with vitest

**Step 3: Pick the top-3 configurations, eval each against a held-out 10-query test set, choose the winner.**

**Step 4: Wire chosen weights into `HYBRID_WEIGHTS`, document the rationale in a code comment, ship.**

**Step 5: Add the grid-search harness to the promptfoo eval suite (ENG-9/10) so future tuning runs are repeatable.**

#### Differentiators (where v0.2 hybrid-rank tuning can subtly lead)

| Behavior | Why it differentiates | Implementation cost |
|---|---|---|
| **Memory-type-aware weights (job_application vs decision_log can have different recency decay)** | mem0/Zep use one global weighting; type-aware is novel because most systems don't have typed memories | MEDIUM — extend `HYBRID_WEIGHTS` to a per-type map; only do this if eval shows type-specific weights win |
| **The grid-search harness in CI** (every PR re-evals weights on labeled set) | Catches future regressions; rare even in production RAG | LOW — extends existing eval CI |
| **Honest reporting of confidence in `meta.confidence`** (already in envelope) | Most competitors return results without confidence; v0.1 envelope already has the field; v0.2 just needs to populate it from rerank-score gap (top-1 score vs top-2 gap) | LOW — formula in hybrid-rank.ts |

#### Anti-Features (DO NOT build for v0.2)

| Behavior | Why competitors / theory suggests it | Why NOT for Engram v0.2 |
|---|---|---|
| **Bayesian hyperparameter optimization (Optuna, etc.)** | Theoretically optimal at scale | Needs 500+ judgments; Russell has 50-100 memories total. Tuning to noise = guaranteed |
| **Learning-to-rank (LambdaMART, ListNet)** | State of the art in commercial search | Needs 5000+ judgments; impossible at v0.2 scale; massive complexity for a 1-user system |
| **Cross-encoder rerank stage** (e.g., BAAI/bge-reranker on Workers AI) | RAG-Fusion paper recommends it | Score noise dominates signal at corpus size 50-100; revisit when corpus > 1000 |
| **Per-user weight tuning** | Personalization is cool | 1 user; defer to v1.0 multi-tenant |
| **Online learning from click-through data** | Industry standard in commercial search | MCP has no concept of "click"; calling LLM doesn't emit selection signals; out of scope until v1.0+ adds a UI |
| **Reinforcement learning from Russell's feedback** | Tempting | Single-user RLHF is a tar pit; the eval harness is the right substrate |

#### Complexity: **LOW-MEDIUM** (the tuning is easy; labeling is the cost; resisting scope creep is the discipline)

**Key risk: scope creep.** It's tempting to "just also add a reranker" or "let me try Bayesian." Both add a week of work and won't beat grid-search at this corpus size. The discipline is to ship grid-search + CI harness and stop.

#### User-facing behaviors that observe this feature

1. Russell runs `recall()` queries he ran in v0.1 production and the top result is the one he actually wanted (whereas in v0.1 it was sometimes #3).
2. The `meta.confidence` field is meaningful: 0.9 means "I'm sure this is right," 0.5 means "best I have," 0.2 means "you should probably refine the query." This unblocks the adaptive-routing logic for query expansion (feature 2).
3. PRs that touch ranking or embeddings show a hybrid-rank eval delta in CI ("NDCG@10: 0.78 → 0.81 on labeled set").

       │
       └──requires──>  Workers AI text-generation binding (v0.1 shipped)

### Suggested Phase Ordering for Roadmapper

1. **Phase 1: Conflict-detection wiring** — lowest risk, highest leverage, scaffold exists. Validates the inbox-via-envelope pattern early.
2. **Phase 2: Hybrid-rank tuning + eval harness** — produces the labeled query set that benefits all subsequent phases. Confidence score from this feeds adaptive routing.
3. **Phase 3: Recall synthesis** — depends on phase 2's improved ranking quality (synthesis of noisy top-K = bad synthesis).
4. **Phase 4: Query expansion (adaptive)** — depends on phase 2's confidence score for the routing decision. Ship this last because it's the most easily deferred if milestone scope is tight.

If Russell needs to cut scope: **drop query expansion first** (feature 2). It has the weakest evidence of v0.2-scale ROI per the 2026 production literature, and the v0.1 single-pass `recall()` is honest about being a stub. Conflict-detection, synthesis, and hybrid-rank tuning all have v0.1 scaffolds waiting for completion and have stronger competitive-pressure justifications.

| Risk | Severity | Mitigation |
|---|---|---|
| Conflict-detection precision below 80% on real data | HIGH | The ENG-16 precision gate (50-sample) already exists; do not ship until it passes. Pattern from CLAUDE.md (mem0 false-positive horror stories) |
