## 1. Conflict-Detection Wiring (Feature 1)

### What ships

The `detectConflict` callable in `packages/triage-worker/src/conflict-detection.ts`
already passed the ENG-16 30-pair eval at P=0.875 / R=0.933. v0.2 wires it
into the queue consumer flow per its current "verdict: ship-as-suggestions"
posture — never auto-alert, always surface via inbox UI.

### New libraries / SDK methods / APIs

**None.** All the moving parts already exist in v0.1:
- `env.VECTORIZE.query(...)` — for the cosine-similarity prefilter
- `env.AI.run(CLASSIFIER_MODEL, ...)` — for the conflict classification call (already wired in `detectConflict`)
- `stub.insertInboxEntry(...)` — Plan 02 already provides this RPC (used today by `moveToInbox` at `queries.ts:666`)
- Workspace SQLite `inbox` table — schema already exists (`schema.ts:122`)

### Integration point — exact location and shape

The wiring lives in `packages/triage-worker/src/index.ts` inside the
`store-normal` branch (lines 213-242) of the existing `switch (decision)`.
Add a new step AFTER `updateBlockEnrichment` but BEFORE `message.ack()`:

```typescript
// === v0.2 Feature 1: post-store conflict detection (inbox-only suggestions) ===
// Runs ONLY in the "store-normal" branch — low-memorability content (inbox/cold)
// is not worth comparing because the dedup signal is already weak.
//
// Wrapped in ctx.waitUntil to keep store-normal latency at the existing 430ms p50
// budget. Conflict surface is a v0.2 nice-to-have, NOT a critical path.
ctx.waitUntil(
  (async () => {
    try {
      // Step 1: cosine-similarity prefilter — top 3 vectors above 0.7 in the same workspace namespace.
      // The 0.7 threshold is intentionally HIGHER than MIN_COSINE_THRESHOLD (0.6) used by recall —
      // we only spend AI on pairs likely to contradict (Pitfall: brute-force NxN explodes cost).
      const newVector = await getNewBlockVector(env, event.id); // helper reads from Vectorize
      const neighbors = await env.VECTORIZE.query(newVector, {
        topK: 4,                            // 1 will be the just-inserted vector; the other 3 are candidates
        returnMetadata: "all",
        namespace: event.workspace_id,
        filter: { type: { $eq: parsed.classified_type } },  // same memory type = same fact space
      });
      const candidates = neighbors.matches
        .filter((m) => m.id !== event.id && m.score >= 0.7)
        .slice(0, 3);
      if (candidates.length === 0) return;

      // Step 2: hydrate candidates from SQLite to get their content.
      const candidateBlocks = await stub.getBlocksByIds({
        workspace_id: event.workspace_id,
        ids: candidates.map((c) => c.id),
      });

      // Step 3: detect conflicts (parallel — each call is independent and small).
      const results = await Promise.all(
        candidateBlocks.map((c) =>
          detectConflict(env, event.content, c.content ?? "")
        )
      );

      // Step 4: for each contradiction, write to INBOX (not conflicts table).
      // Per v0.2 spec: "low-confidence inbox suggestions; never auto-alerted."
      // The inbox UI (v0.4) renders these with proposed_type="conflict"; user reviews
      // and either confirms (promotes to conflicts table) or dismisses.
      for (let i = 0; i < results.length; i++) {
        const r = results[i];
        if (r === null || r.category !== "contradiction") continue;
        await stub.moveToInbox({
          workspace_id: event.workspace_id,
          block_id: crypto.randomUUID(),       // new inbox entry, distinct from the block id
          entry: {
            content: `Possible conflict with ${candidateBlocks[i].id}: ${r.reason}`,
            proposed_type: "conflict",
            proposed_properties: {
              memory_a_id: event.id,
              memory_b_id: candidateBlocks[i].id,
              category: r.category,
              ai_confidence: r.confidence,
            },
            memorability_score: r.confidence,    // reuse the inbox memorability gate for UI sort
            source: "triage:conflict-detection",
          },
        });
      }

      writeAnalytics(env, {
        blobs: ["triage-worker", "conflict-detection", wsTag, "success"],
        doubles: [candidates.length, results.filter((r) => r?.category === "contradiction").length, 0, 0],
        indexes: [ANALYTICS_ENV_TAG],
      });
    } catch (err) {
      console.warn("triage:conflict-detection-failed", { id: event.id, err });
      // Non-fatal — main store-normal path already acked.
    }
  })()
);
```

### Rationale

- **`ctx.waitUntil` over inline await:** Conflict detection adds 1-2s of LLM latency per candidate. Keeping it OFF the critical store-normal path preserves the AI-SPEC.md §"latency budgets" 430ms p50 for `remember()`.
- **Cosine prefilter at 0.7 (NOT 0.6):** ENG-16 eval showed `detectConflict` precision drops sharply on weakly-similar pairs (the LLM happily invents contradictions when given two unrelated memories). The high cosine bar is the cheapest way to cut false-positive volume.
- **`filter: { type: { $eq: classified_type } }`:** Two memories in different `memory_type`s (e.g. `job_application` vs `meeting_note`) can't structurally contradict — they describe different fact spaces. Filtering at the Vectorize query layer (one of the four metadata indexes already created in v0.1) is free.
- **Inbox-as-suggestion, not direct write to `conflicts` table:** Per the milestone scope ("low-confidence inbox suggestions; never auto-alerted"). The `conflicts` SQLite table stays reserved for v0.3 `conflict()` MCP tool with explicit user/Claude promotion. This also avoids polluting the conflicts surface with the ~12.5% false-positive rate from ENG-16 eval.

### Alternatives considered

| Option | Why not |
|---|---|
| Brute-force NxN conflict scan in nightly Cron | Cost explodes at ~N²/2 LLM calls. 1000 memories × $0.0002/call = $0.20/night just to find duplicates. Per-write cosine prefilter scales linearly. |
| Write directly to `conflicts` table | ENG-16 P=0.875 means 1-in-8 surfaced "conflicts" are false. Auto-writing to `conflicts` would surface low-quality alerts. Inbox provides human-review gate. |
| Increase cosine prefilter threshold to 0.85 | Eliminates most candidates but misses genuine semantic contradictions phrased differently (e.g., "Alice was hired" vs "Alice declined the offer" — likely 0.72-0.78 cosine). 0.7 is the sweet spot from spike SEED-001 distance distribution. |
| Run conflict detection on inbox/cold-storage paths too | Defeats the whole memorability-gating design. If we already flagged the new write as low-importance (<0.4), it's not worth burning AI to compare against the corpus. |

### Anti-patterns to avoid

- **Do NOT call `detectConflict` synchronously inside the `remember()` MCP handler.** Adds 1-3s blocking latency to the user-facing path. Use `ctx.waitUntil` in the triage worker (already async-by-design).
- **Do NOT skip the cosine prefilter.** Direct comparison of every new memory against every existing one in the workspace is O(N) AI calls per write — turns a $0.001 ingest into a $0.10 ingest at 100-memory workspaces.
- **Do NOT write `benign_update` results to the inbox.** The eval harness already tracks these as a distinct category; the surface meaning of "conflict" in the inbox UI requires that they actually contradict.

## 2. Query Expansion in `recall()` (Feature 2)

### What ships

`recall()` currently embeds the raw user query once and runs one Vectorize
query (see `packages/mcp-server/src/tools.ts:517-547`). v0.2 inserts a CF AI
step BEFORE the embedding: rewrite the query into 3-4 semantic variants,
embed each, query Vectorize once per variant, **then merge with Reciprocal
Rank Fusion (RRF)** instead of naively concatenating + deduplicating.

### Recommended pattern: Multi-Query + RRF (NOT HyDE)

**Multi-Query rewriting** uses a small/fast LLM to generate paraphrases of
the user query — different vocabulary, different angles, different
specificity levels. Each variant is then embedded and queried against
Vectorize independently. Results are fused with RRF.

**Why NOT HyDE for v0.2:**

| Concern | HyDE | Multi-Query + RRF |
|---|---|---|
| Latency penalty (per `recall()`) | +800-1500ms (full hypothetical doc generation) | +200-400ms (4 short paraphrases in parallel) |
| Hallucination risk on personal memory | HIGH — model fabricates plausible-sounding "answers" to "what did I save about Acme" with nonsense content | NONE — model only paraphrases the QUESTION, never invents an ANSWER |
| Works well when corpus has actual documents | Yes (HyDE's original use case is academic/Wikipedia retrieval) | Yes |
| Works well for short personal-memory snippets | **No** — the hypothetical doc embedding lands closer to LLM training data than to your tiny personal note about "Alice's Acme interview" | Yes — variants share the same semantic space as the original |
| Industry recommendation for short-form retrieval | Skip | Use |

Source: HyDE 2025 follow-up research (HyPE) acknowledged HyDE's hallucination rate on personal queries is HIGH and recommended hybrid policies. Engram's corpus is precisely the worst-case shape for HyDE — short, personal, idiosyncratic.

### Reciprocal Rank Fusion merge step

After the 3-4 Vectorize queries return, **DO NOT** naively concat + dedupe by
ID + sort by cosine. That throws away the rank-position signal from each
variant. Use RRF with k=60 (the de facto standard from TREC literature):

```typescript
// packages/mcp-server/src/rrf.ts (NEW FILE — v0.2)

/**
 * Reciprocal Rank Fusion. Combines N ranked lists by summing 1/(k+rank) across
 * every list a document appears in. Documents that consistently rank high
 * across multiple expanded queries surface to the top.
 *
 * k=60 is the canonical TREC constant — small enough that top-3 results
 * dominate, large enough that mid-rank consistency boosts ranking.
 *
 * @param rankings - One ranked list per expanded query. Each list = Vectorize
 *   match[] in descending cosine order.
 * @param k - Rank constant. Default 60 per literature.
 * @returns Merged list of unique ids with combined RRF scores, sorted desc.
 */
export function reciprocalRankFusion(
  rankings: VectorizeMatch[][],
  k: number = 60,
): Array<{ id: string; rrf_score: number; best_cosine: number }> {
  const scores = new Map<string, { rrf_score: number; best_cosine: number }>();
  for (const ranking of rankings) {
    for (let rank = 0; rank < ranking.length; rank++) {
      const match = ranking[rank];
      const existing = scores.get(match.id) ?? { rrf_score: 0, best_cosine: 0 };
      scores.set(match.id, {
        rrf_score: existing.rrf_score + 1 / (k + rank + 1),       // ranks are 1-indexed in the formula
        best_cosine: Math.max(existing.best_cosine, match.score), // keep best cosine for hybrid-rank
      });
    }
  }
  return Array.from(scores.entries())
    .map(([id, s]) => ({ id, ...s }))
    .sort((a, b) => b.rrf_score - a.rrf_score);
}
```

**Integration point:** In `recall()` handler at `packages/mcp-server/src/tools.ts`,
the steps AI-04 Step 1 (embed query) and Step 2 (Vectorize query) become:

```typescript
// === v0.2 AI-04': expand query + multi-vectorize + RRF ===
const variants = await expandQuery(env, args.query);              // [original, v1, v2, v3]
const vectors = await Promise.all(
  variants.map((v) => safeRun(env, EMBEDDING_MODEL, { text: [v] }))
);
const queries = await Promise.all(
  vectors.map((vec) =>
    vectorizeQuery(env, props.workspace_id, vec.data[0], {
      topK: fetchSize,
      ...(args.types?.length ? { filter: { type: { $in: args.types } } } : {}),
      returnMetadata: "all",
    })
  )
);
const merged = reciprocalRankFusion(queries.map((q) => q.matches));

// Pass to MIN_COSINE_THRESHOLD filter using best_cosine, then hybrid-rank
const filteredMatches = merged
  .filter((m) => m.best_cosine >= MIN_COSINE_THRESHOLD)
  .slice(0, fetchSize)
  .map((m) => ({ id: m.id, score: m.best_cosine }));
```

The downstream `hybridRank` call is UNCHANGED — it consumes `{ id, score }`
shaped matches and the cosine component still works. The RRF merge replaces
the dedup step that would have been needed had we naively concat'd; the
ranking signal is now multi-variant-aware.

### Anti-patterns to avoid

- **Do NOT concatenate result lists and dedupe by max(cosine).** Throws away the multi-query signal. A document ranked #1 by query 2 and #3 by query 3 is more relevant than one ranked #1 by query 1 only — RRF captures that, max-cosine doesn't.
- **Do NOT skip the original query in the variant set.** Always include `[args.query, v1, v2, v3]` as the input to `reciprocalRankFusion`. The original query is the ground truth; variants are amplification.
- **Do NOT generate >4 variants.** Cost scales linearly with variants × (embed + Vectorize round-trip). Empirically, 3-4 variants captures 95% of the diversity benefit (DMQR-RAG paper, 2024).
- **Do NOT use `temperature: 0` for query rewriting.** Defeats the diversity goal. Use 0.5-0.7.

## 3. Synthesis Path Activation (Feature 3)

### What ships

`recall()` already accepts `verbosity ∈ {chunks, synthesis, both}` and the
synthesis branch is scaffolded at `packages/mcp-server/src/tools.ts:600-639`.
v0.2 work is **calibration + eval**, not new code: validate the existing
"stuff" pattern stays under the 2-5s p50 latency budget against the
diversified real corpus, then promote `verbosity=synthesis` from "implemented
but unvalidated" to "shipped with eval gate."

### Recommended pattern: "Stuff" (NOT map-reduce)

The three canonical RAG synthesis patterns from LangChain:

| Pattern | LLM calls | Use case | Fits Engram? |
|---|---|---|---|
| **Stuff** | 1 | All retrieved docs fit in context window | **YES** — recall returns top-25 max, each block summary <500 tokens. Fits Scout's 131K context with 99% headroom. |
| Map-Reduce | N+1 (N map + 1 reduce) | Too many docs to stuff, summaries can be combined independently | No — adds N× latency to a path with a 2-5s budget |
| Refine | N (sequential) | Iterative refinement of a single answer | No — sequential serialization breaks the latency budget |

**Engram's recall surface is "stuff-shaped" by design.** The hybrid-rank +
MIN_COSINE_THRESHOLD filter caps the input to ~25 high-quality memories;
synthesizing them into a 2-4 sentence summary is a single LLM call. Map-reduce
only becomes relevant when v0.3 ships `reflect()` (deep cross-corpus
synthesis across hundreds of memories) — flagged as a v0.3 design problem,
not v0.2.

### Model choice for SYNTHESIS_MODEL

**Recommendation: KEEP the v0.1 alias `SYNTHESIS_MODEL = llama-4-scout`.**

Synthesis is the one place in Engram where output quality matters most
(it's what Claude reads as the "summary" surfacing to the user). Scout's
17B-MoE handles the "preserve dates, sources, technical identifiers, numeric
values, decision-rejection naming" rubric (see `SYNTHESIS_SYSTEM_PROMPT` at
`tools.ts:118`) much better than a 3B model.

**Cost math:**
- Scout: $0.27/M input + $0.85/M output. A synthesis call = ~3K input (memories) + ~300 output (summary) ≈ $0.001 per `recall(verbosity=synthesis)`.
- 70B fp8: $0.293/M input + $2.253/M output ≈ $0.0015 per call. 50% more expensive for marginal quality gain (synthesis is short).
- 3.3-70b is also slower per-token (TTFT ~2s per the pricing page benchmarks), eating into the 2-5s budget.

**Anti-recommendation: Do NOT swap SYNTHESIS_MODEL to llama-3.3-70b
"because bigger is better."** Scout is calibrated to this prompt; the
ENG-22 byte-frozen prompt contract means swapping models invalidates the
eval baseline. Treat 70B as a v0.3 escalation if synthesis quality is the
bottleneck in the AI-05 eval gate.

### What's actually new in v0.2

Three concrete code changes — all in `recall-f1.eval.test.ts` and one
analytics tweak:

1. **Add `verbosity: "synthesis"` and `verbosity: "both"` test cases** to `recall-f1.eval.test.ts` covering all 27 real-corpus entries. Assert: (a) p50 latency ≤5s, (b) synthesis contains at least one date/identifier from the top-3 ranked memories (spike-findings §6 "5 drop categories" contract), (c) zero hallucinated entities not in the source set.
2. **Add LLM-as-judge assertion** for synthesis faithfulness — use the same `llama-4-scout` model as judge with a prompt asking "does this summary contain any claim NOT supported by the listed memories?" Pattern matches promptfoo's `llm-rubric` assertion style (already used in conflict-precision eval).
3. **Promote analytics signal** — the existing `writeAnalytics(... "mcp-server", CLASSIFIER_MODEL, ..., "success")` at `tools.ts:618` is already in place. Add a new `blobs[1] = "synthesis"` dimension so the v0.4 dashboard can split synthesis-path latency from extraction-path latency.

### Anti-patterns to avoid

- **Do NOT add map-reduce synthesis "because LangChain has it."** Doubles latency for zero benefit at the 25-memory cap. Reach for it ONLY when v0.3 `reflect()` needs to summarize across 100+ memories.
- **Do NOT use `temperature: 0` for synthesis.** Produces brittle, repetitive prose. `temperature: 0.3` (current value at `tools.ts:614`) is correct — preserves the cite-by-position behavior while allowing natural phrasing.
- **Do NOT mark synthesis as required when query has no good matches.** Already handled at `tools.ts:606-639`: synthesis branch is gated by `args.verbosity`, and on failure it sets `synthesis = null` and surfaces in `meta.gaps`. v0.2 should preserve that honest-failure posture per CONTEXT.md D-07.

## 4. Hybrid-Rank Weight Tuning + bge-reranker (Feature 4)

### What ships

The locked weights `HYBRID_WEIGHTS = { cosine: 1.0, recency: 0.15,
type_match: 0.2, scope_match: 0.15 }` at `packages/mcp-server/src/hybrid-rank.ts:44`
are starting heuristics per AI-SPEC §4. v0.2 Task 5.1 runs an A/B sweep
against the 27-entry diversified real corpus to either confirm or tune them.

### New tool: `@cf/baai/bge-reranker-base` (HIGH-value addition)

This is the **single biggest v0.2 stack win.** Cloudflare quietly ships a
cross-encoder reranker that scores `(query, document)` pairs directly —
purpose-built for the post-Vectorize rerank step that currently relies
entirely on cosine + heuristics.

**Specs (verified 2026-06-02 from Cloudflare docs):**
- Model: `@cf/baai/bge-reranker-base`
- Pricing: **$0.0031 per M input tokens** (~85x cheaper than Scout output)
- API shape:
  ```typescript
  await env.AI.run("@cf/baai/bge-reranker-base", {
    query: args.query,
    contexts: candidates.map((c) => ({ text: c.summary ?? c.content })),
    top_k: 25,
  });
  // Returns { response: Array<{ id: number, score: number }> } — scores in [0..1] via sigmoid
  ```
- Batches all candidates in ONE call (no parallel fanout needed)
- Cross-encoder: directly attends `(query, doc)` pairs vs bi-encoder cosine which scores them independently. Empirically 10-30% precision@5 improvement on RAG benchmarks (BEIR, MS MARCO).

**Stage 1 (existing):** Hybrid score using `bge-reranker` output as the
`cosine` component, with the recency/type/scope boosts layered on top:

**Stage 2 (new):** Insert the bge-reranker call in `recall()` BETWEEN the

```typescript
  query: args.query,
  contexts: rerankCandidates.map((c) => ({
    text: c.summary ?? c.content?.slice(0, 1500) ?? "(empty)",
  })),
  top_k: filteredMatches.length,
});

// rerankResp.response is an array of { id: index, score: number } — map back to block ids
const rerankByIdx = new Map(
  (rerankResp.response as Array<{ id: number; score: number }>).map((r) => [r.id, r.score])
);
const matchesWithRerank = filteredMatches.map((m, idx) => ({
  ...m,
  rerank_score: rerankByIdx.get(idx) ?? m.score,  // fall back to cosine if reranker omits
}));

const ranked = hybridRank(matchesWithRerank, rerankCandidates, args, Date.now());
```

### Cost / latency budget

- Reranker call: ~25 contexts × ~500 chars ≈ ~12K input tokens × $0.0031/M ≈ **$0.000037 per recall()** — effectively free.
- Latency: single round-trip, ~150-300ms (cross-encoder over short summaries). Fits the recall budget comfortably.
- Net effect on `recall(verbosity=chunks)` p50: +300ms (~1.5s → ~1.8s). Still under the 2-5s budget that synthesis sits at.

### Anti-patterns to avoid

- **Do NOT skip the bge-reranker call to "save 300ms".** It is the single best precision improvement available in v0.2 at a near-zero cost. The 300ms is well under the recall budget.
- **Do NOT delete the cosine component entirely.** Keep `match.score` (raw Vectorize cosine) as the fallback when the reranker is unavailable (test envs, AI binding failures). Defensive coding pattern matches the v0.1 `safeRun` discipline.
- **Do NOT tune weights against synthetic fixtures.** The diversified real-corpus (19 job-search + 8 non-job per session context) is the ONLY trustworthy signal. Synthetic queries optimize for synthetic queries. Per RTK + the developer profile "Frustrations: regression" directive, the sweep must protect against weight changes that improve synthetic precision but regress real-corpus recall.
- **Do NOT version-bump `HYBRID_WEIGHTS` without an audit comment.** Per `hybrid-rank.ts:42-43`: "Plan 05-06's weight-tuning task commits tuned values here with a dated audit comment." Same rule applies to the v0.2 sweep — comment must reference the eval run + the corpus version used.

## 7. Risks & Things That Will Move on You

| Risk | Severity | Mitigation |
|---|---|---|
| Cloudflare deprecates `llama-3.2-3b-instruct` (the v0.2 query-expansion target) | LOW | The 2026-04-20 changelog announced deprecations effective 2026-05-30 — Scout family + Llama 3.2 family stayed. But monitor `developers.cloudflare.com/workers-ai/changelog/` monthly. Fallback: `INGESTION_CLASSIFIER_MODEL` (Scout) — the alias swap is a one-line revert. |
| `bge-reranker-base` API shape changes (`{id, score}` vs alternative) | LOW | Cloudflare's reranker API has been stable since 2024. Pin to the documented response shape; wrap in a thin `safeRerank(env, query, contexts)` helper so any future shape change is one-file. |
| RRF merge with very small K (only 3-4 candidates per variant) underperforms vs simple max-cosine | LOW | The eval harness in `hybrid-rank-sweep.eval.test.ts` should include a `rrf: false` ablation arm. If RRF doesn't beat max-cosine on the real corpus by ≥3% recall@5, drop it and revert to dedup-by-max. |
| `detectConflict` 12.5% false-positive rate floods inbox | MEDIUM | Inbox-only surface is the mitigation: false positives degrade UX (Russell sees noise) but don't corrupt data. v0.3 conflict() tool gives Claude/user the explicit promote path. Add an analytics counter on inbox writes from `triage:conflict-detection` so we can spot a flood early. |
| Query expansion injects bias from the rewriter model | MEDIUM | The prompt's "Do NOT invent facts" rule is the firewall. Eval gate must include: take a query with a misspelled entity, confirm the variants don't "correct" the misspelling (which would change the semantic target). Add this case to `query-expansion-recall.eval.test.ts`. |
| Synthesis hallucinates entities not in the source memories | MEDIUM | Already addressed by the v0.1 byte-frozen `SYNTHESIS_SYSTEM_PROMPT` ("Acknowledges gaps when the memories don't directly answer the query — do NOT fabricate"). v0.2 work adds the LLM-judge faithfulness assertion as the regression gate. |
| Sweep tunes weights to corpus quirks that don't generalize | MEDIUM | Hold out a 5-entry slice of the real corpus for validation (not in the sweep set). Any weight change must improve held-out metrics, not just training metrics. Note: 27 entries is genuinely too small for robust generalization claims — flag this in the sweep results doc. |
| `ctx.waitUntil` in triage worker exceeds CPU/wall-clock budget on burst loads | LOW | Worker CPU budget is configurable up to 5min (current default 30s per v0.1 STACK.md §5). Conflict prefilter adds ~3-5s per message at most (3 candidates × ~1s LLM each in parallel). Well within budget. Monitor via the existing `triage:do-rpc-failed` analytics. |
| Workers AI 429 rate limits on the rewriter call | LOW | Existing `safeRun` helper already wraps `env.AI.run` with 429 detection (`tools.ts:354`). Rewriter call uses the same helper. On 429, recall falls back to single-query (no expansion) and surfaces `meta.gaps`. |
