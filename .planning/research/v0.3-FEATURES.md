# Feature Landscape — v0.3 Identity + Surface

**Domain:** MCP-native AI memory product, first human-facing frontend
**Milestone:** v0.3 Identity + Surface
**Researched:** 2026-06-12
**Predecessor:** v0.1 + v0.2 FEATURES.md (MCP tool surface and intelligence layer — those are DONE; this doc is frontend-only)

---

## Context: What Is Being Surfaced

v0.2 shipped a fully working backend. The data that needs a UI already exists in SQLite:

| Table | What's in it | Why it needs a UI now |
|-------|--------------|----------------------|
| `inbox` | Low-confidence captures (0.4–0.8 score) + conflict suggestions (`proposed_type="conflict"`) | Conflict detection shipped in v0.2 but has no human-readable surface — rows just accumulate |
| `conflicts` | Explicitly detected contradictions with severity (low/medium/high), `memory_a_id`, `memory_b_id`, `description`, `resolved_at` | Written by triage pipeline; never read by a human today |
| `blocks` | Every stored memory: type, content, summary, properties (JSON), embedding_id, scope, source, confidence, tags | MCP-queryable but not browsable by a human |
| `relations` | Knowledge graph edges: `from_id`, `to_id`, `relationship` | Invisible to humans; only surfaced via `recall()` context array |
| `tags` | User-applied and AI-inferred tags on blocks | Never rendered in a UI |
| `ENGRAM_IDENTITIES` KV | Sub -> `{ workspace_id, user_id }` mapping | Still bootstrapped by 8-step terminal dance |

The four feature areas are independent in data dependencies but share a single frontend deployment.

## Feature Area 1: Consent / Sign-In Flow

### What It Is

A browser-based flow where a new user (Devon, future users) can connect Engram to Claude Desktop without touching a terminal. Replaces the 8-step `kv:bootstrap` dance documented in ENG-11-DESIGN.md.

### Critical Finding: Email Sending Constraint

**The "CF Email Routing magic links" framing in the milestone description is ambiguous.** Research found two distinct Cloudflare email products:

- **Email Routing** (generally available, free): Handles _incoming_ email only. Cannot send outbound to arbitrary addresses.
- **Email Sending / Email Service** (beta, Workers Paid required): Can send outbound to arbitrary addresses. 3,000 emails/month included on paid plan. Currently in public beta.

For magic links to work for Devon (a new, unverified user), you must either:
1. Use **Cloudflare Email Sending** (beta, requires Workers Paid — Russell is already on Workers Paid for Vectorize)
2. Use **Resend** via HTTP fetch (stable, free tier 3k/mo, Cloudflare's own documented tutorial recommends it)

Verdict: Email Sending via Cloudflare's own binding (`env.EMAIL.send()`) is viable because Russell is on Workers Paid, but it is in beta. Resend is the safer production choice with the same free economics at v0.3 scale (2 users). **Flag this as a decision point for requirements, not a blocker.** Either path uses the same flow shape below.

### Table Stakes

| Feature | Why Expected | Complexity | Backend Dependency |
|---------|--------------|------------|-------------------|
| Email entry form at `/auth/login` | Entry point for the flow; cannot start without it | Low | None (static HTML) |
| Magic link generation + storage | Token = `crypto.randomUUID()`, stored in KV with 15-minute TTL (`expirationTtl: 900`; KV minimum TTL is 60s) | Low | KV (new `ENGRAM_MAGIC_TOKENS` namespace) |
| Transactional email send (magic link) | Delivers the link to the user's inbox | Low-Med | CF Email Sending binding OR Resend HTTP fetch (decision point) |
| Token verification endpoint (`/auth/callback?token=...`) | Validates token from KV, exchanges for identity, creates session | Med | KV read + `ENGRAM_IDENTITIES` KV write |
| First-sign-in workspace bootstrap | Auto-creates `workspace_id` from email slug on first successful auth (replaces manual `kv:bootstrap` step) | Med | `ENGRAM_IDENTITIES` KV write — same schema as existing `kv-bootstrap.mjs` |
| Session cookie issuance | Signs a short-lived session cookie (`__Secure-session`, HttpOnly, SameSite=Strict) after token verification | Med | KV or existing OAuth infrastructure |
| "Check your email" interstitial | User sees this after submitting their email; explains what to expect | Low | None (static page) |
| Post-sign-in success page with MCP config snippet | After first sign-in, show: workspace is ready + the exact `claude_desktop_config.json` block to paste | Low | Read from verified session — workspace_id is known |
| Returning user flow (link verify, skip bootstrap, redirect to dashboard) | If KV identity already exists for this email's sub, no bootstrapping needed; redirect to /inbox | Low | `ENGRAM_IDENTITIES` KV lookup |

### Differentiators

| Feature | Value | Complexity | Notes |
|---------|-------|------------|-------|
| One-click copy for `claude_desktop_config.json` snippet | Eliminates the copy-paste error that caused Russell to wipe his config in v0.1 | Low | JS clipboard API + "Copied!" toast |
| Workspace name picker at first sign-in | More personal than the auto-slug | Low | One extra form field before KV write |
| Auto-detect if `mcp-remote` is already installed (deep link scheme) | Could open Claude Desktop directly after auth | High | Not standard; skip for v0.3 |

### Anti-Features (Do Not Build for v0.3)

| Anti-Feature | Why Avoid | What to Do Instead |
|--------------|-----------|-------------------|
| Password authentication | Passwords require bcrypt, reset flows, and account lockout — entire class of security complexity not needed for a 2-user product | Magic link only. Passwords belong in v1.0 if at all |
| OAuth social login (Google, GitHub) | Each provider requires app registration, scopes, callback verification, and token refresh — 3-5 days of work for 2 users | Defer to v1.0 managed cloud path |
| Email + OTP (6-digit code) | More complex than a link; identical security properties | Magic link already solves the use case |
| Email rate-limiting / anti-abuse | At 2 users, unnecessary. KV TTL on tokens is sufficient | At v1.0 scale add Cloudflare rate limiting rule |
| "Remember this device" checkbox | Cookie session already handles this; checkbox implies persistent vs session semantics that add state | Not needed at v0.3 scale |
| Account deletion / data export in sign-in flow | Separate concern; belongs in admin area | See Feature Area 4 |
| Multi-email / alias support | One workspace, one primary email per user | Defer to v0.4/v1.0 |

### Flow Shape (Table Stakes Target)

```
Devon's journey (first user, less than or equal to 5 steps):
  1. Russell sends Devon the URL: https://engram.workers.dev/auth/login
  2. Devon enters email, clicks "Send magic link"
  3. Devon checks email, clicks link (15-min expiry, single-use)
  4. Browser: Engram verifies token, bootstraps workspace, issues session cookie
     -- success page shows: "Your memory workspace is ready."
     -- Shows pre-filled claude_desktop_config.json block with copy button
  5. Devon adds to Claude Desktop config, restarts Claude Desktop

Returning user (Russell):
  1. Visits /auth/login
  2. Enters email, clicks link
  3. Token validates against existing KV identity -> session cookie -> redirect to /inbox
```

**Important:** This browser session (for the UI) is PARALLEL to, not a replacement for, the MCP OAuth flow (used by Claude Desktop's `mcp-remote` bridge). The existing `oauth.ts` `/authorize` handler is unchanged. Two auth paths coexist:
- MCP path: Claude Desktop -> `mcp-remote` -> OAuth PKCE -> KV identity lookup (existing, unchanged)
- Browser UI path: email -> magic link -> session cookie -> KV identity lookup (new)

### Backend Dependencies

- KV namespace: `ENGRAM_MAGIC_TOKENS` (new, TTL-governed tokens)
- KV namespace: `ENGRAM_IDENTITIES` (existing; first-sign-in writes the same `{ workspace_id, user_id }` shape as `kv-bootstrap.mjs`)
- Email sending: CF Email Sending binding (`send_email`) OR Resend fetch (decision at requirements phase)
- Static assets binding in `mcp-server` Worker (co-located, not a new Worker — see Frontend Deployment section)
- Existing `oauth.ts` is NOT replaced; session cookies are a new auth layer for the browser UI only

## Feature Area 2: Inbox UI

### What It Is

A human-readable review surface for two kinds of items the v0.2 triage pipeline already writes into SQLite but never shows a human:

1. **Low-confidence captures** — memorability 0.4-0.8; stored in `inbox` table with `proposed_type`, `proposed_properties`, `memorability_score`, `source`
2. **Conflict suggestions** — `inbox` rows where `proposed_type = "conflict"`, also separately in the `conflicts` table with `memory_a_id`, `memory_b_id`, `description`, `severity`

Note: v0.2 writes conflict contradictions into `inbox` (proposed_type="conflict") AND into the `conflicts` table. The inbox UI needs to handle both entry points. The `conflicts` table is the authoritative source for conflict resolution state (`resolved_at`).

### Table Stakes

| Feature | Why Expected | Complexity | Backend Dependency |
|---------|--------------|------------|-------------------|
| Inbox list view — count badge, newest first | At minimum users need to see pending items exist | Low | `SELECT * FROM inbox WHERE resolved_at IS NULL ORDER BY created_at DESC` |
| Low-confidence item card: summary + proposed type + memorability score + source | Shows what was captured and how confident the AI was | Low | `inbox` rows: `content`, `proposed_type`, `proposed_properties`, `memorability_score`, `source` |
| Accept action on low-confidence item | Promotes to `blocks` table with confidence + type confirmed | Med | WorkspaceDO write: insert into `blocks`, delete from (or mark resolved in) `inbox` |
| Reject action on low-confidence item | Marks resolved without storing; item goes to cold storage path or is soft-deleted | Low | `inbox` update: `resolved_at = now()` |
| Edit-before-accepting (type correction, field edits) | Critical: AI classification is wrong often enough that correction before accepting is necessary | Med | Form over `proposed_properties` JSON; writes corrected values on accept |
| Conflict pair view: side-by-side Memory A vs Memory B | The core value of conflict detection; without visual comparison the description string is meaningless | Med | `conflicts` JOIN `blocks` on `memory_a_id`, `memory_b_id` |
| Conflict resolution actions: Keep A / Keep B / Keep Both | Standard resolution choices; "Keep Both" marks reviewed without deletion | Med | WorkspaceDO: `forget(id, cascade=false)` on the rejected memory; update `conflicts.resolved_at` |
| Conflict severity badge (low / medium / high) | Helps prioritize review order | Low | `conflicts.severity` already populated by v0.2 triage |
| Conflict description rendered prominently | v0.2 writes a human-readable `description` field; display it above the pair | Low | `conflicts.description` |
| Empty state — "All caught up" | Table stakes for any inbox UI; missing = feels broken | Low | Static render when `inbox` count = 0 AND unresolved `conflicts` = 0 |
| Unreviewed count in nav | Badge count like email unread | Low | `SELECT COUNT(*) FROM inbox WHERE resolved_at IS NULL` |

### Differentiators

| Feature | Value | Complexity | Notes |
|---------|-------|------------|-------|
| "Why was this flagged?" expandable reasoning | Shows memorability score, source signal — not the cosine score (not currently stored per-conflict in SQLite) | Low | Render existing `memorability_score` + `source`; cosine would need schema addition |
| Inline filter: type, source, score range | For users with many items | Med | SQL WHERE clause additions |
| Bulk accept/reject | For clearing many low-confidence items at once | Med | Multi-select UI + batch write |
| Undo (5-second window) | Prevents accidental rejections | Med | Soft-delete + scheduled hard-delete via Queues |

### Anti-Features (Do Not Build for v0.3)

| Anti-Feature | Why Avoid | What to Do Instead |
|--------------|-----------|-------------------|
| AI-suggested merge text for conflict resolution | Requires LLM call at review time — violates "CF AI for grunt work, not Claude" principle | Show two memories side-by-side; human writes merged text if needed |
| Notification emails for new inbox items | Zero-to-one product with 2 users; check the inbox | Defer to v0.4 daily digest |
| Threaded conflict discussion / comments | No team at v0.3; Russell and Devon work separately | Defer until team workspaces in v0.4 |
| Custom inbox rules / filters | Over-engineered for 2 users | At v1.0 scale with community type packs |
| Auto-accept above threshold toggle | An extra setting that increases complexity; the inbox exists because humans should review these items | Keep it as review-required |
| Priority scoring UI | `memorability_score` IS the priority signal; no human-set priority layer needed | Display score, sort by it |

### Backend Dependencies

- `inbox` table: `id`, `content`, `proposed_type`, `proposed_properties`, `memorability_score`, `source`, `created_at`
- `conflicts` table: `id`, `memory_a_id`, `memory_b_id`, `description`, `severity`, `detected_at`, `resolved_at`
- `blocks` table: reads for conflict pair display (JOIN on `memory_a_id`/`memory_b_id`)
- WorkspaceDO query helpers: `queries.ts` will need new methods — `getInboxItems()`, `resolveInboxItem(id, action, correctedData?)`, `resolveConflict(id, action, keepId?)`
- New Worker routes: `GET /api/inbox`, `POST /api/inbox/:id/accept`, `POST /api/inbox/:id/reject`, `GET /api/conflicts`, `POST /api/conflicts/:id/resolve`

## Feature Area 3: Memory Browser

### What It Is

A human browse/search/filter interface over the `blocks` table — the actual stored memories. Not a replacement for `recall()` (Claude still does semantic queries via MCP); this is for the human to verify, audit, and understand what Engram has stored.

### Table Stakes

| Feature | Why Expected | Complexity | Backend Dependency |
|---------|--------------|------------|-------------------|
| Memory list view with pagination | The most basic read surface; users need to see what is stored | Low | `SELECT id, type, summary, scope, source, confidence, created_at FROM blocks ORDER BY created_at DESC LIMIT 50 OFFSET ?` |
| Search bar (text match on summary/content) | Without search the browser is useless beyond first few records | Low | SQLite LIKE or FTS5 on `blocks.content` + `blocks.summary` |
| Filter by memory type | Typed blocks have different structures; type is the primary browse dimension | Low | `WHERE type = ?` using values from `memory_types` table |
| Filter by scope (personal / project / org) | Plant the scope filter now even though v0.3 is single-workspace | Low | `WHERE scope = ?` |
| Filter by date range | "What did I remember last week?" is a natural query | Low | `WHERE created_at BETWEEN ? AND ?` |
| Filter by tag | AI-inferred and user-applied tags exist in `tags` table | Low | JOIN `tags` on `block_id WHERE tag = ?` |
| Memory detail view | Click a list item: see full content, summary, all properties, source, confidence, related memories, tags | Med | `blocks` + `tags` + `relations` JOIN for detail panel |
| Summary vs raw content toggle | Engram stores both `summary` (CF AI) and `content` (original); users sometimes want the original | Low | Toggle in detail view: `blocks.summary` vs `blocks.content` |
| Extracted properties panel | `blocks.properties` is a JSON object with typed fields per memory_type | Low | Render `properties` JSON as labeled field list using `memory_types.fields` schema |
| Tags display (AI-inferred + user-applied) | Already stored in `tags` table with `source` field | Low | JOIN `tags` WHERE `block_id = ?` |
| Related memories list in detail view | `relations` table shows explicit knowledge graph edges | Low | `SELECT * FROM relations WHERE from_id = ? OR to_id = ?` |
| Delete memory (single record) | Users need ability to remove incorrectly stored items | Low | Maps to existing `forget(id)` MCP tool via Worker API route |
| Confidence score indicator | Visual signal of how sure the AI was; helps spot misclassifications | Low | `blocks.confidence` as a colored badge |
| Source badge (mcp:claude, connector:slack, etc.) | Provenance is important for a memory product | Low | `blocks.source` |

### Differentiators

| Feature | Value | Complexity | Notes |
|---------|-------|------------|-------|
| Semantic search integration | Wire the search bar to the existing `recall()` Vectorize backend instead of (or in addition to) SQLite LIKE | Med-High | Bridges human UI to MCP tool; worthwhile differentiator that validates the recall path; adds Worker-to-Worker routing complexity |
| Entity highlight in summary | Bold entity names in the summary text | Med | Requires entities stored per block — check if triage pipeline stores extracted entities in `properties` or separately |

### Anti-Features (Do Not Build for v0.3)

| Anti-Feature | Why Avoid | What to Do Instead |
|--------------|-----------|-------------------|
| Inline memory editing | Risk: editing AI-extracted properties breaks semantic consistency (embedding was for original content); mutation needs re-embedding | Read-only for v0.3. Add edit + re-embed path in v0.4 |
| Bulk operations (multi-select delete, tag, etc.) | 2 users, early product — adds UI complexity before basic read experience is validated | Single-record delete is sufficient |
| Full knowledge graph visualization | Graph rendering (D3, Cytoscape) is a product in itself; at v0.3 the related memories list in detail view is sufficient | Defer to v0.4 |
| Memory type schema editor (create/edit custom types) | Memory types are schema-as-data but the editor belongs with the multi-workspace work in v0.4 | List the system types; do not surface the editor |
| Sorting by semantic relevance without a query | Sort by date/type/confidence is enough without a query | Semantic sort only makes sense when the user has entered a query |
| Export from UI | `export()` MCP tool is scoped for v0.4 | Let Claude call `export()` for now |
| Real-time auto-refresh as new memories arrive | WebSocket sync is an explicit anti-feature; apply same logic | Manual refresh or page reload is sufficient |
| Editing relations / tags from the browser | Mutations that affect the graph should go through the MCP tools to preserve invariants | Read-only graph display; mutations via MCP |

### Backend Dependencies

- `blocks` table: all columns
- `tags` table: JOIN on `block_id`
- `relations` table: JOIN on `from_id`/`to_id`
- `memory_types` table: for rendering typed `properties` fields with labels
- New Worker routes: `GET /api/memories` (list, filter, paginate), `GET /api/memories/:id` (detail), `DELETE /api/memories/:id`
- Optional differentiator: `recall()` tool for semantic search path (direct Vectorize query or internal tool dispatch)

## Feature Area 4: Admin + Eval-Budget Dashboard

### What It Is

Minimal management surface: identity/workspace administration (today: Russell + Devon) and a Workers AI neuron-spend dashboard that productizes `scripts/eval-budget-summary.mjs` into a browser view.

**Scope calibration:** v0.3 is a single-tenant product (Russell's Cloudflare account, Russell + Devon as users). "Admin" at this scale means seeing who is connected, inviting a second user, and viewing Workers AI neuron spend. It does NOT mean billing, role matrices, or multi-tenant isolation.

### Table Stakes

| Feature | Why Expected | Complexity | Backend Dependency |
|---------|--------------|------------|-------------------|
| Connected users list | See who has KV identity records: user_id, workspace_id | Low | `ENGRAM_IDENTITIES` KV list (only 2 entries at v0.3; full list scan is acceptable) |
| Invite user (admin-triggered magic link) | The primary onboarding action: Russell enters Devon's email, system sends a magic link with pre-created workspace slot | Med | Magic link flow (Feature Area 1) + optionally a new `ENGRAM_INVITES` KV entry OR reuse magic tokens with an `invited_by` metadata field |
| Eval-budget table: neuron spend by model, last 7d / 30d | Productizes `eval-budget-summary.mjs` — shows which Workers AI models consume the most neurons | Med | Analytics Engine SQL API: `POST https://api.cloudflare.com/client/v4/accounts/${env.CF_ACCOUNT_ID}/analytics_engine/sql` with Bearer token; requires `CF_API_TOKEN` as a Worker secret |
| Current-month neuron total + estimated cost | Shows the $0.011/1000 cost calculation explicitly | Low | Aggregate query on Analytics Engine dataset |
| Workers AI daily free tier headroom display | 10,000 neurons/day free — show how much daily headroom remains | Low | Today's spend query: `WHERE timestamp > toStartOfDay(now())` |

### Differentiators

| Feature | Value | Complexity | Notes |
|---------|-------|------------|-------|
| Eval-budget chart: spend over time | Time-series line chart of daily neuron spend | Med | Same SQL query, `GROUP BY toStartOfDay(timestamp)` — render as SVG or Canvas chart |
| Per-model neuron breakdown | Shows which models (bge-base, llama3, etc.) cost the most | Low | `GROUP BY model_name` in SQL query |
| Cost alert threshold (warn above N neurons/day) | Self-service budget guard to avoid bill shock | Med | KV-stored threshold + warning banner |
| Workspace reset / re-bootstrap button | For development: flush identity + restart without a terminal | Med | Worker route that calls existing `kv:bootstrap` logic with cleared state |

### Anti-Features (Do Not Build for v0.3)

| Anti-Feature | Why Avoid | What to Do Instead |
|--------------|-----------|-------------------|
| Role-based access control (owner/editor/viewer) | `members` table exists but v0.3 has 2 users; RBAC adds 3-5 days of middleware for zero user value today | All v0.3 users are owners; add RBAC in v0.4 when teams exist |
| Workspace billing / Stripe integration | 0 paying customers; billing belongs at v1.0 | Record spend data now via Analytics Engine; bill later |
| Multi-tenant admin (cross-workspace visibility) | Russell's account only; other users' workspaces are isolated by WorkspaceDO | Defer to v1.0 managed cloud |
| Audit log / security event log | At 2 users, auditing is theatre | Add at v1.0 when SOC2 matters |
| Team management (invite by role, revoke by role) | One workspace, two users | Single "invite" action is sufficient |
| Custom domain management | Worker is on `*.workers.dev`; custom domain is a v1.0 concern | Use the default workers.dev URL |
| Grafana / external dashboard integration | Analytics Engine has Grafana support, but standing up Grafana for 2 users is enormous overhead | Build the chart inline in the UI; Grafana is for future scale |
| Cloudflare AI Gateway spend integration | AI Gateway is a separate product not currently wired into Engram | Pure Workers AI Analytics Engine is sufficient for v0.3 |
| User deletion / workspace archive | Not needed at 2 users | Delete by running `kv:bootstrap` in reverse; add UI in v1.0 |

### Backend Dependencies

- KV: `ENGRAM_IDENTITIES` (list, read) — existing
- KV: `ENGRAM_MAGIC_TOKENS` (write invite tokens) — new, shared with Feature Area 1
- Analytics Engine: `AI_ANALYTICS` dataset (existing — `eval-budget-summary.mjs` already writes to it)
- New Worker routes: `GET /api/admin/users`, `POST /api/admin/invite`, `GET /api/admin/budget`
- Worker secrets required: `CF_ACCOUNT_ID` (32-char account ID), `CF_API_TOKEN` (scoped to Analytics Engine read) — must be stored as Worker secrets via `wrangler secret put`, NOT in wrangler.jsonc
- Analytics Engine SQL API is external HTTP only; no internal binding for reads. Worker issues `fetch()` to `https://api.cloudflare.com/...`

## Cross-Cutting: Frontend Deployment

### Where Does the UI Live?

Two options within the Cloudflare-only constraint:

| Option | Shape | Tradeoff |
|--------|-------|----------|
| Static assets in existing `mcp-server` Worker | Add `assets: { directory: "dist", binding: "ASSETS" }` to `mcp-server`'s `wrangler.jsonc`; single Worker serves MCP + UI | Simpler deployment; one Worker to configure; API routes coexist with MCP routes. Cloudflare's full-stack blog explicitly recommends this pattern. |
| New dedicated `engram-ui-worker` package | Separate Worker serving only the UI; calls mcp-server's internal routes | Cleaner separation on paper but doubles the Workers to deploy/configure; over-engineered for v0.3 |

**Recommendation:** Co-locate UI in `mcp-server` Worker using static assets binding with SPA mode (`index.html` fallback for client-side routing). Cloudflare has explicitly moved investment from Pages to Workers for exactly this full-stack use case (confirmed 2026).

### Framework (noted here as input to STACK.md)

Options in order of appropriate complexity for 4 screens with 2 users:

1. **Vanilla HTML + Alpine.js or HTMX**: Zero build step, ~10-20KB total. Appropriate. HIGH confidence.
2. **Preact + Vite**: 3KB runtime, React-compatible API. Good for interactive UIs. Moderate complexity increase.
3. **React/Next.js**: Over-engineered for 4 screens at 2-user scale; ~40KB baseline JS for no gain. Anti-feature.

## Feature Dependencies

```
Feature Area 1 (Auth) must ship before Feature Area 2 (Inbox) and 3 (Memory Browser)
  -- Inbox and Memory Browser require a session to know which workspace to query

Feature Area 4 (Admin -- Invite) depends on Feature Area 1 (Magic Link generation)
  -- Admin invite flow reuses the magic link token generation + email send logic

Feature Area 2 (Inbox -- Conflict pair view) depends on blocks table reads
  -- Conflict resolution requires reading Memory A + Memory B from blocks

Email sending decision (CF Email Service beta vs Resend) gates Feature Area 1 + Feature Area 4
  -- Both auth flow and admin invite need the same email sender; decision once, used twice
```

## MVP Recommendation

Given the wide scope and the non-negotiable goal of Devon connecting without a terminal:

**Must ship (v0.3 acceptance gate):**
1. Auth: email entry -> magic link -> token verify -> workspace bootstrap -> MCP config snippet page
2. Inbox: list + accept/reject on low-confidence items + conflict pair view + resolve actions
3. Memory browser: list + type/date filter + detail view (read-only)
4. Admin: connected users list + invite action + neuron spend table

**Defer within v0.3 (stretch if time allows):**
- Eval-budget time-series chart (table is the MVP; chart is stretch)
- Semantic search in memory browser (LIKE search is sufficient for v0.3 scale)
- Bulk inbox actions
- Conflict "why flagged" expand panel
- Cost alert threshold in admin

**Confirmed anti-features (do not build at any point in v0.3):**
- Password auth or social OAuth login
- Inline memory editing
- Full graph visualization
- RBAC / role management
- Billing / Stripe
- Real-time WebSocket updates
- Memory type schema editor
