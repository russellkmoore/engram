## TL;DR — The Big Decisions

1. **Ship 3 phases, not 4.** Pitfall INT-1 (re-embed audit) + conflict-wiring + hybrid-rank tuning belong in Phase A (foundation). Query-expansion + bge-reranker belong in Phase B (recall rewrite). Synthesis eval + default-stays-`chunks` belong in Phase C. Mapping 4 features → 4 phases is the naive arrangement; the dependency graph collapses to 3 because conflict-wiring is orthogonal to the recall path and rides alongside hybrid-rank tuning.

2. **Add `@cf/baai/bge-reranker-base` to the stack — but only inside Phase B's recall rewrite.** STACK calls it "the single biggest v0.2 stack win" (HIGH confidence: GA, $0.0031/M, +10-30% precision@5 on RAG benchmarks). FEATURES warns "wait until corpus > 1000." Reconciliation below — STACK wins on the cost/latency math; FEATURES wins on the "validate against real corpus first" caveat.

3. **Multi-query + RRF (3 variants) — NOT HyDE, NOT 4 variants, NOT always-on.** All 4 research files converge: HyDE hallucinates against personal-memory corpora. Cap at 3 variants (PITFALLS QE-1 cost), gate behind `top1_cosine < 0.65` adaptive routing (FEATURES + PITFALLS QE-1 + QE-2). The 0.85 variant-similarity gate (PITFALLS QE-2) is mandatory.

4. **Conflict-detection wires into `store-normal` via `ctx.waitUntil`, writes to inbox (NOT the conflicts table).** STACK + ARCHITECTURE agree on the integration point (triage-worker `store-normal` branch, post-enrichment, cosine prefilter at 0.7, top-K=3-5 same-type neighbors). The only disagreement was *where the write lands* — STACK says `inbox` (`proposed_type="conflict"`); ARCHITECTURE says `conflicts` table + `moveToInbox`. **Resolution: write to inbox only** per STATE.md decision 5 and ENG-16 verdict; the `conflicts` table remains reserved for v0.3 `conflict()` MCP tool's explicit promotion path. ARCHITECTURE's `insertConflict` RPC moves to v0.3.

5. **Keep `verbosity` default at `"chunks"`. Synthesis is opt-in for v0.2.** ARCHITECTURE flagged the flip-to-`"both"` as Open Q4; STACK + FEATURES + PITFALLS SY-6 all argue against. Synthesis adds 2-5s p50 latency on every recall — that's a user-visible contract change that needs dogfooding evidence before flipping. v0.2 ships the eval gate + LLM-judge faithfulness check, NOT the default flip.

## Convergence — Where All 4 Agents Agreed (HIGH-Confidence Inputs)

These claims appear in 3+ of the 4 research files, independently sourced. Plan against them with confidence:

1. **HyDE is wrong for Engram's personal-memory corpus.** STACK §2 anti-pattern, FEATURES table "skip for v0.2", PITFALLS QE-3 explicit failure mode. All cite the same root cause: personal/short queries are exactly HyDE's worst-case shape.

2. **RRF with k=60 is the right multi-query merge.** STACK §2, ARCHITECTURE §3, FEATURES query-expansion table. Industry-standard constant (Elasticsearch / Azure / AI21 all use 60). ARCHITECTURE provides the implementation; STACK confirms behavior; FEATURES confirms the pattern.

3. **Cosine prefilter at ≥0.7 (TIGHTER than recall's 0.6) before calling `detectConflict`.** STACK §1, ARCHITECTURE §2, PITFALLS CD-3 all converge. Brute-force NxN scan is unacceptable cost; same-type filter + top-3 neighbors caps AI calls per ingest.

4. **`ctx.waitUntil` keeps conflict scan OFF the critical `remember()` path.** STACK + ARCHITECTURE both place it after `updateBlockEnrichment` in the `store-normal` branch, async by design. PITFALLS CD-3 confirms ingest latency must not visibly degrade.

5. **No new npm dependencies needed for v0.2.** STACK §5 explicit, ARCHITECTURE inventories only new internal modules, FEATURES does not introduce any. Everything goes through `safeRun(env, MODEL_ID, args)` and existing zod@4 + ai-config patterns.

6. **Synthesis stays as "stuff" pattern (single LLM call over all retrieved memories).** STACK §3 + FEATURES synthesis-pattern table + ARCHITECTURE §4 all reject map-reduce / refine for v0.2. The 25-memory cap fits Scout's 131K context with 99% headroom. Map-reduce is v0.3 `reflect()` territory.

7. **Synthesis grounding + citation linkage is mandatory.** PITFALLS SY-1 + SY-2 are catastrophic-severity; STACK §3 prescribes LLM-judge faithfulness assertion; FEATURES list "cite source memories" as table stakes. All four files demand inline `[memory_id]` markers + post-process drop of uncited sentences.

8. **27-entry corpus is too small for robust weight-tuning generalization.** PITFALLS HR-1, HR-4 explicit; FEATURES "scope creep" warning; STACK §4 risk row 6. Train/validate split is mandatory; documented as a known limitation, NOT swept under the rug.

9. **Inbox UI work is OUT of v0.2.** FEATURES "anti-feature" call-out, STACK §2 "v0.4 connector", PITFALLS CD-6 explicitly defers to v0.3. Conflicts surface via `EngramResponse.context.conflicts` field + the existing inbox SQLite table. No React/Astro work in this milestone.

10. **The v0.1 `EngramResponse<T>` envelope is frozen. New fields require explicit contract bumps.** PITFALLS INT-4 + INT-6, ARCHITECTURE "no-touch components", STACK §6 integration table. Synthesis populates an EXISTING null field (`result.synthesis`); expanded queries surface in `meta`, not a new top-level field.

11. **Re-embed audit (INT-1) MUST run before any v0.2 feature ships.** PITFALLS catastrophic-severity, ARCHITECTURE doesn't directly address but presumes v2 vectors throughout, STACK §6 confirms "no Vectorize index change" only holds if v1 holdovers don't exist. The 768d→1024d switch from ENG-25 is silently destructive if v1-stamped rows persist.

## Divergence — Where Research Disagrees (and How to Resolve)

### D-1: bge-reranker-base — Add (STACK) or Defer (FEATURES)?

**STACK §4:** "The single biggest v0.2 stack win... +10-30% precision@5 on RAG benchmarks... $0.000037 per recall, effectively free." HIGH confidence.
**FEATURES query-expansion table:** "BAAI/bge-reranker-base — but at 50-100 memories, the rerank score noise > signal. Wait until corpus > 1000 memories." Anti-feature for v0.2.

**Resolution: ADD bge-reranker, ship behind an ablation arm.**
- STACK's cost/latency math is unambiguous and Cloudflare-verified.
- FEATURES' concern is corpus-size, not API/cost. Address it empirically in Phase A's `recall-ranking.eval.test.ts`: include `rerank: 1.0` vs `rerank: 0.0` ablation; if reranker doesn't beat cosine on the 27-entry corpus by ≥3% precision@5, ship with `rerank: 0.0` (effectively disabling it via the weight) and flip to `rerank: 1.0` in v0.3 when corpus grows.
- The `RERANKER_MODEL` constant lands in `@engram/ai-config` regardless; the toggle is the hybrid-rank weight, not a code-path branch.
- Evidence used: STACK Cloudflare-doc verification + FEATURES' explicit "revisit when corpus > 1000" — both can be honored by gating on the weight rather than the integration.

### D-2: `llama-3.2-3b-instruct` model swap for `QUERY_EXPANSION_MODEL`

**STACK §2:** Specialize to 3.2-3b (5.3x cheaper, 2.5x faster TTFT). MEDIUM confidence + eval gate required.
**ARCHITECTURE §3:** "Maybe specialize SYNTHESIS_MODEL / QUERY_EXPANSION_MODEL" — punts on the call.
**FEATURES:** Does not address model choice for the rewriter.
**PITFALLS QE-7:** 429-fallback critical, but doesn't speak to which model.

**Resolution: Land the model swap as an A/B inside `query-expansion-recall.eval.test.ts`, not as the default.**
- v0.2 ships with `QUERY_EXPANSION_MODEL` aliased to `INGESTION_CLASSIFIER_MODEL` (Scout) — same as v0.1.
- The eval test runs 3.2-3b vs Scout side-by-side over the 27-entry real corpus.
- If 3.2-3b matches Scout within 5% recall@5 (STACK's threshold), promote it via a one-line audit-commented alias change in a follow-on PR — does NOT block the milestone.
- This honors STACK's MEDIUM-confidence flag without burning planning bandwidth on a reversible optimization.

### D-3: Phase Structure — 4 phases (FEATURES) vs 3 phases (ARCHITECTURE) vs N/A (STACK feature-by-feature)

**FEATURES "Suggested Phase Ordering":** 4 phases — conflict → hybrid-rank → synthesis → expansion.
**ARCHITECTURE build-order graph:** 3 phases — Phase A (#1 + #2), Phase B (#3), Phase C (#4).
**PITFALLS:** Implicit — Plan 01 = INT-1 + INT-2 + INT-5 (foundation), then per-feature plans.

**Resolution: 3 phases as ARCHITECTURE proposes, with PITFALLS Plan 01 prepended as Wave 0.**

| Phase | Scope | Why |
|---|---|---|
| **Wave 0 (Phase A.0)** | INT-1 re-embed audit, INT-2 tiered test strategy, INT-5 integration-matrix doc | PITFALLS catastrophic gate; must complete before ANY feature work touches Vectorize |
| **Phase A** | Hybrid-rank tuning (#1) + Conflict-detection wiring (#2) | Orthogonal — different workers, different files; A.1 stabilizes recall baseline, A.2 ships independently in triage-worker |
| **Phase B** | Query expansion + RRF + bge-reranker integration in `recall()` (#3) | Depends on A.1's stable hybrid-rank; introduces multi-query path |
| **Phase C** | Synthesis activation eval + LLM-judge faithfulness gate (#4) | Depends on B (synthesis quality is downstream of recall coverage); defaults stay opt-in |

FEATURES' 4-phase ordering (conflict-first) is rejected because conflict-wiring depends on the ENG-16 50-sample precision validation, which is **independent of recall path** — it can run in parallel with hybrid-rank tuning in the same wave. Splitting them across phases serializes work unnecessarily.

### D-4: Hybrid-rank tuning — Ships FIRST (ARCHITECTURE, STACK) or LAST (FEATURES)?

**ARCHITECTURE TL;DR:** "#1 first — stabilizes recall quality baseline."
**STACK §4:** Implicitly first (it's "Feature 4" in their numbering but they call it foundational).
**FEATURES "Suggested Phase Ordering":** Phase 2 (after conflict, before synthesis).
**PITFALLS:** Embedded throughout; doesn't directly order.

**Resolution: Hybrid-rank tuning is Phase A.1 (first feature work after Wave 0).** ARCHITECTURE's argument carries: the RRF merge in Phase B fuses against hybridRank's output. Tuning weights AFTER RRF lands means every weight-sweep iteration also has to account for fusion behavior — entangles variables (PITFALLS HR-6 anti-pattern). Pin weights first against single-query baseline, then layer RRF/reranker on the stabilized formula.

### D-5: Conflict scan placement — per-write (STACK + ARCHITECTURE) or batched nightly (FEATURES doesn't address; PITFALLS CD-3 hints at multi-stage Queue)?

**STACK §1:** Per-write via `ctx.waitUntil` in `store-normal` branch with cosine prefilter.
**ARCHITECTURE §2:** Per-write via `scanConflicts()` helper after `updateBlockEnrichment`.
**PITFALLS CD-3:** "Conflict detection runs as a separate Queue stage (not inline with embedding). Phase 1 embed+store; Phase 2 (async) extract+memorability; Phase 3 (async) conflict scan."
**ARCHITECTURE Open Q1:** "Conflict scan on every store-normal write — or batched? Recommendation: per-write for v0.2 (Russell's volume is single-digit writes/day), revisit at v1.0."

**Resolution: Per-write via `ctx.waitUntil` in the existing `store-normal` branch. NOT a separate Queue stage in v0.2.**
- ARCHITECTURE Open Q1 already proposed and answered this. Single-user volume is single-digit writes/day; cost-of-Queue-orchestration > cost-of-`ctx.waitUntil`-in-existing-handler.
- PITFALLS CD-3 prevention is still honored: cosine prefilter + top-K=5 same-type + per-message bounded parallelism = the same operational shape that a multi-stage Queue would enforce, just without the orchestration tax.
- Revisit at v1.0 when multi-tenant volume justifies a `engram-conflicts` Queue (CLAUDE.md naming reserves the name).

### D-6: Conflict result destination — `inbox` table (STACK) vs `conflicts` table + `moveToInbox` (ARCHITECTURE)

**STACK §1 implementation:** `stub.moveToInbox(..., proposed_type: "conflict")`. Conflicts table left for v0.3.
**ARCHITECTURE §2 implementation:** New `insertConflict()` RPC writes to `conflicts` table; `moveToInbox()` separately surfaces in inbox.

**Resolution: STACK wins — write to `inbox` only.**
- ENG-16 verdict explicit: "low-confidence inbox suggestions; never auto-alerted."
- 12.5% false-positive rate (1 in 8) is too high to pollute the `conflicts` table — that surface is reserved for explicit user/Claude promotion via v0.3 `conflict()` MCP tool.
- ARCHITECTURE's `insertConflict` RPC moves to v0.3 alongside `conflict()` tool.
- Inbox table already supports the `proposed_type` extension; `proposed_properties` carries `{memory_a_id, memory_b_id, category, ai_confidence}` exactly as STACK §1 shows.

### D-7: Synthesis default — flip to `"both"` (ARCHITECTURE Open Q4) vs stay `"chunks"` (STACK + FEATURES + PITFALLS)

**ARCHITECTURE §4:** "v0.2 may flip the default to `'both'` once eval gates pass and the p50 latency budget is validated." Open question.
**STACK §3:** "Treat synthesis as opt-in. Default verbosity stays `chunks`."
**FEATURES Differentiator table:** "Synthesis is opt-in (verbosity=`chunks` default)" — calls out as a differentiator.
**PITFALLS SY-6:** "Synthesis is opt-in (D-01 already locked this). Default verbosity=chunks."

**Resolution: Default stays `"chunks"` for v0.2.** Flipping to `"both"` is a user-visible latency contract change (+2-5s on every recall) and demands dogfooding evidence. v0.2 ships the eval gate + LLM-judge; the default flip is a v0.3 discussion. ARCHITECTURE Open Q4 is closed: stay opt-in.

### D-8: Cross-encoder rerank placement — replace `cosine` in hybrid-rank (STACK) vs separate post-fusion step (ARCHITECTURE doesn't directly address)

**STACK §4 implementation:** Rename `HYBRID_WEIGHTS.cosine` → `HYBRID_WEIGHTS.rerank`; populate from bge-reranker output; semantically the same role.
**ARCHITECTURE §3 implementation note:** "the `score` field that flows downstream into hybridRank is the best cosine across the N queries... preserves the existing MIN_COSINE_THRESHOLD gate."

**Resolution: STACK's drop-in pattern.** The hybrid-rank formula stays mathematically identical — only the source of the `cosine`/`rerank` component changes. Keep a `match.score` fallback (raw Vectorize cosine) when the reranker is unavailable (test envs, 429s). This is the v0.1 `safeRun` defensive-coding discipline applied to a new model.

### Phase A — Recall Quality Baseline (Plans 02 + 03, parallel-trackable)

**Goal:** Stabilize the recall baseline and ship conflict detection. Two plans, can run in parallel because they touch different workers.

#### Plan 02 — Hybrid-rank weight tuning (Feature #1)

- **Files modified:** `packages/mcp-server/src/hybrid-rank.ts` (constants only; recency formula optional refinement).

#### Plan 03 — Conflict-detection wiring (Feature #2)

### Phase B — Query Expansion + Reranker (Plan 04)

**Goal:** Activate multi-query path with bge-reranker. The largest single user-facing latency change in v0.2.

- **Files modified:** `packages/mcp-server/src/tools.ts` `recall()` body (~50-line replacement of single-query block); `packages/mcp-server/src/hybrid-rank.ts` (rename `cosine` → `rerank` constant); `shared/ai-config/src/index.ts` (add `RERANKER_MODEL = "@cf/baai/bge-reranker-base"`).

- **Model:** Keep `QUERY_EXPANSION_MODEL = INGESTION_CLASSIFIER_MODEL` (Scout) as the default. A/B test 3.2-3b in the same eval (D-2 resolution); promote separately if it wins by ≥-5% recall@5.
- **Eval gates:** Recall@5 ≥ v0.1 baseline (no regression); precision@5 ≥ v0.1 + 3% (or skip reranker via weight); entity preservation ≥ 80% (PITFALLS QE-2); recall p50 < 1.8s with expansion ON (PITFALLS QE-5).
