## 2. Conflict Detection Wiring (Feature #2)

### Where it lands (file + function)

Two integration points, both in `triage-worker/`:

1. **Caller site:** `packages/triage-worker/src/index.ts` `queue()` handler, AFTER the `store-normal` / `inbox` enrichment branches (around line 242 / line 270). New conflict-detection step gated to fire ONLY on the `store-normal` branch (post-enrichment, when the block is now durable). Cold-storage and inbox blocks are NOT conflict-scanned.

2. **Candidate selection:** new helper `packages/triage-worker/src/conflict-pipeline.ts` that wraps `detectConflict()` (already shipped in `conflict-detection.ts`) with a candidate-selection step. The current `conflict-detection.ts` is leaf-level (two memories in, ConflictOutput out); the new file is the orchestration layer that picks WHICH pairs to compare.

### Candidate selection algorithm — what we need

`getCandidatesForConflict()` **does not yet exist** in `queries.ts`. The new DO RPC + helper required:

**New WorkspaceDO RPC:** `getCandidatesForConflict(args: { workspace_id, block_id, vector, topK?, sameTypeOnly? })` returning `Memory[]`.

**Implementation:**
- Query Vectorize for top-K (default K=5) neighbors of the new block's embedding, EXCLUDING the block itself by id.
- Apply cosine threshold ≥ 0.7 (TIGHTER than recall's MIN_COSINE_THRESHOLD = 0.6 — conflict detection on dissimilar memories wastes classifier tokens; only same-topic neighbors are conflict candidates).
- Optionally filter `block.type === candidate.type` (e.g., `job_application` only compares against other `job_application`s) — this is the "sameTypeOnly" prefilter that ENG-16 spec calls for. Default `true`.
- Hydrate via `getBlocksByIds()` (existing AI-04 helper).
- Return.

The RPC body should be a new function in `queries.ts` + a method on `WorkspaceDO`. It is NOT pure SQL — it calls into Vectorize. This means:

- **Option A:** WorkspaceDO RPC takes the candidate IDs already chosen by the Worker (triage-worker did the Vectorize query itself), and the DO just hydrates. Simpler; keeps the DO pure-SQLite.
- **Option B:** WorkspaceDO RPC does both the Vectorize query AND the hydrate. Cleaner caller code; couples the DO to Vectorize.

**Recommendation: Option A.** Triage-worker already has `env.VECTORIZE` declared (see `triage-worker/src/index.ts:56`). Keep the DO's responsibility to SQL only — it's the v0.1 design invariant. The new triage-side helper does Vectorize query + then hydrates via the existing `getBlocksByIds` RPC.

### Data flow change

**Current (v0.1):**

```
Queue message → extractAndScore() → routeByMemorability()
  → switch(decision):
    case "store-normal": updateBlockEnrichment(...)
    case "inbox":        moveToInbox(...)
    case "cold-storage": moveToColdStorage(...)
  → message.ack()
```

**With v0.2 conflict detection:**

```
Queue message → extractAndScore() → routeByMemorability()
  → switch(decision):
    case "store-normal": updateBlockEnrichment(...)
                         ↓ (only this branch — NEW)
                         scanConflicts(block_id):
                           vectorizeQuery topK=5 ≥ 0.7
                           getBlocksByIds(neighbors)
                           for each neighbor (parallel up to N=3):
                             detectConflict(content, neighbor.content)
                             if is_conflict + confidence ≥ 0.7:
                               insertConflict({memory_a_id, memory_b_id,
                                              description, severity})
                               moveToInbox(neighbor)  // surfaces as suggestion
    case "inbox":        moveToInbox(...)        // no conflict scan
    case "cold-storage": moveToColdStorage(...)  // no conflict scan
  → message.ack()
```

### What's new and what's reused

- **NEW WorkspaceDO RPC:** `insertConflict(args: { workspace_id, conflict: { id, memory_a_id, memory_b_id, description, severity } })` writing into the existing `conflicts` table (schema already exists per CLAUDE.md SQLite schema). The table even already has `narrowConflictRow` and `listConflicts` helpers — only the write helper is missing.
- **NEW helper:** `packages/triage-worker/src/conflict-pipeline.ts` exposing `scanConflicts(env, workspaceId, blockId, content, vector)` — wraps Vectorize candidate query + hydrate + `detectConflict()` loop + DO `insertConflict()` writes.
- **REUSED:** `detectConflict()` (already shipped, byte-frozen prompt), `getBlocksByIds()` DO RPC (AI-04), `moveToInbox()` DO RPC (AI-06 — repurposed for "low-confidence conflict suggestion" surface per ENG-16 verdict).

### Build-order note: ENG-16 precision gate

ENG-16 requires `detectConflict` to pass a 50-sample precision validation BEFORE wiring it into the production flow. The eval already exists (`__tests__/evals/conflict-precision.eval.test.ts`). The wiring (this section) lands only AFTER the precision number is in — current Active list in PROJECT.md explicitly notes "validated via 50-sample precision gate first — ENG-16".

### Latency budget impact

**+1-3s per ingest enrichment, store-normal branch only.**

Breakdown per ingest message (store-normal):
- Vectorize query for candidates: ~50-100ms
- `getBlocksByIds()` DO RPC: ~10-30ms
- `detectConflict()` AI call: ~700-1500ms per pair (llama-4-scout) × up to 3 pairs in parallel = ~700-1500ms (parallel) or 2.1-4.5s serial
- `insertConflict()` + `moveToInbox()` DO RPCs (only on hit): ~10-30ms

**Total p50 budget: ~1.5s, p95: ~3s.** Acceptable in the Triage Worker because Triage is async-after-response: `remember()` already returned to Claude in ~430ms before Triage even started. Triage's whole budget is whatever the Queue runtime tolerates — minutes is fine.

**Mitigation if it blows:** parallelize the detectConflict calls (Promise.all) bounded at N=3 concurrent — but watch the 429 risk per RESEARCH §"Async-First Design" Pitfall 1 (current triage-worker explicitly avoids `Promise.all` for batches; one-classifier-call-at-a-time inside ONE message is much safer than parallel-across-messages).

### Build dependencies

- **Inbound (required before this):** ENG-16 precision validation (50-sample eval ≥ baseline) — already in plan per PROJECT.md.
- **Outbound (this unblocks):** future "active conflict scan" in `conflict()` MCP tool (v0.3). Also positions the data for v0.4's "Slack proactive conflict alerting" killer demo.

## 3. Query Expansion (Feature #3)

### Where it lands (file + function)

`packages/mcp-server/src/tools.ts` `recall()` handler. Slots in BETWEEN `queryWasTruncated` check (line 512) and the embed call (line 524).

### Data flow change

**Current single-query recall:**

```
recall(query) →
  embed(query) → 1 vector
  vectorizeQuery(vector, topK=fetchSize) → matches
  filter ≥ MIN_COSINE_THRESHOLD → slice topK
  getBlocksByIds → hybridRank → response
```

**With query expansion (N=3 default):**

```
recall(query) →
  expandQuery(query) → [query, variant_a, variant_b]  ← NEW CF AI call
  Promise.all([
    embed(query)     → vector_0,
    embed(variant_a) → vector_a,
    embed(variant_b) → vector_b
  ])  → 3 vectors  (3 parallel safeRun calls — well under 429 threshold for one user)
  Promise.all([
    vectorizeQuery(vector_0, topK=fetchSize) → matches_0,
    vectorizeQuery(vector_a, topK=fetchSize) → matches_a,
    vectorizeQuery(vector_b, topK=fetchSize) → matches_b
  ])
  RRF-merge(matches_0, matches_a, matches_b) → fused matches  ← NEW step
  filter ≥ MIN_COSINE_THRESHOLD-equivalent (see note) → slice topK
  getBlocksByIds → hybridRank → response
```

### Reciprocal Rank Fusion — does it replace `hybridRank`?

**No. RRF chains BEFORE hybridRank, not instead of it.** They serve different roles:

| Step      | Purpose                          | Operates on                       |
| --------- | -------------------------------- | --------------------------------- |
| RRF       | Fuse N ranked lists into ONE     | Per-list rank position only       |
| hybridRank| Re-rank ONE list by multi-signal | Cosine + recency + type + scope   |

**RRF formula (standard, k=60):** `rrf_score(doc) = Σ (1 / (k + rank_in_list_i))`

Implementation outline (new file `packages/mcp-server/src/rrf.ts`):

```typescript
export function rrfMerge(
  matchLists: VectorizeMatches["matches"][],
  k = 60,
): VectorizeMatches["matches"] {
  const fused = new Map<string, { id: string; score: number; rrf: number }>();
  for (const list of matchLists) {
    list.forEach((m, idx) => {
      const existing = fused.get(m.id);
      const contribution = 1 / (k + idx + 1);  // ranks are 1-indexed
      if (existing) {
        existing.rrf += contribution;
        existing.score = Math.max(existing.score, m.score);  // preserve best cosine
      } else {
        fused.set(m.id, { id: m.id, score: m.score, rrf: contribution });
      }
    });
  }
  return [...fused.values()]
    .sort((a, b) => b.rrf - a.rrf)
    .map(({ id, score }) => ({ id, score }));  // strip rrf, keep cosine for downstream
}
```

The `score` field that flows downstream into hybridRank is the **best cosine across the N queries** for that doc id. This preserves the existing MIN_COSINE_THRESHOLD gate semantics — a doc that was highly relevant under ANY variant keeps its strongest cosine signal for the threshold gate.

### Interaction with over-fetch + threshold

The interaction needs explicit thought:

- **Over-fetch (`fetchSize = topK * VECTORIZE_OVERFETCH_FACTOR`):** stays per-query. Each of the N Vectorize calls fetches `fetchSize` matches. Total max docs entering RRF = N · fetchSize, with extensive overlap (a relevant doc shows up in multiple variants).
- **Threshold gate:** moves AFTER RRF. RRF needs the raw rank-positions; gating before RRF would shrink some lists more than others and skew the fusion (the highest-quality variant disproportionately influences the merge).
- **topK slice:** stays AFTER threshold gate. Result: `N·fetchSize → RRF (still all unique ids) → filter ≥ MIN_COSINE_THRESHOLD → slice topK`.

Effective fetch volume per recall: ~6× more Vectorize work (3 queries × overfetch=2 vs current 1 query × overfetch=2). This is OK — Vectorize is cheap (single-digit ms per query at this scale).

### New vs modified components

- **NEW file:** `packages/mcp-server/src/rrf.ts` (pure transform; mirrors `hybrid-rank.ts` shape).
- **NEW file:** `packages/mcp-server/src/query-expansion.ts` (one exported function `expandQuery(env, query): Promise<string[]>` returning `[query, ...variants]`; wraps `safeRun(env, QUERY_EXPANSION_MODEL, ...)` with a bounded prompt).
- **NEW prompt constant:** `QUERY_EXPANSION_PROMPT` in `query-expansion.ts` (becomes byte-frozen after eval baseline lands, same pattern as `SYSTEM_PROMPT` in triage-worker).
- **NEW Zod schema:** `QueryExpansionOutput` (small — `{ variants: string[] }` with cap of 3 variants) + `QUERY_EXPANSION_JSON_SCHEMA` derived via `z.toJSONSchema()` + sanitized. Same pattern as `TRIAGE_JSON_SCHEMA` and `CONFLICT_JSON_SCHEMA`.
- **MODIFIED:** `tools.ts` `recall()` body — replace the single `safeRun → vectorizeQuery → filter → slice` block with the expand → Promise.all(embed) → Promise.all(vectorizeQuery) → rrfMerge → filter → slice block. Roughly 50-line diff inside the handler.
- **MODIFIED:** `@engram/ai-config` already aliases `QUERY_EXPANSION_MODEL = INGESTION_CLASSIFIER_MODEL` — when the v0.2 spike data justifies, this constant can specialize independently (e.g., to a smaller/faster model like `@cf/meta/llama-3.1-8b-instruct` if it's still in catalog, or kept on Scout if quality matters more than 200ms savings).

### Latency budget impact

**Adds ~600-900ms p50 to recall() — significant.**

Breakdown (incremental over current recall):

- 3× parallel embed: ~150-250ms (one embed = ~50-100ms; parallel collapses to slowest)

   - eval passes
   - 80%+ of real recall traces would benefit (some don't need synthesis — single-result lookups)

4. **Prompt tuning loop:** after the eval establishes the baseline number, prompt iteration becomes legitimate. Until then the prompt is byte-frozen per spike contract.

### Does synthesis run inside `recall()` or get streamed?

**Inside the handler. Cannot be streamed via MCP tool response.**

MCP tool calls return a single `CallToolResult` object — the protocol does not support streaming tool output (only the OVERALL HTTP connection can be SSE for the protocol-level message multiplexing, not for content streaming WITHIN a single tool result). Workers AI itself supports streaming via `stream: true`, but that returns a `ReadableStream` to the handler — the handler cannot pipe that out as a tool result; it must drain it into a final string.

Practical consequence:
- Synthesis must complete BEFORE `recall()` returns
- This is what the current code does (`safeRun(...)` without `stream`, then `synthResp.response` is the final string)
- The 2-5s p50 latency is the user-visible cost on every synthesis recall
- Users see the spinner for the full duration

**Alternative (deferred to v0.3 / future):** add a `synthesizeAsync` tool that takes a `recall_id` and returns synthesis later — the recall returns chunks immediately + an ID, Claude can opt-in to the synthesis tool call separately. This is a v1.0 pattern when latency complaints surface; not needed for v0.2 (we have hard data the prompt produces useful output).

### New vs modified components

- **NEW:** `synthesis-fidelity.eval.test.ts` + a labeled corpus.
- **MODIFIED (maybe):** `schemas.ts` default value flip for `verbosity` (one line, gated on eval).
- **MODIFIED (maybe):** `@engram/ai-config` `SYNTHESIS_MODEL` constant if the model specializes.

### Latency budget impact

**+2-5s p50 on `verbosity: "synthesis"` / `"both"` recalls. Zero impact on `verbosity: "chunks"`** (current default).

If v0.2 flips the default to `"both"`, every recall gets the latency hit. This is the single largest UX decision in v0.2 and demands explicit Russell sign-off before flipping.

- **Inbound:** #1 (recall ranking baseline must be stable so synthesis isn't summarizing low-quality matches) and #3 (multi-query coverage gives synthesis better material to work with). Specifically: if #3 isn't shipped first, synthesis may produce confident-sounding answers that miss memories a query variant would have found.
- **Outbound:** future `reflect()` MCP tool (v0.3) — synthesis prompt is the template `reflect()` extends with multi-topic aggregation.

- synthesis: ~3-7s — slow but justified; opt-in
- both: same as synthesis

**Acceptable.** Major risk is if Russell flips the verbosity default to `"both"` (#4 question): every recall becomes a 3-7s operation. Recommend keeping default at `"chunks"` and surfacing synthesis as opt-in via the existing `suggestions.actions` field — already wired.

```
       #1 Hybrid-rank tuning  (mcp-server, pure tuning)
              │

              │           │
              └──────┬────┘
                     ↓
       #4 Synthesis activation (mcp-server, eval + tuning + default flip)
```

- **#1 first** — stabilizes recall quality baseline.
- **#2 in parallel** — different worker, different file, no shared touchpoints with the recall path.
- **#3 after #1** — query expansion's RRF output flows into the (now-tuned) hybridRank.
- **#4 last** — synthesis quality depends on having a stable recall (#1) AND broader recall coverage (#3) to summarize over.

Phasing recommendation for the roadmapper: ship **#1 + #2 in Phase A**, **#3 in Phase B**, **#4 in Phase C**. Three phases, ~5 plans total.

## Open Architectural Questions (flag for roadmap)

1. **Conflict scan on every `store-normal` write — or batched?** Current proposal scans inline (per-write). At v1.0 with N writes/sec, this may saturate Workers AI quota. Batched nightly scan is an alternative that pushes the latency cost to a Cron Worker. **Recommendation:** per-write for v0.2 (Russell's volume is single-digit writes/day), revisit at v1.0.

2. **Query expansion: opt-out parameter or KV-flag?** Adding `expand: boolean` to RecallInputSchema is a public contract surface (extra schema field forever). KV flag is per-deployment, hidden from MCP clients. **Recommendation:** KV flag for v0.2 (we can ship + measure + opt-out without schema churn); add `expand:` schema param in v0.3 IF clients want per-call control.

3. **RRF k value: 60 (standard) or tuned?** k=60 is the Cormack 2009 empirical sweetspot used by Elasticsearch, Azure Cognitive Search, AI21. For our N=3 fusion with high overlap (variants of the same query), k=60 likely works. **Recommendation:** ship with k=60; add to the v0.2 ranking eval to measure if k=40 or k=100 improves precision-at-K against our corpus.

4. **Synthesis verbosity default flip — when and how?** Discussed above. **Recommendation:** stay on `"chunks"` default for v0.2; revisit at v0.3 when more eval data is available.

5. **Cross-Worker DO method type unsafety in triage-worker.** The new `insertConflict` call from triage-worker will use the same `(stub as any).methodName(...)` cast pattern as the existing `updateBlockEnrichment` / `moveToInbox` / `moveToColdStorage` / `markIngestFailed` calls (see `triage-worker/src/index.ts:224-241`). This is documented tech debt — Plan 05-07's note about a shared `@engram/workspace-do` type re-export to recover type safety should be picked up as a small v0.2 cleanup task (one PR, low risk).
