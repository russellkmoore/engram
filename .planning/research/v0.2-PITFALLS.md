## How To Read This File

Each pitfall has:

- **Feature** — which of the four v0.2 features it attacks (Query Expansion / Synthesis / Conflict Surfacing / Hybrid-Rank Tuning / Integration)
- **Severity** — `catastrophic` (silent quality regression that erodes Russell's trust in his own tool), `serious` (production incident or visible UX harm), `annoying` (paper cut, but fixable)
- **Failure mode** — what specifically goes wrong, observed in production RAG systems
- **Warning signs** — concrete observables: metric, log line, user complaint
- **Prevention** — actionable design choice or test, never "be careful"
- **Phase placement** — recommended phase/plan ordering hint for the roadmapper

The **v0.2 MUST-MITIGATE LIST** at the bottom is the short list of items that v0.2 cannot ship without addressing. The v0.1 PITFALLS.md remains in force; this file is the **delta** for the four new intelligence-layer features and the integration pitfalls they introduce.

## 1. Query Expansion Pitfalls

CF AI rewrites each `recall()` query into 3-4 semantic variants before Vectorize. Variants are embedded independently and results are merged + deduplicated. This is a classic RAG-Fusion shape, and RAG-Fusion's well-documented failure modes apply.

### QE-1: Cost runaway — Vectorize bill scales linearly with variant count

- **Severity:** serious
- **Phase:** the expansion-implementation plan (recommended early in v0.2)
- **Failure mode:** Vectorize billing is `(vectors_in_index + queries_in_period) × dimensions`. Engram switched to `qwen3-embedding-0.6b` at **1024d** during ENG-25 (was 768d in original v0.2 PROJECT.md target). 4 variants × 1024 dimensions × current vector count × queries/day. For Russell's personal workspace at ~500 blocks × 5 chunks/block × 1024d, a 4-variant query is 10.24M queried dimensions per call. Multiply by Job Scout agent calling 50× per day = 512M dims/day per workspace. Multi-tenant managed offering at v1.0 makes this the single biggest cost line. Reported in production [Cloudflare Workers + Vectorize stack analysis](https://markaicode.com/stack/cloudflare-workers-openai-stack/): "one production traffic spike can bankrupt your latency budget" — Vectorize cost has the same shape.
- **Warning signs:** Vectorize line item exceeding 30% of monthly Cloudflare bill; per-`recall()` cost climbing without recall-quality improvement.
- **Prevention:** (1) Cap variants at **3** (one rephrase + one HyDE + one keyword extraction) — not 4. (2) **Conditional expansion** — only fan out if the no-expansion path returns `<5` results above `MIN_COSINE_THRESHOLD=0.6`. Skip the AI call entirely on dense workspaces. (3) Cache `query_text → [variants]` for 60s in `recall()` handler memory (cheap; identical queries within a session reuse). (4) Deduplicate at the candidate-vector level before scoring (matches by `id` collapse to one entry with `max(score)`). (5) Track `queried_dimensions_per_recall` in Workers Analytics Engine from day 1 of the plan.
- **Detection:** Add an Analytics Engine alarm at "vectorize_dim_per_recall p99 > 5M" and a CI assert in the expansion-handler unit test: `expect(variantCount).toBeLessThanOrEqual(3)`.

### QE-2: Recall drift — variants pull semantically related but topically wrong content

- **Severity:** catastrophic for trust
- **Phase:** same plan as QE-1
- **Failure mode:** LLM rewrites can change query meaning. The canonical example from RAG-Fusion practice: "how do I cancel my subscription?" → variants `["unsubscribe options", "billing changes", "account cancellation steps"]` is fine; "how do I deploy?" → variants `["deployment guide", "CI/CD pipeline setup", "production launch"]` drifts into adjacent topics. For Engram specifically: "what did I learn about Stripe?" might fan out to `["payment processing notes", "fintech infrastructure", "billing system design"]` — pulling in unrelated research_notes about Square, Adyen, etc. [Documented in Hacker News RAG postmortem thread](https://news.ycombinator.com/item?id=44746089): "rewrites occasionally changed the meaning... casual questions produced formal queries that retrieved the wrong documents."
- **Warning signs:** Russell reports "Engram gave me notes about X when I asked about Y." Promptfoo eval bucket "specific-entity recall" precision drops below v0.1 baseline.
- **Prevention:** (1) **Similarity gate on variants** — compute cosine(embed(original), embed(variant)) and **drop variants below 0.85** (the threshold from the HN postmortem). Workers AI embedding call is cheap relative to the Vectorize query it saves. (2) Always include the original query in the variant set (never drop it). Original is the floor. (3) System prompt for the rewriter must include: *"preserve named entities exactly. If the query mentions 'Stripe', every variant must mention 'Stripe'."* Entity preservation is the failure mode that hurts most for personal-memory RAG. (4) Promptfoo eval bucket: 10 entity-bearing queries (proper nouns), assert variant set contains the entity in ≥80% of generated variants.
- **Detection:** Eval set with deliberately entity-bearing queries; track entity-preservation rate as a CI gate.

### QE-3: HyDE failure mode — hypothetical document is itself wrong, biases retrieval

- **Severity:** serious
- **Phase:** the expansion plan (HyDE is one of the variant generators)
- **Failure mode:** HyDE asks the LLM to draft a hypothetical answer document, then embeds that. When the LLM's hypothetical contains hallucinated facts ("Stripe was founded in 2005" — wrong, it was 2010), the embedding pulls in documents containing similar wrong patterns. [Documented in HyDE failure-mode literature](https://medium.com/@nirdiamant21/hyde-exploring-hypothetical-document-embeddings-for-ai-retrieval-cc5e5ac085a6): "if the LLM's answer drifts off-topic or includes a fictional scenario, the vector might pull in documents related to those hallucinated details." Worse for personal memory than for generic Q&A — Russell's memories are specific, and a generic hallucinated document's embedding is closer to other generic stuff than to Russell's specific notes.
- **Warning signs:** Variants from the HyDE generator have lower variant-similarity scores (QE-2) than rephrase variants. HyDE-only queries retrieve memories Russell didn't write.
- **Prevention:** (1) **Constrain HyDE to short, factual hypotheticals** — prompt: *"Write 1-2 sentences as if you knew the answer. Do not invent specific dates, numbers, or names not present in the query."* (2) Embed HyDE output with the **same model** as the corpus (`qwen3-embedding-0.6b`), not a different model. (3) Track per-variant-source recall quality — if HyDE-sourced matches consistently have lower cosine scores than rephrase-sourced matches in the merged top-K, drop HyDE entirely. (4) Defer HyDE to a Phase 2 of v0.2 if rephrase + keyword-extraction variants alone hit recall quality targets; HyDE is the highest-risk variant generator.
- **Detection:** Eval harness tags each result by which variant retrieved it; track "HyDE-only hits" precision.

### QE-4: Recency-bias compounding — all variants embed similar content, recency weight overwhelms

- **Severity:** annoying → serious for long-term users
- **Phase:** the expansion plan + the hybrid-rank tuning plan (interaction effect)
- **Failure mode:** When 3 variants all embed close to the same point in vector space, they all return the same top-K with similar cosine scores. The hybrid-rank formula `cosine·1.0 + recency·0.15 + type_match·0.2 + scope_match·0.15` then becomes effectively `recency·0.15` as the tiebreaker — because cosine is constant across all candidates. **The recency weight tail-wags-the-dog**. Russell asks "what did I learn about TypeScript last year?" and the top result is yesterday's note about TypeScript because cosine is tied and recency dominates the tiebreaker.
- **Warning signs:** `recall()` results dominated by last-7-days content regardless of query temporality. Russell reports "Engram only remembers recent stuff."
- **Prevention:** (1) **Diversity-aware merge** — when N variants return the same vector ID, increase that ID's `cosine_score` to `max(scores) + 0.05·log(N)` (boost matches multiple variants find). This rewards consensus across variants, breaking the tiebreaker before recency activates. (2) Recency weight should be relative, not absolute — for queries containing temporal markers ("last year", "in 2024"), zero out the recency weight. (3) Test bucket: 5 queries with temporal markers, assert top-3 results respect the temporal constraint (no `created_at` outside the bucket).
- **Detection:** Recall fixture queries with explicit temporal markers; assert temporal constraint honored.

### QE-5: Latency stacking — 4 AI calls + 4 Vectorize queries serialized

- **Severity:** serious
- **Phase:** the expansion plan (latency budget belongs here)
- **Failure mode:** Naive implementation: `await expand(q)` → for each variant `await embed(v)` → for each embedding `await vectorize.query(e)`. Sequential. Pre-expansion v0.1 `recall()` p50 is ~150-400ms (per AI-SPEC.md §4b). Add 1 expansion call (~300ms) + 4 sequential embed calls (~150ms × 4 = 600ms) + 4 sequential Vectorize queries (~80ms × 4 = 320ms) = **+1220ms tax**, p50 climbs to ~1.6-1.8s. Then if `verbosity=synthesis` the synthesis call (2-5s) stacks. User waits 4-7 seconds for `recall(verbosity=synthesis)`.
- **Warning signs:** `recall()` p50 climbs above 1s after expansion ships. Russell reports "recall is slow now."
- **Prevention:** (1) **Parallelize variant embedding + querying** with `Promise.all()`. Workers AI and Vectorize bindings are independent; sequential is purely lost time. Expected parallel p50 = max(embed, vectorize) per variant ≈ 230ms total. (2) **Race the original query against expansion** — start the original-query embed + Vectorize query immediately; in parallel, run the expand AI call → if expansion returns within 400ms AND original results are <5, fire the variant queries; if expansion is slow OR original returned plenty, skip variants and return original. (3) Budget assertion in tests: `expect(p50).toBeLessThan(800)` for expanded path, `<400` for non-expanded.
- **Detection:** Integration test with synthetic load, assert latency budget.

### QE-6: Over-recall — variants return too many vaguely-related memories, noise drowns signal

- **Severity:** serious for UX
- **Phase:** the expansion plan
- **Failure mode:** 3-4 variants × top-K=25 each = 75-100 candidate vectors before dedup. After dedup typically 30-60. Hybrid-rank produces a long tail of medium-quality matches. The envelope's `result.memories[]` (Phase 4 D-10 cap = 25) shows the top, but the cap was calibrated for single-query recall, not expanded. The chunks now include semantically-adjacent-but-not-asked-for content. Russell sees "25 results, half are noise" — perceived precision drops.
- **Warning signs:** User dismisses bottom 10 results in every recall; promptfoo precision@10 drops vs. v0.1 baseline.
- **Prevention:** (1) **Hard cosine threshold AFTER merge** — drop any merged candidate below `MIN_COSINE_THRESHOLD=0.6` (already a constant per STATE.md decision 4). The threshold is the noise floor; tighten to 0.65 for expanded path if needed. (2) **Adaptive limit** — return `min(25, results_above_threshold)`; don't pad with garbage to hit 25. (3) Surface in `meta.coverage`: if expansion ran AND returned fewer high-confidence results than non-expansion alone would have, set `coverage` lower and add `meta.gaps`: `"Query expansion attempted but found no additional high-confidence matches."`
- **Detection:** Eval bucket: queries that should have 3 results return 3 (not padded to 25 with noise).

### QE-7: Expansion AI call failure (429 or hallucinated empty rewrites) → silent fallback or empty results

- **Severity:** serious
- **Phase:** the expansion plan + the 429-aware retry from v0.1 Phase 5
- **Failure mode:** Two sub-modes: (a) The expansion model is rate-limited (429). Naive code throws or returns empty variants; recall() then queries with `[]` variants and returns nothing. (b) Model returns malformed JSON or empty array. Same outcome: zero results despite stored memories.
- **Warning signs:** `recall()` returning zero results for queries that v0.1 served fine; Workers AI 429 rate climbing.
- **Prevention:** (1) **Always include the original query as variant[0]** — even if expansion fails, original is the floor and returns the v0.1-equivalent result set. (2) Reuse v0.1's `detectRateLimit()` + `RateLimitError` from `ai-helper.ts` (already shipped per ENG-25). On 429: skip expansion, run original-only, log `expansion_skipped: rate_limited` to Analytics Engine. (3) Zod-validate the expansion model's output; on parse failure, log + fall back to original-only. **Never** allow the expanded recall path to return strictly fewer results than the non-expanded path would have.
- **Detection:** Test: stub expansion AI to return `[]`, assert `recall()` still returns original-query results.

## 2. Synthesis Path Pitfalls

`recall(verbosity=synthesis|both)` summarizes N retrieved memories into a coherent narrative. Activates a code path that's stubbed in v0.1 (synthesis = null when verbosity=chunks per D-01). The LLM here is `@cf/meta/llama-4-scout-17b-16e-instruct` (per ENG-25 decision).

### SY-1: Hallucination — synthesis invents facts not present in retrieved memories

- **Severity:** catastrophic for trust
- **Phase:** the synthesis-activation plan
- **Failure mode:** The most-documented RAG synthesis failure. LLM "fills in gaps" — "John Smith at Acme" becomes "John Smith, CTO at Acme since 2020" because the model assumed plausible context. For Engram: synthesis summarizing 5 job_application memories may invent a salary range, a contact name, a deadline. Russell trusts the synthesis (it's stored in `result.synthesis`, not a chunk), makes a decision on it. [FACTUM research on citation hallucination](https://arxiv.org/pdf/2601.05866) calls this "a deceptive failure where a model cites a source that fails to support its claim."
- **Warning signs:** Russell reports "Engram told me Stripe pays $X but I don't see that in my memories." Synthesis contains specific numbers/dates/titles not in the input chunks.
- **Prevention:** (1) **Grounding prompt** — `"Summarize ONLY using facts from the memories below. If a claim is not explicitly stated, do not include it. Prefer quotation over paraphrase for entities and numbers."` Temperature `0.2` (low). (2) **Post-synthesis grounding check** — extract entities/numbers from the synthesis with a regex-NER pass; assert each appears in at least one input chunk (string match). On miss, drop the synthesis and return `synthesis: null` with `meta.gaps: ["Synthesis suppressed: contained ungrounded facts."]`. (3) **Citation linkage** — synthesis includes `[memory_id]` markers; envelope post-processor verifies every marker references a `result.memories[].id`. Unverified citation → drop synthesis. (4) Promptfoo eval bucket: 10 multi-memory synthesis queries with known ground truth; assert no novel entities in synthesis output.
- **Detection:** Promptfoo ground-truth eval, manual spot-check 20 synthesis outputs/week (Russell's own usage).

### SY-2: Missing-citation problem — claim with no traceable source

- **Severity:** serious for trust
- **Phase:** synthesis-activation plan
- **Failure mode:** Synthesis says "you applied to 5 fintech startups" but no `[memory_id]` markers. Russell can't trace the claim. Even if true, untraceable claims accumulate suspicion. [Cited in citation-generation literature](https://arxiv.org/pdf/2410.11217): "models may fabricate citations, reference non-existent code locations, or conflate memorized patterns with retrieved content."
- **Warning signs:** Russell asks "where does it say that?" and Engram can't show. Synthesis paragraphs without `[id]` markers.
- **Prevention:** (1) Prompt requires inline `[id]` markers after every factual claim (model card for llama-4-scout supports this; verify with a 5-shot example in the prompt). (2) Post-process: strip any sentence that doesn't contain at least one `[id]` marker. If post-processing drops >50% of synthesis, return `synthesis: null`. (3) Surface citations in the envelope: `result.synthesis_citations: [{ claim_index, memory_ids[] }]`. This makes citation accuracy testable.
- **Detection:** Synthesis with citation density per 100 chars; alert if avg drops below 1 citation per 80 chars.

### SY-3: Token budget overrun — retrieved content + prompt > model context window

- **Severity:** serious (silent truncation, degraded quality)
- **Phase:** synthesis-activation plan
- **Failure mode:** llama-4-scout has 128K context but Cloudflare's binding may impose a smaller practical limit. AI-SPEC.md sets the cap at ~6K tokens per AI-SPEC §"Context Window Strategy". 25 memories × 800 chars summary × 4 chars/token = 5000 tokens. Plus prompt overhead (500 tokens). Plus original query and instructions. Tip-toes the cap. If memories have long content (job postings ~2000 chars each), 5 memories blow 6K. Model silently truncates input — the tail memories are dropped — and synthesis only summarizes the first half.
- **Warning signs:** Synthesis omits content from memories ranked 5-25; large recalls produce shorter/lower-quality synthesis than small recalls.
- **Prevention:** (1) **Pre-flight token count** — use `gpt-tokenizer` (already a v0.1 dep per Phase 4 D-09) to count input tokens before the AI call. If > 5500, **drop trailing memories** (lowest hybrid-rank scores first) until under budget. Append `meta.gaps: "Synthesis input truncated to top N memories due to context budget."`. (2) Prefer `summary` (≤800 chars per Triage Worker contract) over `content` (full text) for input — already a 5-10x compression. Only fall back to `content` for the top-3 if summary is empty. (3) Cap synthesis at 1024 max_tokens output (already in AI-SPEC.md pattern). (4) Reserve 1000 tokens for prompt overhead + output; available for retrieved content is ~5000.
- **Detection:** Pre-flight count vs cap; assert truncation logged when triggered.

### SY-4: False confidence — synthesized output sounds authoritative regardless of input quality

- **Severity:** serious
- **Phase:** synthesis-activation plan
- **Failure mode:** Even when input chunks are low-confidence matches (cosine 0.6-0.7), synthesis produces a confidently-worded summary. The wording masks the underlying uncertainty. Russell reads the summary, doesn't check the cosine scores in `result.memories`, acts on the synthesis. Worse: synthesis of a single low-quality chunk produces a longer, more authoritative-sounding text than a single high-quality chunk's raw content.
- **Warning signs:** Russell quoting synthesis content that turned out to be wrong; user feedback on "synthesis lied to me."
- **Prevention:** (1) **Cosine-aware framing** — if `min(cosine_scores)` < 0.7, prepend synthesis with: *"Low confidence — the memories matched only loosely:"* (frozen META_GAPS-style string). Visible to Claude in `result.synthesis`. (2) `meta.confidence` (Phase 4 envelope field) is `min(cosine_scores) × HYBRID_WEIGHTS.cosine`. Surface this to Claude. (3) Synthesis prompt: *"If the memories don't cover a part of the query, explicitly say 'I don't have memories about X' rather than inventing."* Reward acknowledged gaps. (4) Test: synthesis input of 1 cosine-0.6 match → assert output contains hedging language.
- **Detection:** Manual review correlation: synthesis-with-hedging-language vs. cosine-min-score.

### SY-5: "Summary" that's actually the first memory verbatim

- **Severity:** annoying (UX cheat)
- **Phase:** synthesis-activation plan
- **Failure mode:** When asked to summarize 1 memory, llama-4-scout often returns the memory's content nearly verbatim. When asked to summarize N memories, it sometimes returns memory[0]'s content with `+memory[1].summary` appended. Not really synthesis — just concatenation with tokenizer overhead. Users get less value than v0.1's `verbosity=chunks` already gives.
- **Warning signs:** Synthesis text contains 50+ char substrings matching memory[0].content exactly; synthesis length tracks input memory count linearly (true synthesis is sub-linear).
- **Prevention:** (1) Synthesis prompt explicitly: *"DO NOT copy memory text verbatim. Paraphrase. Identify themes across memories."* (2) Post-process: if synthesis contains a >100-char substring of any input chunk, regenerate once with stronger prompt. If still verbatim, return `synthesis: null` with `meta.gaps: "Synthesis collapsed to verbatim chunks; verbosity: 'chunks' has the same content."`. (3) Always reject single-memory synthesis — if `result.memories.length === 1`, force `synthesis: null` regardless of verbosity arg. Single-memory summary adds no value over the chunk itself.
- **Detection:** Substring-match detector in test fixture.

### SY-6: Latency budget — synthesis adds 2-5s, blows interactive UX

- **Severity:** serious
- **Phase:** synthesis-activation plan
- **Failure mode:** AI-SPEC.md §4b budgets `recall(verbosity=synthesis)` at 2-5s p50. With query expansion (+1.2s from QE-5), total climbs to 3-7s. Russell uses recall interactively in Claude Desktop; >3s feels broken. Worse: if synthesis is cold-start (model not warm), p99 spikes to 10-15s, MCP-1 25K-token-cap timeout windows shrink.
- **Warning signs:** `recall(verbosity=synthesis)` p50 >3s, p99 >8s.
- **Prevention:** (1) **Synthesis is opt-in** (D-01 already locked this). Default `verbosity=chunks` (~400ms p50); synthesis is explicit. Document the cost in the tool description (D-02 already covers). (2) **Streaming synthesis** if Workers AI binding supports SSE — Claude can start reading the synthesis before it finishes. (Verify llama-4-scout streaming support before promising this.) (3) **Skip synthesis if `result.memories.length === 0`** — no input, no synthesis, return immediately. (4) Track synthesis p50/p99 in Analytics Engine; alarm at p50 > 4s.
- **Detection:** Analytics Engine dashboard.

### SY-7: Synthesis drift across model versions — Cloudflare rotates `llama-4-scout` weights silently

- **Severity:** serious
- **Phase:** synthesis-activation plan + production monitoring plan
- **Failure mode:** Like v0.1's AI-3 (model drift breaks summary quality silently) but worse — synthesis is the user-facing output. Model rotation changes tone, length, hedging behavior. Old synthesis outputs are inconsistent with new ones; conflict detection between "previously summarized" claims gets noisier.
- **Warning signs:** User reports "summaries look different than they used to"; promptfoo eval baseline drift week-over-week.
- **Prevention:** (1) **Pin model name + version** if Cloudflare provides versioned aliases (verify). Otherwise log the `model` from binding response on every synthesis call. (2) **Frozen prompt** — never edit the synthesis system prompt without running promptfoo eval baseline; prompt changes should bump a `SYNTHESIS_PROMPT_VERSION` constant. (3) Monthly: 20 representative input fixtures → run synthesis → diff against locked baseline outputs. Alert on >30% character-level diff. (4) Promptfoo CI gate already runs on PR; this catches at-PR drift.
- **Detection:** Monthly drift snapshot; promptfoo CI.

## 3. Conflict Surfacing Pitfalls

ENG-16's `detectConflict()` shipped with `P=0.875 R=0.933` on a 30-pair eval. v0.2 wires it live as low-confidence inbox suggestions (never auto-alerted per STATE.md decision 5).

### CD-1: False-positive trust erosion — every notification fatigues the user

- **Severity:** catastrophic for adoption
- **Phase:** the conflict-wiring plan
- **Failure mode:** 0.875 precision means **1 in 8 detected conflicts is wrong**. If Russell sees 8 conflicts/week and 1 is bogus, that's tolerable; if Triage detects 50/week (every memory pair scored), 6 are bogus and Russell starts ignoring all of them. Security industry data: ["more than 50% of false-positive alerts cause analyst desensitization"](https://www.stamus-networks.com/blog/the-hidden-risks-of-false-positives-how-to-prevent-alert-fatigue-in-your-organization). The same dynamic applies to memory conflicts. The v0.1 PITFALLS.md MP-2 already documented this in general terms; v0.2 makes it concrete.
- **Warning signs:** Russell dismisses >50% of surfaced conflicts ("acceptance rate"); inbox grows unboundedly.
- **Prevention:** (1) **Inbox-only, never proactive notification** (per STATE.md decision 5 — already locked). Russell pulls, Engram doesn't push. (2) **Severity thresholding** — only show `severity=high` conflicts in the default inbox view; `medium`/`low` accessible via explicit filter. (3) **Aging policy** — conflicts unviewed for 30 days auto-archive (don't pile up). (4) **One-click dismissal** with `wrong | not_actually_a_conflict | resolved` reasons; feed dismissals back into a 50-sample correction set for ENG-16 v2. (5) Sample size on the precision eval is small (30 pairs from STATE.md, 50-sample eval per CD-2); broaden to 100 pairs before scaling notification surface area.
- **Detection:** Acceptance rate dashboard (acted-on / surfaced); alert if < 40%.

### CD-2: False-negative regression — memorability rubric changes flip prior-validated pairs

- **Severity:** serious
- **Phase:** conflict-wiring plan + the eval-harness work
- **Failure mode:** ENG-16 validated 30-50 pairs against a specific memorability rubric. v0.2's hybrid-rank tuning (HR-1..6) may shift the upstream scoring distribution — pairs that v0.1 scored "memorability 0.75" may now score 0.65, falling out of the conflict-eligible band. The 0.875 precision number from the original eval **no longer applies** to the new scoring distribution. Silent regression: detected-conflict count drops, looks like quieter system; actual conflicts are being missed.
- **Warning signs:** Detected-conflict count drops sharply after a model or weight change; recall on the 50-pair validation set drops below 0.9.
- **Prevention:** (1) **Re-run the ENG-16 validation set on every change** to: memorability model, memorability prompt, embedding model, hybrid-rank weights. CI gate: precision ≥ 0.85 AND recall ≥ 0.90. (2) **Lock the validation corpus** in `.planning/research/conflict-validation-pairs.json` (or extend the existing 30-pair set to 100). Version it. (3) Distinguish "conflict not detected" from "memorability threshold not met" — log the reason. Dashboard: pairs-with-conflict-but-below-memorability per week. (4) When precision/recall changes >2pp, write a migration note; never silently accept.
- **Detection:** CI gate on validation corpus; pairs-below-threshold dashboard.

### CD-3: Latency in ingest pipeline — 1-3s additional per memory

- **Severity:** serious
- **Phase:** conflict-wiring plan
- **Failure mode:** `detectConflict()` is an inference call. For each new memory, candidate pairs must be considered (every memory in the same workspace? Every memory of the same type? A vector-similarity-pre-filtered set?). Naive: N existing memories × 1 conflict call each = O(N) AI calls per write. At 500 blocks per workspace, that's 500 AI calls = 30-60s per remember(). Triage Worker becomes the bottleneck.
- **Warning signs:** Triage Worker p50 climbs >5s; queue backlog grows; `ingest_status` rows stuck in `phase_2_embedded` (per v0.1 IP-7 mechanic).
- **Prevention:** (1) **Vector-similarity pre-filter** — only run `detectConflict()` against the top-K (K=5) most cosine-similar existing memories of the same `type`. Cosine pre-filter is one Vectorize call (~80ms) vs. N AI calls. (2) **Type-bound pairing** — never compare `job_application` against `meeting_note`; they're not conflict-eligible. Filter at SQL level before pairing. (3) **Skip-list** — memories with `cold_storage=true` (per Phase 5 D-07) are excluded from conflict consideration. (4) Budget: conflict detection runs as a **separate Queue stage** (not inline with embedding). Phase 1 embed+store; Phase 2 (async) extract+memorability; Phase 3 (async) conflict scan. Multi-stage Queue per v0.1 progressive enrichment model. (5) Per-write conflict budget: max 5 `detectConflict()` calls per memory (top-5 cosine candidates only).
- **Detection:** Triage Worker p99 latency dashboard; AI-calls-per-memory metric.

### CD-4: Confidence inflation — pair the same memory with itself or near-duplicates, get high-confidence false conflicts

- **Severity:** annoying → serious
- **Phase:** conflict-wiring plan
- **Failure mode:** Cosine pre-filter (CD-3) returns top-K most-similar memories. If Russell stored a job posting twice (legitimate dedup miss, common at ingest), the top-K-similar pair is the duplicate. `detectConflict()` sees nearly-identical content and... may or may not flag it (depends on prompt). If it flags, it's high-confidence (the contents really are the same), and the conflict is "memory A says X, memory B says X" — useless.
- **Warning signs:** Conflict descriptions with identical or near-identical text on both sides; Vectorize cosine between conflicting memories >0.95.
- **Prevention:** (1) **Cosine ceiling** on conflict-eligible pairs: skip pairs with cosine >0.92 (they're duplicates, not conflicts — route to `duplicate_resolution`, not `conflict`). (2) Surface duplicate-detection as a separate signal: `meta.suggestions.actions: "Found near-duplicate; consider forget()."`. (3) Test: store the same memory twice, assert zero conflict generated, one duplicate suggestion generated.
- **Detection:** Conflict-cosine histogram; alert on conflicts at cosine >0.92.

### CD-5: Time-blind conflicts — "Russell uses TypeScript" vs "Russell uses Python" flagged as conflict

- **Severity:** annoying
- **Phase:** conflict-wiring plan + a `created_at`-aware prompt pass
- **Failure mode:** Already documented in v0.1 PITFALLS.md MP-2. Surfaces specifically in v0.2 because conflict detection is going live. Without temporal awareness, evolving facts (jobs, tools, preferences) look like contradictions. Russell switched from React to Vue last year; both memories are true at their respective times. Engram cries wolf.
- **Warning signs:** Conflicts where both memories are >30 days old AND `created_at` diff >90 days; user dismissal reason "not_actually_a_conflict" dominant.
- **Prevention:** (1) **Include `created_at` in the conflict prompt** — `"Memory A (2025-01-15): ... Memory B (2026-04-20): ... Are these contradictory FACTS-AT-THE-SAME-TIME, or evolution-over-time? Only flag if facts-at-same-time."`. (2) Severity rule: pairs with `created_at` diff >180 days default to `severity=low` regardless of model output. (3) Test fixture: 10 evolution-over-time pairs (job changes, tool migrations, opinion updates); assert ≤1 surfaced as `severity=high`.
- **Detection:** Time-diff histogram of surfaced conflicts.

### CD-6: Conflict descriptions leak workspace content into Inbox UI

- **Severity:** annoying for v0.2, serious for v0.3 (multi-tenant)
- **Phase:** conflict-wiring plan
- **Failure mode:** v0.2 is single-tenant (Russell only). But the conflict description string includes verbatim chunks of memory A and memory B. When v0.3 multi-tenant lands, conflict descriptions written in v0.2 may carry forward unrestricted access patterns into the inbox UI. Also: long conflict descriptions blow MCP-1 25K-token cap if many conflicts surface together.
- **Warning signs:** Conflict description > 500 chars; conflicts including full memory bodies rather than just the contradicting fields.
- **Prevention:** (1) Conflict description format frozen: `"<Property>: A says <X>, B says <Y> (memory_ids: [a_id, b_id])"`. Bounded by property name + 2 short values + IDs. Max 200 chars per conflict. (2) Conflict storage in SQLite uses `memory_a_id` + `memory_b_id` foreign keys + property name + value-pair; the rendered description is generated at read time, not stored. Future workspace_id checks gate rendering. (3) Inbox/conflict surfacing in MCP envelope: cap N conflicts shown per response at 5; remainder via cursor.
- **Detection:** Length assertions on conflict descriptions; envelope-size test with worst-case conflict bundle.

## 4. Hybrid-Rank Tuning Pitfalls

Task 5.1 A/B work tunes `HYBRID_WEIGHTS = {cosine: 1.0, recency: 0.15, type_match: 0.2, scope_match: 0.15}` against a real-corpus eval set. STATE.md notes the corpus is 27 entries (small).

### HR-1: Small-N overfitting — 27 real-corpus entries don't generalize

- **Severity:** serious for long-term quality
- **Phase:** the hybrid-rank tuning plan
- **Failure mode:** 27 entries is below the threshold most relevance-tuning research uses (typically ≥150 query-document pairs per [DAT paper](https://arxiv.org/pdf/2503.23013)). Weight values that maximize F1 on 27 entries are likely overfit — fitting noise rather than signal. The tuned weights perform worse on the 28th entry than the starting weights. [Overfitting in hyperparameter tuning literature](https://www.meegle.com/en_us/topics/overfitting/overfitting-in-hyperparameter-tuning): "improper validation techniques, such as using an unrepresentative validation set or failing to use cross-validation, can lead to overfitting."
- **Warning signs:** Tuned weights produce dramatically different relative weighting than starting (e.g., `recency: 0.5` instead of `0.15`); F1 on the tuning set hits 0.95+ but recall on novel queries drops.
- **Prevention:** (1) **Hold out a validation set** — split 27 entries into 20 train / 7 validate. Never tune against validate; report validate F1 as the publishable number. (2) **K-fold cross-validation** on the 20-train set (k=5). Average F1 across folds is the tuning signal. (3) **Bayesian-optimization-with-uncertainty** rather than grid search; the optimizer outputs a confidence band that explicitly admits small-N. (4) **Lock weights with documented evidence** — any weight change requires a written justification (`docs/hybrid-rank-changelog.md`) including pre/post F1, validate-set F1, and a hand-reviewed sample of result reorderings. No silent weight changes. (5) Sample size: until corpus grows to ≥100 entries, prefer **light tuning** (±20% around starting weights, not full sweep).
- **Detection:** Validate-set F1 reported alongside train-set F1 on every weight change.

### HR-2: Reward hacking — "good F1, bad outcomes" (metric improves but ranks worsen)

- **Severity:** serious
- **Phase:** hybrid-rank tuning plan
- **Failure mode:** F1 measures whether the right set is returned, **not the order**. A weight combination might return all correct results but with the user's intended top-pick at rank 5 instead of rank 1. F1=0.83 hides this. [RAG metrics literature](https://nirantk.com/writing/rag-metrics-for-technical-leaders/): "traditional metrics like nDCG/MAP/MRR misfit RAG, where LLMs consume a set of passages rather than a browsed list; position discounts and prevalence-blind aggregation miss what matters: whether the prompt at cutoff K contains the decisive evidence." Engram's case is the inverse: Russell reads top-3, so rank order DOES matter — but F1 alone doesn't reward it.
- **Warning signs:** F1 climbs but Russell reports "it found the right memory but it was 4th"; MRR drops while F1 rises.
- **Prevention:** (1) **Track MRR alongside F1** — Mean Reciprocal Rank of the gold-truth top match. MRR=1.0 means gold is always rank-1. (2) **Pareto front, not single metric** — tune for `(F1, MRR, p50_latency)`; reject weight combos that improve F1 by <5% while dropping MRR by >10%. (3) **Top-1 accuracy** as the visible metric — for Russell's user experience, "did the top result match?" is more meaningful than F1@10. (4) Per-query inspection on weight changes: hand-review 5 queries from the train set, look at top-3 reordering, gut-check whether reorderings are improvements. Reviewer sign-off in changelog.
- **Detection:** Tuning script reports F1, MRR, top-1, p50 simultaneously; reject single-axis wins.

### HR-3: Threshold sensitivity — small weight changes flip rank order on small corpora

- **Severity:** annoying → serious
- **Phase:** hybrid-rank tuning plan
- **Failure mode:** On 27 entries, hybrid-rank scores are tightly clustered (cosine differences of 0.02 are common). Weight change of `recency: 0.15 → 0.18` produces large rank reorderings because the score-clustering is tight. "Tuned" weights produce wildly unstable rankings across small input perturbations (different time-of-day on the recency calc; one memory added; one removed). [DAT paper](https://arxiv.org/pdf/2503.23013) explicitly addresses this: "fixed weighting parameter (α) determined through offline tuning on validation datasets ... fails to account for diverse nature of user queries."
- **Warning signs:** Re-running the same recall() at different timestamps produces different top-3; running with N=27 vs N=28 corpus produces different top-3.
- **Prevention:** (1) **Sensitivity analysis as part of tuning** — for each candidate weight set, perturb each weight by ±5% and report the rank-reorder rate. Reject weight sets with >30% rank instability. (2) **Stable recency function** — current is linear time decay; switch to bucketed (day/week/month/year) so recency doesn't shift on minute-to-minute timestamps. (3) **Score-clustering report** — if top-5 scores span <0.05, log `meta.warnings: "Result ranking sensitive to weight tuning."`. (4) Don't expose weight tuning to per-workspace customization until corpus ≥1000 entries; until then, global weights only.
- **Detection:** Sensitivity-analysis output in tuning script; rank-instability test.

### HR-4: Tuning to the corpus = leaking test data into training

- **Severity:** serious
- **Phase:** hybrid-rank tuning plan
- **Failure mode:** The 27-entry real-corpus is Russell's actual memories. Tuning weights on it then using it to validate is the same as testing on training data. The reported F1 is inflated. When Russell's corpus grows to 100, weights derived from those original 27 don't reflect the new shape. Compounds with HR-1.
- **Warning signs:** F1 on the tuning set is dramatically higher than F1 on fresh queries Russell tries.
- **Prevention:** (1) **Time-split the corpus** — train on memories from before date X, validate on memories from after date X. Simulates the corpus-grows-over-time reality. (2) **Generate synthetic queries** with the AI for memories the queries didn't originally serve — broadens the corpus beyond Russell's specific recall patterns. (3) **Adversarial queries** — Russell hand-writes 20 queries designed to be hard (entities that appear in multiple memories; queries with ambiguous intent). Add to validation set. (4) Re-tune annually or when corpus grows 5x; lock weights between re-tunings.
- **Detection:** Train/validate F1 gap; flag if gap >10pp.

### HR-5: Recency weight on a stale-vector corpus penalizes legitimately important old memories

- **Severity:** serious
- **Phase:** hybrid-rank tuning plan
- **Failure mode:** 30-day recency half-life (per AI-SPEC.md). Russell's note from 6 months ago about "Stripe interview took 4 weeks, focus on system design" is highly relevant when he's preparing for another interview today, but recency-scored to ~0.18 (six months = ~6 half-lives = 2^-6 ≈ 0.015 of the raw recency factor, then × HYBRID_WEIGHTS.recency=0.15). Effective demotion. Top result becomes yesterday's note about "interview tomorrow" (low informational value but high recency).
- **Warning signs:** Russell's known-relevant historical notes consistently rank below recent low-value notes.
- **Prevention:** (1) **Per-type recency profile** — `decision_log` and `research_note` have **long half-lives** (180 days); `meeting_note` and `inbox` short (14 days). Configurable per memory type. (2) **Cap recency contribution** — recency weight contributes ≤0.15 of total score even at maximum (memory created right now). Prevents recency from dominating tied-cosine outcomes (also addresses QE-4 interaction). (3) **Query-temporality detection** — queries with no temporal marker get default recency; queries with "recent"/"latest" double the weight; queries with "I learned" or "what did I think about" halve it. (4) Lock per-type half-lives in `@engram/ai-config`; tune only globally (the type-multipliers) until corpus is large enough for per-type evidence.
- **Detection:** Old-but-correct memory recall test bucket.

### HR-6: Anti-pattern — tuning weights and embedding model simultaneously

- **Severity:** serious (entangled experiments)
- **Phase:** hybrid-rank tuning plan + future embedding upgrade plan
- **Failure mode:** v0.2 plan might tune weights AND consider a future embedding upgrade. Doing both at once: an F1 improvement could come from either change, and isolating which is impossible. Worse: weight tune optimized for `qwen3-embedding-0.6b` is wrong for a `bge-large` upgrade. Common RAG pitfall — entangled variables defeat learning.
- **Warning signs:** Multi-variable PR diffs; F1 changes attributed vaguely.
- **Prevention:** (1) **One-variable changes only** — separate PRs for weight tuning, embedding-model bumps, prompt changes. (2) **PR template asks** "what other variables changed?"; reviewer enforces. (3) Tuning script records the embedding model + version in the output so retrospectively-attributed changes are traceable. (4) Embedding-model upgrade is a separate plan with its own re-tune-after step.
- **Detection:** PR review enforcement.

## 5. Integration Pitfalls (v0.1 → v0.2 Compatibility)

These are not feature-specific; they arise from ADDING features to a working production RAG system.

### INT-1: EMBEDDING_VERSION=2 holdovers — v1 vectors poison v2 results

- **Severity:** catastrophic
- **Phase:** the first plan that touches Vectorize in v0.2
- **Failure mode:** Engram's `ai-helper.ts` has `EMBEDDING_VERSION = 2` (verified 2026-06-02). Mixing v1 (bge-base 768d) and v2 (qwen3 1024d) vectors in the SAME Vectorize index is **physically impossible** (index is dimension-locked at 1024d per VEC-1 — the index would reject 768d upserts). BUT the failure surfaces if v1 SQLite rows still have `embedding_model='@cf/baai/bge-base-en-v1.5'` stamps — re-embed scripts that filter on `WHERE embedding_version < 2` may skip rows that need re-processing. [Embedding migration literature](https://medium.com/data-science-collective/different-embedding-models-different-spaces-the-hidden-cost-of-model-upgrades-899db24ad233): "mixing embedding models alters the geometry of the embedding space ... directions, distances, and neighborhood structures shift, causing your vector index optimized for the previous coordinate system to search the wrong space."
- **Warning signs:** `SELECT COUNT(*) FROM blocks WHERE embedding_version IS NULL OR embedding_version < 2` returns >0; Vectorize index has `vector_count != blocks_count`.
- **Prevention:** (1) **One-time audit** at start of v0.2: assert all `blocks` rows have `embedding_version = 2` and `embedding_model = '@cf/qwen/qwen3-embedding-0.6b'`. If not, run re-embed migration BEFORE v0.2 ships any feature. (2) Re-embed migration script (idempotent): for each block with version<2, embed with current model, upsert to Vectorize (replaces old vector), update SQLite stamp atomically. (3) **Vectorize re-creation gate** — if dimension change was made between v0.1 and v0.2 ship (which it was per STATE.md: 768→1024), the v0.1 index is gone and v0.2 index must be re-populated. Verify via `wrangler vectorize get engram-memories --json` that `dimensions == 1024`. (4) CI gate: assertion test that current EMBEDDING_VERSION matches all stored blocks' embedding_version.
- **Detection:** Migration audit script run as part of `npm run setup` in v0.2.

### INT-2: Wrangler test config (`remote: true`) cost runaway in CI

- **Severity:** serious (real money in test budget)
- **Phase:** the test-infra plan (Wave 0 or Plan 01)
- **Failure mode:** ENG-24 fixed integration tests by adding `remote: true` to wrangler.test.jsonc — tests now hit **real** Cloudflare Vectorize + Workers AI. Every CI run consumes neurons and Vectorize ops. v0.2 adds: query expansion tests (~4x AI per recall), synthesis tests (~2-5s per call, billed), conflict-detection eval tests (50 pairs × inference call), hybrid-rank tuning eval (27+ queries × multiple weight configs × full recall path). At 10 CI runs/day, v0.2 test cost could exceed the entire account's free tier within days. Cloudflare bills aggressively for unexpected usage.
- **Warning signs:** Cloudflare bill line item "Workers AI" or "Vectorize" appearing in dev account; CI run time climbing.
- **Prevention:** (1) **Tiered test strategy** — three tiers: `unit` (mocks, no remote), `integration` (remote, run on `main` branch only, not on every PR), `eval` (remote, weekly cron). Configure in vitest.config.ts with explicit `--project` flags. (2) **Eval budget cap** — eval scripts include `MAX_AI_CALLS=200` env-var guard; abort if exceeded. (3) **Skip-integration default** — `npm test` runs unit only; `npm run test:integration` opts in; CI workflow uses environment selector. (4) **Promptfoo provider rate limit** — set `maxConcurrency: 2` to avoid burst-triggering 429s (which themselves cost retry budget). (5) Workers Analytics Engine query on dev account daily to alert if neurons consumed >X.
- **Detection:** Daily neuron-consumption check; CI run-time budget.

### INT-3: Vectorize cross-tenant — v0.2 single-tenant defaults forward-incompatible with v0.3

- **Severity:** serious (forward-compat trap)
- **Phase:** every v0.2 plan that touches Vectorize
- **Failure mode:** v0.2 has one user (Russell, `workspace_id="russell-personal"`). v0.3 brings multi-tenant. v0.1 Phase 5 already mandates `namespace per workspace` in Vectorize (per AI-SPEC.md) and `vectorize-helper.ts` already enforces namespace argument. BUT v0.2's new features (query expansion variants, conflict-detection candidate fetches) may be written without going through the helper. Direct `env.VECTORIZE.query` calls without namespace **silently search global**. Russell only notices when v0.3 lands and Devon's workspace returns Russell's vectors.
- **Warning signs:** Grep `env.VECTORIZE.query` outside `vectorize-helper.ts`; conflict-detection or expansion plan PRs that bypass the helper.
- **Prevention:** (1) **Re-confirm the ESLint/grep gate** from v0.1 Phase 5 is in place and runs in CI. (2) **New plans MUST use `vectorize-helper.ts`** — never call binding directly. Add to the plan-template's "required patterns" section. (3) Cross-workspace pentest test extended: for each new v0.2 feature (expansion, conflict candidates), add a pentest assertion that workspace_A vectors don't leak into workspace_B query results. (4) Code review checklist item: "Does this PR call `env.VECTORIZE.*` directly?"
- **Detection:** Grep-based CI gate; pentest fixture extended per new feature.

### INT-4: Phase 4 envelope contract — v0.2 features add fields that break existing tests

- **Severity:** serious
- **Phase:** every v0.2 plan
- **Failure mode:** Phase 4 D-07 froze the `EngramResponse<T>` envelope. v0.2 features want to add fields: `result.expanded_queries: string[]` (for QE transparency), `result.synthesis_citations: [{...}]` (for SY-2 grounding), `result.conflict_candidates: Conflict[]` (for CD inbox feed), etc. Adding fields to a frozen envelope breaks Phase 4 `envelope.test.ts` schema assertions. Worse: untested combinations of fields trigger MCP-1 25K-token-cap failures (per v0.1 PITFALLS MCP-1 + MCP-7).
- **Warning signs:** envelope.test.ts failing on v0.2 PR; envelope serialized size climbing in tools-integration.test.ts.
- **Prevention:** (1) **Distinguish "new field" from "new content in existing field"** — synthesis populates an EXISTING null field (per Phase 5 D-07 honest-stubs); expansion variants go into `meta.warnings` or `meta.gaps`, not a new field; conflict candidates go into `context.conflicts` (existing field per CLAUDE.md envelope spec). Only add new top-level fields with explicit envelope contract bump. (2) **Token-budget assertions extended** — for every new field-populating feature, add a worst-case test (e.g., 25 expanded results + synthesis + 10 conflict candidates) and assert serialized response <8K tokens (v0.1 MCP-1 budget). (3) Envelope schema versioning: add `meta.envelope_version: 2` field when content semantics shift even if shape doesn't.
- **Detection:** envelope.test.ts + token-budget asserts on every new feature.

### INT-5: Integration test debt compounds across plans

- **Severity:** annoying → serious (slow buildup, hard to repair)
- **Phase:** Plan 01 (early v0.2) — set the testing discipline
- **Failure mode:** Each plan adds happy-path tests; integration tests across features (query expansion + synthesis + hybrid-rank all interacting) are deferred. By v0.2 ship, the matrix of `verbosity × expansion-on-or-off × hybrid-weights × workspace-state` is untested. Bugs surface as Russell uses combinations Engram never tested. Common pitfall in incremental RAG development.
- **Warning signs:** PRs add tests for the new feature alone; no test combines multiple v0.2 features.
- **Prevention:** (1) **Dedicated integration test plan** at end of v0.2 (or interleaved as last plan in each wave): explicit end-to-end test combining all v0.2 features. (2) **Promptfoo eval suite** as the cross-feature gate — every PR runs the full eval suite (recall F1, conflict precision, synthesis grounding). (3) **Cross-feature test fixtures** — at least 5 scenarios that exercise expansion+synthesis+conflict+rank together; assert all pass. (4) Track "untested combinations" as Linear ENG sub-issues; resolve before milestone close.
- **Detection:** Coverage matrix in `.planning/research/v0.2-INTEGRATION-MATRIX.md` (to be created in Plan 01).

### INT-6: Synthesis + expansion + conflict surfacing in one response — MCP-1 25K cap is the silent ceiling

- **Severity:** serious
- **Phase:** the final integration plan + token-budget audit
- **Failure mode:** v0.1 PITFALLS MCP-1 + MCP-7 said the envelope budget is 25K (hard) / 8K (target). v0.2 adds: query expansion may surface variants in `meta`, synthesis adds up to 1024-token string in `result.synthesis`, conflict surfacing may add multiple `Conflict` objects to `context.conflicts`, hybrid-rank may add per-result `meta.scoring_explanation`. A "kitchen sink" recall: `recall(verbosity=synthesis, expand=true)` against a workspace with conflicts surfacing top-25 results + synthesis + 5 conflicts + entities + suggestions = easily 10K+ tokens, dangerously close to the 25K hard cap.
- **Warning signs:** `trimToBudget` (from Phase 4) silently truncating; users seeing inconsistent results.
- **Prevention:** (1) **Tiered truncation policy** — when approaching budget, drop in this order: `context.entities[N+]` → `context.timeline[N+]` → `context.conflicts[5+]` → `result.memories[]` extra fields (keep `id`, `summary`, `score`; drop `content`) → `meta.scoring_explanation` → `result.synthesis_citations`. (2) **Per-section budgets** revisited for v0.2: `result.memories ≤ 4K`, `result.synthesis ≤ 1.5K`, `context.* ≤ 1.5K combined`, `meta + suggestions ≤ 1K`. (3) **Kitchen-sink test** in integration: `recall(verbosity=synthesis, limit=25)` against fixture workspace with 10 conflicts, 50 entities; assert serialized ≤ 8K tokens. (4) On truncation, emit `meta.truncated: true` so Claude knows to follow up.
- **Detection:** Kitchen-sink integration test.

## v0.2 MUST-MITIGATE LIST (Ruthless 8)

The eight items v0.2 absolutely cannot ship without addressing. Everything else is deferrable; these are quality-of-output critical.

1. **INT-1: Re-embed audit pre-feature** — Before any v0.2 feature ships, verify `SELECT COUNT(*) FROM blocks WHERE embedding_version < 2` returns 0 across all blocks. 2. **QE-2 + QE-7: Variant similarity gate + original-as-floor** — Query expansion must (a) drop variants with cosine(original, variant) < 0.85, (b) always include the original query as variant[0]. Without (a), HyDE + rephrase drift will silently degrade recall. Without (b), a single 429 wipes out the entire recall.

3. **SY-1 + SY-2: Synthesis grounding + citation linkage** — Synthesis prompt requires inline `[memory_id]` markers AND post-process drops any sentence lacking a citation. Without it, synthesis hallucination is the single biggest trust-killer in v0.2.

4. **CD-1: Inbox-only, no proactive notification** — STATE.md decision 5 already locks this; the v0.2 implementation plan must enforce it. Any conflict surfacing that proactively notifies (push to Inbox UI, MCP suggestion) fails the must-mitigate gate.

5. **CD-3: Cosine pre-filter before `detectConflict()` AI calls** — Per-write conflict scan must use top-K=5 cosine-similar candidates of the same type, not full-N scan. Without this, Triage Worker melts under any meaningful workspace size.

6. **HR-1 + HR-4: Train/validate split on the 27-entry corpus** — Until corpus reaches 100+ entries, all weight tuning reports both train-set F1 and held-out validate-set F1. Single-number F1 is forbidden in v0.2 tuning PRs. Without this discipline, every "improvement" is statistically noise.

7. **INT-2: Tiered test strategy + neuron budget guard** — `remote: true` integration tests do NOT run on every PR. Three tiers (`unit` / `integration` / `eval`) with environment selectors. Eval scripts have `MAX_AI_CALLS=200` guard. Without it, dev-account billing risk is real.

8. **INT-4 + INT-6: Envelope budget audit + kitchen-sink token test** — Every new v0.2 feature ends with a worst-case integration test asserting serialized envelope ≤ 8K tokens AND envelope-shape test (`envelope.test.ts`) still passes. Don't break Phase 4's frozen contract.

- HR-2 reward hacking (MRR tracking is a "good to have" until F1 dynamics prove problematic)
