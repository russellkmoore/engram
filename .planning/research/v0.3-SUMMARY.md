# Research Summary — v0.3 Identity + Surface

**Project:** Engram
**Milestone:** v0.3 — Identity + Surface (first human-facing UI)
**Researched:** 2026-06-12
**Confidence:** HIGH (stack, architecture, pitfalls grounded in official CF docs and source inspection; MEDIUM on CF Email Service beta reliability)

---

## Executive Summary

v0.3 adds Engram's first browser surface to an existing, fully-deployed Cloudflare Workers + Durable Objects + MCP backend. The scope is deliberately wide: four surfaces (consent/sign-in, inbox, memory browser, admin/eval dashboard) delivered as a single milestone. The right approach is **server-side rendering with Hono JSX + HTMX on a separate `engram-web` Worker** using Workers Static Assets — not a React SPA bolted onto the existing MCP server. The two-Worker isolation rationale that separated `engram-mcp-server` from `engram-triage-worker` applies with equal force here: the MCP hot path must not share CPU budget or deployment lifecycle with a UI that will be iterated on rapidly.

The highest-risk item in v0.3 is not the UI itself — it is the **identity-convergence invariant**: a user who authenticates via the browser magic-link flow and a user who connects via Claude Desktop must resolve to the same `ENGRAM_IDENTITIES` KV record and the same `WorkspaceDO` instance. Getting this wrong means the UI and the AI client operate on different workspaces with no data overlap — a silent, extremely confusing failure. This design must be locked and tested before any auth code ships. The `link-mcp` step (where a verified web session writes a second KV entry keyed on the `mcp-remote` `clientId`) is the architectural solution: `oauth.ts` requires zero changes; the web flow writes the same `{ workspace_id, user_id }` shape it already expects.

The second highest-risk item is email infrastructure: Cloudflare Email Routing (what ENG-11 called "CF Email Routing magic links") is inbound-only and cannot send. Outbound transactional email requires the separate Cloudflare Email Service (`send_email` binding, Workers Paid required, public beta as of April 2026) or Resend as a fallback. Verifying CF Email Service access and a suitable sender domain are **pre-phase prerequisites** that gate Phase 1 (Auth). With those two risks mitigated upfront, the remaining work — DO RPC methods, Hono routes, Tailwind UI — follows well-established patterns with high confidence.

## Key Findings

### Recommended Stack

The UI is built with **Hono JSX + HTMX** (SSR-first, no SPA framework) served from a **separate `engram-web` Worker** using **Workers Static Assets**. This is not a compromise — it is the correct choice for the four surfaces in scope (a sign-in form, an inbox list, a memory table, a simple admin dashboard). None of these surfaces require client-side routing or a React bundle. HTMX `hx-post`/`hx-get` handles the interactive elements. For the memory browser's limited reactivity needs, `hono/jsx/dom` (2.8 KB) or Alpine.js (~7 KB) is sufficient without adding a full SPA framework.

Styling uses **Tailwind CSS v4 via standalone CLI** (not the Vite plugin, which conflicts with `@cloudflare/vite-plugin` per GitHub issues tailwindcss#15399 / workers-sdk#9379) plus **Radix UI primitives** for accessible components (dialog, toast, dropdown-menu). `shadcn/ui` is the right long-term direction but targets React; it is deferred until the Vite plugin conflict resolves upstream.

Session management uses **Hono signed cookies + KV session store**: `hono/cookie`'s `setSignedCookie`/`getSignedCookie` (HMAC-SHA-256 via WebCrypto, native in workerd) backed by a `WEB_SESSIONS` KV namespace. The session value is an opaque token; the payload (workspace_id, user_id) lives server-side in KV, not in the cookie. This is the correct pattern for magic-link auth which requires revocability.

**Resolved disagreement — UI Worker placement:** Three of four researchers (STACK, ARCHITECTURE, PITFALLS) agreed on a separate `engram-web` Worker; FEATURES suggested co-locating in `mcp-server`. The separate-Worker answer is correct. The one thing that stays in `mcp-server` is the OAuth consent HTML in `defaultHandler` — it must stay there because `OAuthProvider` dispatches `/authorize` to `defaultHandler` directly, and a cross-Worker redirect for consent would require passing OAuth state through redirects and add CSRF surface.

**Core technology additions:**

- `engram-web` Worker (new package): Hono v4.12.x + HTMX, Workers Static Assets, `run_worker_first: ["/api/*", "/auth/*"]`
- Tailwind CSS v4: standalone CLI (`tailwindcss --input --output`), `@import "tailwindcss"` in CSS entry, no Vite plugin
- `@radix-ui/react-dialog`, `@radix-ui/react-toast`, `@radix-ui/react-dropdown-menu`: accessible headless primitives for inbox detail, notifications, nav
- CF Email Service `send_email` binding: outbound transactional email, `env.EMAIL.send({ to, from, subject, html, text })`
- `WEB_SESSIONS` KV namespace (new): magic tokens (15-min TTL) and session records (30-day TTL)
- `WORKSPACE` DO binding on `engram-web`: `script_name: "engram-mcp-server"` — same namespace, direct DO RPC from the web Worker

**Explicitly not adding:** React, `@cloudflare/vite-plugin`, `@tailwindcss/vite`, Astro, Remix, Next.js, any ORM, any external auth library beyond Hono's built-ins.

### Expected Features

**Must ship (v0.3 acceptance gate):**

- **Auth / sign-in:** email entry form → magic link (CF Email Service) → POST-gate confirmation page → token verify → workspace bootstrap → session cookie → MCP config snippet with copy button. Zero terminal commands for a new user (Devon). Returning users (Russell): same flow, no re-bootstrap.
- **Link-MCP step:** `/consent/link-mcp?sub=<clientId>` — authenticated web user approves linking their web workspace to the `mcp-remote` OAuth subject. Writes to `ENGRAM_IDENTITIES` KV so `oauth.ts` finds the record on next MCP connection.
- **Inbox UI:** list of pending low-confidence items + conflict pairs (side-by-side Memory A vs Memory B). Accept (with optional type/property override), reject, and conflict resolve (Keep A / Keep B / Keep Both) actions. Severity badges, empty state.
- **Memory browser:** paginated list of `blocks` with type/scope/date/tag filters, text search (SQLite LIKE), detail view (full content, properties, tags, related memories, summary vs raw toggle). Read-only.
- **Admin dashboard:** connected users list (from `ENGRAM_IDENTITIES` KV), admin-triggered invite (magic link to Devon's email), neuron spend table (7d/30d) ported from `eval-budget-summary.mjs` via server-side proxy to Analytics Engine SQL API.

**Should have (stretch if time allows within v0.3):**

- Eval-budget time-series chart (table is MVP; chart is stretch)
- Per-model neuron breakdown in admin dashboard
- Semantic search integration in memory browser (route to `recall()` Vectorize backend instead of LIKE)
- Conflict "why flagged?" expandable panel (memorability score + source signal)
- Bulk inbox accept/reject

**Confirmed anti-features (do not build at any point in v0.3):**

- Password authentication, social OAuth login (Google/GitHub), OTP codes
- Inline memory editing (breaks semantic consistency; mutations need re-embedding)
- Full graph visualization (D3/Cytoscape — product in itself)
- RBAC / role management (`members` table exists; add at v0.4 with teams)
- Billing / Stripe
- Real-time WebSocket updates
- Memory type schema editor (defer to v0.4 multi-workspace work)
- AI-suggested merge text for conflict resolution (LLM call at review time — violates "CF AI for grunt work" principle)
- Auto-accept toggle for inbox items

### Architecture Approach

The architecture is a **thin JSON API BFF on `engram-web`** that calls `WorkspaceDO` RPC methods directly via a DO binding (`script_name: "engram-mcp-server"`), bypassing the MCP layer entirely. The `EngramResponse<T>` envelope is optimized for Claude (pre-synthesis, coverage signals, gap analysis) — a browser UI wants flat JSON. Routing through MCP-over-HTTP would pay synthesis cost the UI cannot render, and would require MCP tool mutations for inbox actions that must not become public MCP tools (the MCP surface is capped at 9 tools, inbox management is a UI concern).

**Major components (new):**

1. `packages/web/src/index.ts` — Worker entry, auth gate middleware, Hono route dispatch, assets catch-all
2. `packages/web/src/auth/magic-link.ts` — token issuance (256-bit, SHA-256 stored), `EMAIL.send()`, POST-gate verify, `ENGRAM_IDENTITIES` KV write
3. `packages/web/src/auth/session.ts` — Hono signed cookie read/write/delete, `WEB_SESSIONS` KV ops
4. `packages/web/src/bff.ts` — typed `WorkspaceDO` stub resolver: `session_id → WEB_SESSIONS KV → workspace_id → env.WORKSPACE.idFromName()`
5. `packages/web/src/routes/consent.ts` — GET/POST `/consent`, POST `/consent/magic-link`, GET `/auth/verify`, GET+POST `/consent/link-mcp`
6. `packages/web/src/routes/inbox.ts` — `GET /api/inbox`, `POST /api/inbox/:id/accept`, `POST /api/inbox/:id/reject`
7. `packages/web/src/routes/memories.ts` — `GET /api/memories`, `GET /api/memories/:id`
8. `packages/web/src/routes/admin.ts` — `GET /api/admin/members`, `GET /api/admin/neuron-spend` (server-side proxy to AE SQL API)

**Modified (WorkspaceDO new RPC methods, each with `assertOwnsWorkspace` as first line):**

- `listInbox({ workspace_id, cursor?, limit?, type_filter? })` → `{ items: InboxItem[], next_cursor }`
- `acceptInboxItem({ workspace_id, id, override_type?, override_properties? })` → `{ block_id }`
- `rejectInboxItem({ workspace_id, id, reason? })` → `void` (soft-delete: sets `rejected_at`)
- `listBlocks({ workspace_id, cursor?, limit?, type?, scope?, query?, include_cold? })` → `{ blocks: BlockSummary[], total_count, next_cursor }`
- `listMembers({ workspace_id })` → `MemberSummary[]`
- Schema migration: `+rejected_at INTEGER` on `inbox` table (migration tag v3)

**Explicitly not modified:** `mcp-server/src/index.ts`, `mcp-server/src/oauth.ts`, `mcp-server/wrangler.jsonc`, `triage-worker/`, `ENGRAM_IDENTITIES` KV schema, MCP tool surface (no new MCP tools for v0.3).

**Identity convergence design (the crux):**

```
Magic-link verify writes:
  ENGRAM_IDENTITIES.put(user_id, { workspace_id, user_id })

Link-MCP confirm writes:
  ENGRAM_IDENTITIES.put(mcp_clientId, { workspace_id, user_id })

OAuth authorize reads (existing, unchanged):
  ENGRAM_IDENTITIES.get(sub=clientId) → { workspace_id, user_id }
```

Both writes produce the same `{ workspace_id, user_id }` shape satisfying `IdentityRecordSchema`. `oauth.ts` requires zero changes.

### Critical Pitfalls (Must-Mitigate Checklist)

The following 15 items cannot be deferred. v0.3 cannot ship without addressing all of them.

| ID | Pitfall | Minimum Required Action |
|----|---------|------------------------|
| ML-1 | Mail scanner pre-fetches magic link, consumes single-use token | POST-gate confirmation page: GET `/auth/verify` renders "Sign in" button only; token consumed on POST |
| ML-2 | Token entropy too low / plain-text storage | 256-bit token via `crypto.getRandomValues`, store SHA-256 hash in KV, 15-min TTL, delete on first use |
| ML-3 | Open redirect on callback URL | Server-side allowlist, `new URL()` parse, validate `origin === ALLOWED_ORIGIN` before redirect |
| EM-1 | CF Email Routing is inbound-only — cannot send | Confirm `[[send_email]]` CF Email Service access on account BEFORE auth phase begins |
| IC-1 | Magic-link creates divergent workspace identity | Write to same `ENGRAM_IDENTITIES` KV schema; never auto-create a new workspace from web login if one already exists |
| IC-2 | KV propagation lag invalidates first session read | Hono signed cookie for session (no per-request KV lookup for session validation); KV used for identity writes only |
| IC-3 | Web session reads wrong workspace via URL manipulation | `workspace_id` derived exclusively from session cookie via KV, never from URL path or query params |
| WP-1 | CSRF on inbox write endpoints | `__Host-CSRF` double-submit cookie + Origin header check on all mutating routes |
| WP-3 | Missing workspace ownership check on web writes | Session-derived `workspace_id` → DO stub construction; `assertOwnsWorkspace()` fires as second layer in DO |
| DU-1 | Chatty per-row DO calls from list views | Single paginated `listInbox(limit, cursor)` DO RPC — one SQL query per page, never N per item |
| DU-3 | UI shares CPU with MCP Worker hot path | Separate `engram-web` Worker with independent deployment — locked before any UI code |
| SA-1 | SPA fallback swallows auth callback navigation | `run_worker_first: ["/api/*", "/auth/*"]` in wrangler.jsonc |
| SA-2 | Secret leakage via VITE_* into client bundle | `@cloudflare/vite-plugin` ≥ 1.6.0 (CVE-2025-59427 patch); no secrets with VITE_ prefix; all secrets in Worker `env` |
| IC-5 | Session cookie leaks across workers.dev subdomains | `__Host-engram-session` cookie name prefix; deploy on custom domain |
| AD-4 | Analytics Engine API token exposed to browser | Admin neuron-spend handler is server-side only; token in Worker secret (`wrangler secret put AE_API_TOKEN`) |

**Additional high-priority (serious severity, should not ship without):**

- ML-4: Token replay via KV eventual consistency — use POST-gate (ML-1 prevention covers this) or DO-backed atomic token consumption
- IC-4: Race between web signup and OAuth bootstrap — `idFromName()` is deterministic; make workspace creation idempotent (check `ENGRAM_IDENTITIES` before writing)
- WP-2: Double-accept creates duplicate blocks — `INSERT INTO blocks ... ON CONFLICT(id) DO NOTHING`; disable Accept button on click
- WP-5: Conflict resolution triggers DO fan-out on re-embedding — SQLite mutation only in DO handler; re-embedding queued via `MemoryEvent` to triage worker
- DU-2: Cold-start 1-3s blank screen — lightweight `stub.ping()` RPC pre-warms DO; skeleton loader in UI shell
- AD-1: Analytics Engine sampling corrupts totals — always `SUM(_sample_interval * double1)`, never bare `SUM(double1)`

## Implications for Roadmap

### Dependency-Aware Build Order

Research from all four files converges on the same 5-phase build order. This is not optional — it is driven by hard data dependencies.

### Phase 1: Auth + Session Foundation
**Rationale:** Every authed surface (inbox, memories, admin) requires a valid session. The identity-convergence design must be validated end-to-end before any feature work begins. This phase is also the highest-risk: magic-link security, email infrastructure, KV convergence, cookie security, and the `link-mcp` UX are all here. Do not proceed to Phase 2 until a fresh user can complete the full flow zero-terminal.

**Delivers:**
- `packages/web/` scaffolded with full wrangler.jsonc, bindings, and `run_worker_first: ["/api/*", "/auth/*"]`
- `auth/magic-link.ts`: 256-bit token, SHA-256 storage, `EMAIL.send()`, POST-gate verify, `ENGRAM_IDENTITIES` write
- `auth/session.ts`: Hono signed cookie, `WEB_SESSIONS` KV ops
- `routes/consent.ts`: magic-link request → "check your email" page → POST-gate confirmation → session issue → `/inbox` redirect
- `routes/consent.ts`: `GET /consent/link-mcp`, `POST /consent/link-mcp` (the identity-convergence step)
- `bff.ts`: session → workspace_id → DO stub resolver
- Auth gate middleware: rejects unauthenticated requests to `/api/*`, `/inbox`, `/memories`, `/admin`

**Addresses:** Sign-in flow (Feature Area 1 table stakes), MCP config snippet page (differentiator)

**Must avoid:** ML-1 through ML-5, EM-1, IC-1 through IC-5, SA-1, SA-2, IC-5

**Acceptance gate:** New user (Devon): email → click link → confirmation page → click "Sign in" → working `__session` cookie + `ENGRAM_IDENTITIES` entry + MCP config snippet displayed. Returning user (Russell): email → link → session. Claude Desktop link-mcp: visit `/consent/link-mcp?sub=<clientId>` → confirm → Claude Desktop MCP tools work. Zero terminal commands. `IdentityRecordSchema` satisfied.

**Research flag:** NEEDS research-phase attention for `mcp-remote` 403 error surface — the exact error message format in Claude Desktop and whether it renders the link-mcp URL as clickable determines UX viability vs needing a QR/polling fallback. Verify empirically in Phase 1.

### Phase 2: WorkspaceDO New RPC Methods
**Rationale:** Inbox and memory browser routes call DO methods that do not exist yet. These are server-side additions to `workspace-do/` with no UI — they can be developed and tested in isolation before any frontend work. They are the data layer that Phase 3, 4, and 5 build on.

**Delivers:**
- `WorkspaceDO.listInbox()` + SQL + types
- `WorkspaceDO.acceptInboxItem()` + idempotent SQL (`ON CONFLICT DO NOTHING`)
- `WorkspaceDO.rejectInboxItem()` + soft-delete (`rejected_at`) + schema migration v3
- `WorkspaceDO.listBlocks()` + SQL with `LIMIT`/cursor (never unbounded) + types
- `WorkspaceDO.listMembers()` + types
- Unit tests for all 5 methods (each with `assertOwnsWorkspace` verified in test)

**Must avoid:** DU-1 (unbounded queries), WP-2 (double-accept duplicates), WP-5 (fan-out in DO handler)

**Research flag:** Standard DO RPC patterns — well-established, skip research-phase.

### Phase 3: Inbox UI
**Rationale:** The inbox is the highest-value surface for day-to-day use: v0.2 conflict detection has been producing rows since launch with no human review surface. This is also where the most write-path security work lives (CSRF, workspace validation), making it the right place to establish those patterns before the simpler read-only surfaces.

**Delivers:**
- `routes/inbox.ts`: `GET /api/inbox`, `POST /api/inbox/:id/accept`, `POST /api/inbox/:id/reject`
- Inbox HTML page: item cards (low-confidence), conflict pair view (side-by-side Memory A/B), severity badges, empty state
- CSRF protection (`__Host-CSRF` double-submit) on all write routes
- Pessimistic UI updates (no optimistic removes before API confirms)

**Must avoid:** WP-1 (CSRF), WP-2 (double-accept), WP-3 (workspace ownership on writes), WP-4 (optimistic desync)

**Research flag:** Standard Hono/HTMX patterns — well-documented, skip research-phase.

### Phase 4: Memory Browser
**Rationale:** Read-only surface, no write-path security complexity. Simpler to implement after inbox establishes the route patterns. The `listBlocks` RPC from Phase 2 is the only DO method needed; detail view reuses the existing `getBlock`.

**Delivers:**
- `routes/memories.ts`: `GET /api/memories` (paginated, filtered), `GET /api/memories/:id`
- Memory list HTML: type/scope/date/tag filters, SQLite LIKE search, pagination
- Memory detail HTML: full content, summary/raw toggle, properties panel, tags, related memories list
- `DELETE /api/memories/:id` (maps to existing `forget()` logic) — the only mutation in this phase

**Must avoid:** DU-4 (unbounded `listBlocks` queries — enforced by Phase 2 implementation)

**Research flag:** Skip research-phase for list/detail/filter patterns. If semantic search integration (Vectorize-backed `recall()` via the memory browser search box) is pursued as a stretch, that integration point warrants a research spike in Phase 4 planning.

### Phase 5: Admin + Eval-Budget Dashboard
**Rationale:** Analytics Engine query infrastructure is independent of the DO work (no Phase 2 dependency). `listMembers` from Phase 2 and the magic-link send from Phase 1 are reused for the invite flow. Admin is the lowest daily-use surface and the right place to end — any rough edges in the UI layer are less visible here.

**Delivers:**
- `routes/admin.ts`: `GET /api/admin/members`, `POST /api/admin/invite`, `GET /api/admin/neuron-spend`
- Admin HTML: connected users list, invite form, neuron spend table (7d/30d) with `SUM(_sample_interval * double1)` aggregation
- Server-side proxy to Analytics Engine SQL API; `AE_API_TOKEN` Worker secret; 5-minute KV cache on query results
- KV cache for analytics results (prevents per-page-load queries, DU-5 mitigation)
- Timezone-aware time bucketing (AD-2 prevention)

**Must avoid:** AD-1 (sampling correction), AD-2 (timezone bucketing), AD-3 (90-day retention labeling), AD-4 (token never in browser), DU-5 (cached analytics, not per-refresh queries), SC-3 (scope ceiling: neuron spend + identity list only)

**Research flag:** Analytics Engine SQL API — medium-documented. Confirm `_sample_interval` handling and `toStartOfDay(timestamp, timezone)` syntax before building. Worth a targeted research spike at phase planning time.

---

### Phase Ordering Rationale

- Auth must come first because it gates every subsequent surface (session required for all API routes)
- DO RPC methods must come before any UI route that calls them (Phase 2 before Phases 3–5)
- Inbox comes before memory browser because it has the highest feature value (unreviewed data has been accumulating) and establishes write-path security patterns
- Memory browser is pure read after inbox patterns are established — natural second surface
- Admin last: independent of memory/inbox, lowest urgency, can absorb any schedule slip without blocking the other surfaces
