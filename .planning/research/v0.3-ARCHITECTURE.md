# Architecture: v0.3 Identity + Surface — Frontend Integration

**Domain:** Adding first browser UI to an existing Cloudflare Worker + DO + OAuth backend
**Researched:** 2026-06-12
**Overall confidence:** HIGH (all decisions grounded in actual source files + verified Cloudflare docs)

---

## Baseline (Do Not Re-Research)

The existing two-Worker split is:
- `engram-mcp-server` — OAuthProvider wrapping `EngramMcp.serve("/mcp")`. The `defaultHandler` owns `/`, `/health`, `/authorize`, and the admin audit/purge endpoints. All non-MCP routes live in `packages/mcp-server/src/oauth.ts`.
- `engram-triage-worker` — queue consumer, no HTTP surface.
- `WorkspaceDO` — per-workspace SQLite (blocks, relations, tags, members, memory_types, inbox, conflicts). Every public method's first line is `assertOwnsWorkspace(workspace_id)`, which compares the provided `workspace_id` against `this.ctx.id.name`. This guard is the data-plane backstop.
- `ENGRAM_IDENTITIES` KV — keyed on OAuth `sub` (= `clientId` in current v0.1 flow), value is JSON `{ workspace_id, user_id }`. This is the identity bridge between OAuth and DO routing. The schema is locked by `IdentityRecordSchema` in `oauth.ts`: `{ workspace_id: z.string().min(1), user_id: z.string().min(1) }`.

## Question 1: Where Does the UI Live?

**Recommendation: a new `engram-web` Worker with static assets. Do NOT extend `engram-mcp-server`.**

### Rationale

The hot-path isolation rationale that produced the two-Worker split applies here with equal force. The MCP server is the product's critical path — it must never be taken down for a UI deploy, and a crashing UI handler must never affect MCP tool calls. Adding web routes, session middleware, cookie handling, and HTML rendering to `engram-mcp-server` violates both failure-isolation goals.

The Cloudflare Workers Static Assets feature (released 2025, HIGH confidence) makes a separate web Worker the clean choice. The `assets` block in wrangler.jsonc delivers static files from Cloudflare's CDN exactly like Pages, but inside the Workers build pipeline already used by this project. No new toolchain. Independent deploys.

```jsonc
// packages/web/wrangler.jsonc (new file)
{
  "name": "engram-web",
  "main": "src/index.ts",
  "compatibility_date": "2026-05-22",
  "compatibility_flags": ["nodejs_compat"],
  "assets": {
    "directory": "./dist/",
    "binding": "ASSETS",
    "run_worker_first": true   // auth gate runs before any asset byte is served
  },
  "durable_objects": {
    "bindings": [
      { "name": "WORKSPACE", "class_name": "WorkspaceDO", "script_name": "engram-mcp-server" }
    ]
  },
  "kv_namespaces": [
    { "binding": "ENGRAM_IDENTITIES", "id": "<same id as mcp-server>" },
    { "binding": "WEB_SESSIONS", "id": "<new namespace id>" }
  ],
  "send_email": [{ "name": "EMAIL" }],
  "analytics_engine_datasets": [{ "binding": "ANALYTICS", "dataset": "engram_ai_analytics" }]
}
```

Key properties:
- `engram-web` deploys, redeploys, and rolls back independently of `engram-mcp-server`.
- `packages/mcp-server/` source is not modified.
- `run_worker_first: true` ensures the auth gate intercepts unauthenticated requests to `/inbox`, `/memories`, `/admin` before the CDN returns a byte of HTML.
- The WORKSPACE DO binding uses `script_name: "engram-mcp-server"` — this is how one Worker binds to a DO class declared in a different Worker script. The DO instance is the same; there is one WorkspaceDO namespace shared across both Workers.

### Why Not Pages

Cloudflare Pages was the historical answer for static sites but Workers Static Assets (2025) supersedes it for projects already in a Workers monorepo. Pages adds a second deploy system, a different build pipeline, and cannot bind directly to Durable Objects. Workers Static Assets gets the same CDN delivery with zero new toolchain surface.

### Monorepo Addition

```text
engram/
  packages/
    mcp-server/          # unchanged
    triage-worker/       # unchanged
    workspace-do/        # new DO RPC methods added (see Question 5)
    web/                 # NEW
      src/
        index.ts         # Worker entry — auth gate + route dispatch
        auth/
          magic-link.ts  # token issuance, email send, verification
          session.ts     # cookie set/read/delete, WEB_SESSIONS KV ops
        routes/
          consent.ts     # GET /consent, POST /consent/magic-link, GET /auth/verify, GET /consent/link-mcp
          inbox.ts       # GET /api/inbox, POST /api/inbox/:id/accept, POST /api/inbox/:id/reject
          memories.ts    # GET /api/memories, GET /api/memories/:id
          admin.ts       # GET /api/admin/members, GET /api/admin/neuron-spend
        bff.ts           # typed helper: resolves WorkspaceDO stub for authenticated user
      dist/              # built frontend output (Vite + React/Preact)
      wrangler.jsonc
      package.json
```

## Question 2: How Does the Browser Talk to Data?

**Recommendation: thin JSON API on `engram-web` calling `WorkspaceDO` RPC methods directly via the WORKSPACE DO binding — not MCP-over-HTTP.**

### Why Not MCP-Over-HTTP

The `EngramResponse<T>` envelope is optimized for Claude, not for a browser UI. Every response includes `context.related[]`, `context.entities[]`, `meta.coverage`, `meta.gaps`, and `suggestions`. This is synthesis-first data designed to minimize Claude's reasoning burden — a human looking at an inbox wants a flat list, not a pre-synthesized narrative with gap analysis. Piping the browser through the MCP layer means:

1. The UI pays the CPU cost of synthesis it does not render.
2. No MCP tool mutates the inbox today — `acceptInboxItem` and `rejectInboxItem` have no MCP equivalents and must not get one (the MCP surface is capped at 9 tools, and inbox management is a UI concern, not an AI concern).
3. MCP is a stateful transport (session DOs, `EngramMcp` instances) — calling it from a browser BFF adds unnecessary session-DO lifecycle complexity.

### Why Not a New REST Layer on MCP Server

Adding REST routes to `engram-mcp-server` violates the isolation principle established in Question 1. It also couples the web API's deployment lifecycle to the MCP server's.

### Recommended Pattern: Web Worker BFF with Direct DO RPC

After validating the session cookie (see Question 4), the web Worker resolves the `WorkspaceDO` stub for the authenticated user's `workspace_id` and calls RPC methods directly:

```typescript
// packages/web/src/bff.ts
export function getWorkspaceStub(env: Env, workspace_id: string) {
  // workspace_id comes from the session record (KV-backed), never from the request body
  const id = env.WORKSPACE.idFromName(workspace_id);
  return env.WORKSPACE.get(id) as unknown as WorkspaceDO;
}
```

This is a standard Cloudflare pattern: multiple Workers can bind to the same DO namespace. The DO does not know or care which Worker called it — `assertOwnsWorkspace` validates the `workspace_id` argument against `this.ctx.id.name` regardless of caller.

### Web API Shape

The web API surface is thin, flat JSON — not `EngramResponse<T>`. No `context`, no `meta.coverage`, no `suggestions`. Pagination is cursor-based (keyset on `created_at`).

```
GET  /api/inbox                  → stub.listInbox({ workspace_id, cursor?, limit? })
POST /api/inbox/:id/accept       → stub.acceptInboxItem({ workspace_id, id, ... })
POST /api/inbox/:id/reject       → stub.rejectInboxItem({ workspace_id, id, reason? })
GET  /api/memories               → stub.listBlocks({ workspace_id, cursor?, limit?, type?, query? })
GET  /api/memories/:id           → stub.getBlock({ workspace_id, id })
GET  /api/admin/members          → stub.listMembers({ workspace_id })
GET  /api/admin/neuron-spend     → env.ANALYTICS SQL query (direct binding)
```

## Question 3: Magic-Link Auth Flow End-to-End

**This is the crux. The magic-link flow must produce the SAME KV identity record that the MCP OAuth path consumes.**

### The Convergence Invariant

The existing `oauth.ts` authorize handler does:

```typescript
// packages/mcp-server/src/oauth.ts (existing, unchanged)
const sub = oauthReqInfo.clientId;
const raw = await env.ENGRAM_IDENTITIES.get(sub);
// raw = JSON { workspace_id, user_id }
```

For a new user to connect via Claude Desktop, their `ENGRAM_IDENTITIES` KV entry must exist before they attempt an MCP tool call. Today this requires the 8-step `kv:bootstrap` terminal dance. v0.3 replaces that with a browser flow that writes the same KV record.

The identity record schema is locked by `IdentityRecordSchema` in `oauth.ts`:
```typescript
{ workspace_id: z.string().min(1), user_id: z.string().min(1) }
```

### Complete Flow

**Step 1 — User arrives at `engram-web` for the first time.**

`GET /` or `GET /consent`. No session cookie. The Worker's auth gate sees no cookie and serves the static consent/sign-in page from the ASSETS binding. (The auth gate only blocks `/api/*` routes and the authed page routes `/inbox`, `/memories`, `/admin`.)

**Step 2 — User submits their email.**

`POST /consent/magic-link` with `{ email: "user@example.com" }`.

Worker:
1. Generates `magic_token`: 32-byte cryptographically random hex string via `crypto.getRandomValues`.
2. Derives `user_id` from email: `email.toLowerCase().replace(/[^a-z0-9]/g, "-")` (deterministic slug).
3. Derives `workspace_id`: `${user_id}-personal`.
4. Writes to `WEB_SESSIONS` KV:
   ```
   key:   magic:<magic_token>
   value: JSON { email, user_id, workspace_id, issued_at: Date.now() }
   TTL:   900 seconds (15 minutes)
   ```
5. Sends magic-link email via `env.EMAIL.send(...)`:
   ```
   to:      user@example.com
   from:    noreply@engram.app
   subject: Sign in to Engram
   html:    <a href="https://engram-web.workers.dev/auth/verify?token=<magic_token>">Sign in</a>
   ```
   Note: Cloudflare Email Service (public beta, May 2026) supports arbitrary recipient addresses on the Workers Paid plan. For v0.3's controlled user set, a pre-verified destination address in Email Routing is an acceptable interim approach that stays on the free plan.
6. Returns `{ status: "sent" }` to the browser.

**Step 3 — User clicks the link in their email.**

`GET /auth/verify?token=<magic_token>`

Worker:
1. Reads `magic:<magic_token>` from `WEB_SESSIONS` KV.
2. If missing or expired: redirect to `/consent?error=expired`.
3. Belt-and-suspenders: validate `issued_at` is within 15 minutes (complements the KV TTL which may not have fired yet on edge).
4. Deletes the magic token entry immediately — single-use invariant.
5. Writes to `ENGRAM_IDENTITIES` KV (same namespace as `engram-mcp-server`):
   ```
   key:   <user_id>   (the email-derived slug)
   value: JSON { workspace_id, user_id }
   ```
   This entry is keyed on `user_id`, not on the `mcp-remote` `clientId`. It exists so the `link-mcp` step in Step 4 can look it up.
6. Generates `session_id`: 32-byte random hex.
7. Writes to `WEB_SESSIONS` KV:
   ```
   key:   session:<session_id>
   value: JSON { user_id, workspace_id, email, created_at: Date.now() }
   TTL:   2592000 seconds (30 days)
   ```
8. Sets cookie:
   ```
   Set-Cookie: __session=<session_id>; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=2592000
   ```
9. Redirects to `/inbox`.

**Step 4 — Bootstrapping the Claude Desktop MCP connection (the link-mcp step).**

After Step 3, the user has a working web session, but Claude Desktop does not yet have an `ENGRAM_IDENTITIES` entry keyed on their `mcp-remote` `clientId`. The `clientId` is generated by `mcp-remote` on first connection and is not known until the user actually tries to connect via Claude Desktop.

Flow:
1. User adds Engram to `claude_desktop_config.json` (same one-liner as today, script prints the snippet).
2. User restarts Claude Desktop, triggers any MCP tool call.
3. `mcp-remote` hits `/authorize` → `oauth.ts` looks up `sub = clientId` in `ENGRAM_IDENTITIES` → not found → returns:
   ```
   403: Unknown OAuth subject: <clientId>. Visit https://engram-web.workers.dev/consent/link-mcp?sub=<clientId> to connect your account.
   ```
   This is the same 403 as today, but the message now contains an actionable link instead of a terminal command.
4. User clicks the link in a browser where they already have a web session (`__session` cookie).
5. `GET /consent/link-mcp?sub=<clientId>` on `engram-web`:
   - Validates session cookie → gets `{ user_id, workspace_id }` from `WEB_SESSIONS` KV.
   - Renders a confirmation page: "Link your Claude Desktop account to Engram? (workspace: `workspace_id`)"
6. User clicks Confirm → `POST /consent/link-mcp`:
   - Writes to `ENGRAM_IDENTITIES` KV:
     ```
     key:   <clientId>   (the mcp-remote sub)
     value: JSON { workspace_id, user_id }
     ```
   - Returns success page: "Claude Desktop linked. Retry your tool call."
7. User retries the MCP tool call in Claude Desktop → `/authorize` succeeds → `completeAuthorization` → MCP session established.

**Result:** The 8-step terminal dance is replaced by:
1. Visit engram-web, enter email, click magic link (3 browser interactions → web session)
2. Add one-liner to `claude_desktop_config.json`, restart Claude Desktop (2 interactions, same as today)
3. Click the error link, confirm in browser (2 browser interactions → MCP linked)

Total: 7 interactions, zero terminal commands, zero file editing. With a copy-snippet improvement to step 2, this reaches the ≤5 meaningful steps target.

### KV Convergence Summary

```
Magic-link verify:
  ENGRAM_IDENTITIES.put(user_id, { workspace_id, user_id })

Link-MCP confirm:
  ENGRAM_IDENTITIES.put(mcp_clientId, { workspace_id, user_id })

OAuth authorize (existing, unchanged):
  ENGRAM_IDENTITIES.get(sub=clientId)  → reads the link-mcp entry
```

Both KV writes produce the same `{ workspace_id, user_id }` value. The schema satisfies `IdentityRecordSchema`. The `oauth.ts` authorize handler requires zero changes.

## Question 4: Session and Security Boundary

**Recommendation: HttpOnly session cookie backed by `WEB_SESSIONS` KV. The `assertOwnsWorkspace` DO guard is preserved and remains the data-plane backstop.**

### Cookie Strategy

```
Name:     __session
Value:    <session_id>  (32-byte hex opaque token — NOT a JWT, NOT the workspace_id)
Flags:    HttpOnly; Secure; SameSite=Lax; Path=/
Max-Age:  2592000 (30 days)
```

The session_id is opaque. The session payload is stored server-side in `WEB_SESSIONS` KV. The cookie value cannot be decoded by the browser or an attacker to learn `workspace_id` or `user_id`.

### Workspace Resolution Chain

```
Request arrives at engram-web
  │
  ├── Read __session cookie → session_id (opaque)
  ├── WEB_SESSIONS.get(session_id) → { user_id, workspace_id, email }
  │     If null/expired → redirect to /consent
  │
  └── Pass workspace_id to BFF
        │
        └── env.WORKSPACE.idFromName(workspace_id) → DO stub
              │
              └── WorkspaceDO.someMethod({ workspace_id, ... })
                    │
                    └── assertOwnsWorkspace(workspace_id) → PASS or THROW
```

`workspace_id` flows from KV (server-authoritative), never from request body or URL params. The DO method re-validates it against `this.ctx.id.name`. An attacker who controls the request body cannot escalate to a different workspace.

### CSRF Protection

`SameSite=Lax` blocks cross-site POST requests (the primary CSRF vector). For defense-in-depth on mutating endpoints, add a `X-Requested-With: XMLHttpRequest` header check — simple, zero-cost, blocks form-based CSRF that Lax's "top-level navigation" exception could theoretically allow.

### Session Invalidation

`WEB_SESSIONS.delete(session_id)` immediately invalidates the session. Sign-out: delete the KV record + respond with `Set-Cookie: __session=; Max-Age=0`. Cookie lifetime does not matter once the backing KV record is gone.

### The assertOwnsWorkspace Guarantee Is Preserved

The web path does not weaken the existing security invariant:

- MCP path: `props.workspace_id` comes from `ENGRAM_IDENTITIES` KV via `completeAuthorization` → `assertOwnsWorkspace`.
- Web path: `workspace_id` comes from `WEB_SESSIONS` KV → `assertOwnsWorkspace`.

Both paths source `workspace_id` from a server-side KV lookup keyed on a credential (OAuth token / session cookie). Neither path accepts `workspace_id` from the request body. The DO's `assertOwnsWorkspace` guard fires in both cases.

## Question 5: Data Flow Per Surface + New DO RPC Methods

### 5.1 Inbox UI

**Data source:** `inbox` table. Conflict items are `proposed_type = 'conflict'` rows (written by `insertConflictAsInbox`). Low-confidence items are any other `proposed_type` with `memorability_score < 0.8`.

**New DO RPC methods:**

```typescript
// Paginated inbox with optional type filter
listInbox(args: {
  workspace_id: string;
  cursor?: string;      // created_at of last item (keyset pagination)
  limit?: number;       // default 25
  type_filter?: 'all' | 'conflict' | 'low_confidence';
}): {
  items: InboxItem[];
  next_cursor: string | null;
}

type InboxItem = {
  id: string;
  content: string;
  proposed_type: string;
  proposed_properties: Record<string, unknown>;  // includes memory_a_id/memory_b_id for conflicts
  memorability_score: number;
  source: string;
  created_at: number;
};

// Accept: promote inbox item to a stored block
acceptInboxItem(args: {
  workspace_id: string;
  id: string;
  override_type?: string;
  override_properties?: Record<string, unknown>;
}): { block_id: string }

// Reject: soft-delete (mark rejected_at, keep row for audit)
rejectInboxItem(args: {
  workspace_id: string;
  id: string;
  reason?: string;
}): void
```

For conflict items (`proposed_type = 'conflict'`):
- Accept = "this contradiction is real; flag both `memory_a_id` and `memory_b_id`." The `acceptInboxItem` implementation writes a row to the `conflicts` table and marks the inbox row `rejected_at` (consumed).
- Reject = "false positive; dismiss." The `rejectInboxItem` implementation marks the inbox row `rejected_at` with `reason = 'false_positive'`.

**Existing DO methods used (no changes needed):** `insertConflictAsInbox` (write side, triage worker), `listConflicts` (the `conflicts` table view — distinct from `inbox`).

### 5.2 Memory Browser

**Data source:** `blocks` table (primary), `tags` table (count), `relations` table (detail view).

**New DO RPC methods:**

```typescript
// Paginated block listing with lightweight filters
listBlocks(args: {
  workspace_id: string;
  cursor?: string;       // id of last seen block (keyset on created_at DESC)
  limit?: number;        // default 20
  type?: string;         // filter by memory_type id
  scope?: string;        // 'personal' | 'project' | 'org'
  query?: string;        // non-empty: proxies to lexicalSearchBlocks
  include_cold?: boolean; // default false
}): {
  blocks: BlockSummary[];
  total_count: number;   // approximate COUNT(*) for the applied filter
  next_cursor: string | null;
}

type BlockSummary = {
  id: string;
  type: string;
  summary: string;       // AI-generated summary (truncated for list)
  properties: Record<string, unknown>;
  scope: string;
  source: string;
  confidence: number;
  created_at: number;
  updated_at: number;
  tag_count: number;     // from JOIN on tags (denormalized for list rendering)
};
```

**Existing DO methods used:** `getBlock({ workspace_id, id })` — detail view (no change needed). `lexicalSearchBlocks` — called internally by `listBlocks` when `query` is non-empty. `deleteBlock` — for a future "forget from UI" action (v0.3 can expose it as `DELETE /api/memories/:id`).

### 5.3 Minimal Admin

**Data source:** `members` table (workspace management) + Analytics Engine (neuron-spend dashboard).

**New DO RPC methods:**

```typescript
// List workspace members
listMembers(args: {
  workspace_id: string;
}): MemberSummary[]

type MemberSummary = {
  user_id: string;
  role: string;           // 'owner' | 'editor' | 'viewer'
  invited_by: string | null;
  joined_at: number;
};
```

**Analytics Engine (neuron-spend dashboard):** The `ANALYTICS` binding is declared on `engram-web`'s wrangler.jsonc pointing to the same `engram_ai_analytics` dataset already written by the triage worker. The neuron-spend query from `scripts/eval-budget-summary.mjs` is ported directly into the `/api/admin/neuron-spend` handler. No change to `engram-mcp-server` required.

## Build Order (Dependency-Aware)

### Phase 1 — Auth + Session Foundation

**Must ship first. All authed surfaces depend on this.**

Deliverables:
- `WEB_SESSIONS` KV namespace provisioned + wrangler.jsonc declared
- `send_email` (`EMAIL`) binding configured (verify with Cloudflare Email Service or Email Routing destination address)
- `packages/web` scaffolded with full wrangler.jsonc
- `auth/magic-link.ts`: token issuance, `WEB_SESSIONS` write, `EMAIL.send`, token verify, `ENGRAM_IDENTITIES` write
- `auth/session.ts`: session KV read/write/delete, cookie helpers
- `routes/consent.ts`: GET `/consent`, POST `/consent/magic-link`, GET `/auth/verify`, GET + POST `/consent/link-mcp`
- Auth gate middleware in `src/index.ts`: reject unauthenticated requests to `/api/*` + `/inbox` + `/memories` + `/admin`
- `bff.ts`: session → workspace_id → DO stub resolver

Acceptance gate: a fresh user can go from the consent page → email → click link → have a working `__session` cookie AND a working Claude Desktop MCP connection in ≤7 browser interactions, zero terminal commands. The `ENGRAM_IDENTITIES` entry written by the web flow must satisfy `IdentityRecordSchema` (parseable by the existing `oauth.ts` handler without changes).

### Phase 2 — New DO RPC Methods

**Cannot ship authed surfaces without these. Depends on Phase 1 for test harness.**

Deliverables:
- `WorkspaceDO.listInbox()` + SQL query + types
- `WorkspaceDO.acceptInboxItem()` + SQL query
- `WorkspaceDO.rejectInboxItem()` + SQL query (+ `rejected_at` migration)
- `WorkspaceDO.listBlocks()` + SQL query + types
- `WorkspaceDO.listMembers()` + types
- Unit tests for all 5 new DO methods (consistent with existing test discipline)

### Phase 3 — Inbox UI

**Depends on Phase 1 (auth gate) + Phase 2 (`listInbox`, `acceptInboxItem`, `rejectInboxItem`).**

Deliverables:
- `routes/inbox.ts`: GET `/api/inbox`, POST `/api/inbox/:id/accept`, POST `/api/inbox/:id/reject`
- Frontend inbox page (list + accept/reject actions + conflict item rendering)

### Phase 4 — Memory Browser

**Depends on Phase 1 (auth gate) + Phase 2 (`listBlocks`, `getBlock`).**

Deliverables:
- `routes/memories.ts`: GET `/api/memories`, GET `/api/memories/:id`
- Frontend memories page (list, search, detail)

### Phase 5 — Admin + Eval Dashboard

## Architecture Diagram

```
Browser (unauthenticated)
  └── GET /consent → engram-web → ASSETS binding → static consent page
  └── POST /consent/magic-link
        ├── WEB_SESSIONS KV.put(magic:<token>, { email, user_id, workspace_id }, TTL=900)
        └── EMAIL.send({ to: email, subject: "Sign in", html: <link> })
  └── GET /auth/verify?token=<token>
        ├── WEB_SESSIONS KV.delete(magic:<token>)
        ├── ENGRAM_IDENTITIES KV.put(user_id, { workspace_id, user_id })
        ├── WEB_SESSIONS KV.put(session:<id>, { user_id, workspace_id, email }, TTL=30d)
        └── Set-Cookie: __session=<id> → redirect /inbox

Browser (authenticated)
  └── GET /consent/link-mcp?sub=<mcp-clientId>
        ├── WEB_SESSIONS KV.get(session:...) → { user_id, workspace_id }
        └── [confirm] ENGRAM_IDENTITIES KV.put(<mcp-clientId>, { workspace_id, user_id })

  └── GET /api/inbox
        ├── WEB_SESSIONS KV.get(session:...) → workspace_id
        └── WORKSPACE.idFromName(workspace_id)
              └── WorkspaceDO.listInbox({ workspace_id })
                    └── assertOwnsWorkspace(workspace_id) → SQL

  └── POST /api/inbox/:id/accept
        ├── WEB_SESSIONS KV.get(session:...) → workspace_id
        └── WorkspaceDO.acceptInboxItem({ workspace_id, id })
              └── assertOwnsWorkspace(workspace_id) → SQL

Claude Desktop (existing path, unchanged)
  └── mcp-remote → GET /authorize
        └── ENGRAM_IDENTITIES KV.get(sub=clientId) → { workspace_id, user_id }
              └── completeAuthorization({ props: { workspace_id, user_id } })
                    └── EngramMcp session DO → MCP tools
```

## Confidence Assessment

| Area | Confidence | Basis |
|------|------------|-------|
| Separate Worker recommendation | HIGH | Grounded in existing two-Worker isolation rationale + confirmed static assets feature exists (CF docs) |
| Static assets + `run_worker_first` | HIGH | Context7 CF Workers docs, official wrangler.jsonc examples |
| DO binding via `script_name` across Workers | HIGH | Standard CF pattern, docs verified |
| Service bindings Worker-to-Worker RPC | HIGH | Context7 CF docs confirmed |
| ENGRAM_IDENTITIES convergence design | HIGH | Grounded in actual `oauth.ts` source code, `IdentityRecordSchema` inspection |
| Magic-link KV flow | HIGH | Standard KV TTL pattern, well-established |
| Email send to arbitrary addresses | MEDIUM | Cloudflare Email Service (public beta May 2026) supports arbitrary addresses on Workers Paid plan; for v0.3 controlled user set, Email Routing pre-verified destination is a viable free-tier alternative |
| Session cookie security | HIGH | `HttpOnly; Secure; SameSite=Lax` + KV-backed is the standard Workers pattern, confirmed by community examples |
| New DO RPC method shapes | HIGH | Derived directly from existing `WorkspaceDO` method patterns and `inbox`/`blocks` table schema |
| `assertOwnsWorkspace` preservation | HIGH | Confirmed by reading actual DO source; web path sources workspace_id from KV, same guarantee as MCP path |
