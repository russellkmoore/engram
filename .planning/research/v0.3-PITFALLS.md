## 1. Magic-Link Security Pitfalls

The v0.3 magic-link flow is the first unauthenticated entry point added to the Engram Worker. Any bug here can grant workspace access to the wrong principal. The entire identity→workspace mapping that the `kv:bootstrap` script builds carefully is only as safe as this entry point.

### ML-1: Mail scanner pre-fetches the link, consumes the single-use token before the user clicks

- **Feature:** Magic-Link Auth
- **Severity:** catastrophic (user cannot log in; support-invisible because the failure looks like "link expired")
- **Phase:** Auth Worker — first plan that implements the `/auth/magic/verify` endpoint

**What goes wrong:**  
Enterprise mail security gateways (Microsoft Defender for Office 365, Mimecast, Proofpoint, Google Safe Browsing) issue a GET request to every URL in delivered email to scan for malware. For a naive single-use implementation, the gateway GET request arrives before the human clicks, validates the token, marks it consumed, and stores the URL in logs. The human clicks a dead link and sees "expired or already used." This is the single most frequently reported production failure mode for magic-link auth. It is silent because the gateway does not tell the user it pre-fetched the link.

**Warning signs:**  
Users report "link expired immediately." Corporate email users fail at higher rates than personal email users. The token audit log shows a `verified_at` timestamp with a user-agent string matching a known scanner (`msnbot`, `DomainTools`, `GoogleBot`, `Proofpoint Essentials`, `Barracuda`).

**Prevention (choose one; both can be combined for defense-in-depth):**

*Option A — POST-confirmation gate (recommended for Engram):*  
The callback URL (`/auth/magic/verify?token=…`) serves only a minimal HTML page with a single button: "Sign in to Engram." Token consumption happens only on POST submission of that page. A GET to the callback URL by a scanner sees a 200 HTML page, no token consumed. This pattern is the only reliable defense against scanners that issue GET requests. The extra click is acceptable for a security-focused MCP tool. Implementation: on GET, render confirmation HTML; on POST with the token in the body (not the URL), validate and consume the token.

*Option B — Token not in the GET URL, but only in the POST body:*  
Redirect `/auth/magic/verify?token=TOKEN` immediately to a page that stores the token in a `<form hidden input>`, and renders only after a fresh fetch that puts the raw token into an in-memory JS variable. The user clicks "Confirm"; the JS POSTs the token to the API. Scanner GETs only the redirect page (no token in the HTML response body).

**Critical:** Never log the raw token — only its SHA-256 hash. The token IS the credential.

**Sources:** [Magic Link Pitfalls — Evan Todd](https://etodd.io/2026/03/22/magic-link-pitfalls/), [better-auth discussion #6985](https://github.com/better-auth/better-auth/discussions/6985), [Security Boulevard deep-dive](https://securityboulevard.com/2026/05/are-magic-links-secure-a-technical-deep-dive-into-email-based-authentication/)

### ML-2: Token entropy too low or stored in plain text — token is brute-forceable or database-leaked

- **Feature:** Magic-Link Auth
- **Severity:** catastrophic
- **Phase:** Auth Worker — same plan as ML-1

**What goes wrong:**  
A 6-digit numeric token (10^6 combinations) is brute-forceable in seconds against an unauthenticated endpoint with no rate limiting. A 32-byte hex string stored plain in KV means any KV namespace read (developer, billing admin, accidental log line) yields usable tokens. Tokens that don't expire or that can be reused indefinitely compound both risks.

**Warning signs:**  
KV value for a magic-link entry looks like `{ token: "abc123def", ... }`. Token is shorter than 32 bytes. Token TTL not set, or set to >15 minutes.

**Prevention:**  
(1) Generate tokens with `crypto.getRandomValues(new Uint8Array(32))` → base64url-encode → 43-character string (256 bits of entropy — brute-force infeasible). (2) Store **only** `SHA-256(token)` in KV; the raw token appears only in the email link and in Worker memory for the duration of the request. (3) Set TTL to **15 minutes maximum** on the KV entry. (4) On successful verification, delete the KV entry immediately (single-use enforcement). (5) Rate-limit the `/auth/magic/request` endpoint: max 3 requests per email per 5 minutes (prevents magic-link spam flooding a user's inbox). Use a second KV entry keyed by email for this, with 5-minute TTL.

### ML-3: Open redirect on the callback — attacker phishes credentials via manipulated redirect_to

- **Feature:** Magic-Link Auth
- **Severity:** serious
- **Phase:** Auth Worker — same plan as ML-1

**What goes wrong:**  
If the magic-link URL includes a `redirect_to` or `next` parameter (`/auth/magic/verify?token=X&next=https://evil.com`), and the callback Worker redirects to that URL after validation, the attacker can craft a phishing link: email the user `https://engram.../auth/magic/verify?token=REAL_TOKEN&next=https://attacker.com/fake-engram`. User clicks, gets authenticated, then immediately lands on attacker's page. This is a documented magic-link–specific account takeover vector.

**Warning signs:**  
The `next` or `redirect_to` parameter accepts any URL, including external ones. The Worker redirects using `return Response.redirect(url.searchParams.get('next'))` without validation.

**Prevention:**  
(1) Maintain a server-side allowlist of valid post-login destinations. For v0.3, this is exactly one entry: the root of the UI Worker (`https://engram-ui.${WORKER_DOMAIN}`). (2) Use JavaScript's `new URL()` constructor to parse — never use `startsWith()` or string operations. (3) Validate that `new URL(next).origin === ALLOWED_ORIGIN` before redirecting. (4) If no `next` or if validation fails, redirect to the root. (5) Do not put `next` in the email link at all for v0.3 — there is only one valid destination.

### ML-4: Token replay — token is consumed on GET but survives network replay or race

- **Feature:** Magic-Link Auth
- **Severity:** serious
- **Phase:** Auth Worker

**What goes wrong:**  
If the Worker validates the token and sets the session cookie in the same response, and a network replay (or the browser's Back button + reload) replays the GET request with the same token URL, a second valid session might be issued before the KV delete propagates. KV eventual consistency (up to 60 seconds cross-region) means a delete followed by a read from another colo may return the old value, allowing the token to be consumed twice.

This is the same propagation-lag class that Phase 7 dogfooding hit with the bootstrap KV write (documented in ENG-11-DESIGN §0).

**Warning signs:**  
Two sessions exist for the same `sub` with `created_at` within milliseconds. KV audit log shows token key read twice before delete propagation.

**Prevention:**  
(1) Route all token validation requests through a **Durable Object** (a lightweight `MagicLinkDO` or reuse the existing `WorkspaceDO` as a validation coordinator) to guarantee single-execution semantics. The DO SQLite table marks tokens as consumed atomically — no KV propagation lag. (2) If a pure-KV implementation is used instead, use `KV.put` with `ifMatch` metadata for optimistic concurrency, though this is less reliable. (3) Prefer the DO approach: write `{ token_hash, consumed: false, expires_at }` to DO storage, mark `consumed: true` atomically before returning the session cookie. The DO's event loop serializes concurrent requests to the same token. (4) Add an idempotency header (`Idempotency-Key`) to the POST confirmation (ML-1 prevention) so browser double-click cannot issue two POST requests.

### ML-5: Email enumeration — the request endpoint reveals whether an email is registered

- **Feature:** Magic-Link Auth
- **Severity:** annoying → serious (privacy violation for users)
- **Phase:** Auth Worker

**What goes wrong:**  
A naive implementation returns `{ error: "Email not found" }` for unregistered addresses and `{ success: "Link sent" }` for registered ones. An attacker can enumerate which email addresses have Engram accounts by scripting requests to `/auth/magic/request`.

**Warning signs:**  
The response body, status code, or timing differs between registered and unregistered email addresses.

**Prevention:**  
(1) Always return `{ success: "If this email is registered, a link was sent" }` regardless of whether the email exists, and always return the same HTTP status (200). (2) Add a constant-time delay (or use `await new Promise(r => setTimeout(r, 200))`) to prevent timing oracle attacks. (3) For v0.3, Engram has a closed user base — you can return a slightly different message only to users enrolled in `ENGRAM_IDENTITIES` KV, but mask the reason: "Link sent. If you don't receive it within 2 minutes, contact the workspace admin." (4) Rate-limit by source IP regardless.

### ML-6: Magic-link phishing — attacker sends a fake Engram magic-link email to trick users

- **Feature:** Magic-Link Auth
- **Severity:** serious
- **Phase:** Email Infrastructure — must be addressed alongside EM-1

**What goes wrong:**  
An attacker sends a visually identical email claiming to be from Engram with a link to `https://engram-auth.attacker.com/magic?token=FAKE`. The user clicks, enters any data the attacker wants. This is a social-engineering attack amplified by the trust inherent in magic-link emails.

**Warning signs:**  
No DMARC enforcement on the sending domain. Users receive emails claiming to be from Engram from unknown domains.

**Prevention:**  
(1) Implement DMARC with `p=reject` on the sending domain as soon as any email is sent — this prevents spoofing from the legitimate sending domain. (2) Include only a single, clearly branded action in the email body. Do not include a form or request any data. (3) Train user expectations: the only Engram email action is "Click this link to sign in." Nothing else. (4) Display the Worker URL prominently in the email text so users can verify the domain before clicking.

## 2. Email Infrastructure Pitfalls

The v0.3 magic-link flow requires sending transactional email from Cloudflare. This is the first time Engram sends email — and Cloudflare's email story has two distinct products with different capabilities.

### EM-1: Cloudflare Email Routing is INBOUND-ONLY — it cannot send magic-link emails

- **Feature:** Email Infrastructure
- **Severity:** catastrophic (blocks the entire feature if misunderstood)
- **Phase:** Infrastructure planning — must be resolved before Auth Worker is scoped

**What goes wrong:**  
The ENG-11 design document references "CF Email Routing magic links," but Cloudflare Email Routing is an **inbound routing product only**. It receives emails addressed to your domain and routes them to Workers or destination addresses. It cannot send email outbound. A Worker cannot call `EmailRouting.send()` — that API does not exist. Developers who build the auth flow assuming Email Routing handles outbound will discover this only when they try to deploy.

**Warning signs:**  
Searching for "Cloudflare Email Routing send email" in the docs returns the Email Workers API (inbound processing), not a sending API.

**Prevention:**  
Use **Cloudflare Email Service** (separate product, in beta as of June 2026, Workers Paid plan required). This is the product that provides outbound transactional email from Workers via a native `EMAIL` binding — no API keys required, DKIM/SPF managed automatically by Cloudflare. Configuration: add `[[send_email]]` binding in `wrangler.jsonc`. Magic-link email flow: `env.EMAIL.send({ to, from, subject, content })`. **The roadmap must explicitly plan for Email Service Beta access** — confirm it is available on the account before the auth phase begins.

**Key limits (verified June 2026):**

- New accounts start with a conservative daily quota that scales based on reputation
- Recipients: 50 per message (not relevant for magic links)
- Message size: 5 MiB standard
- Free sends to verified destination addresses (does not count toward quota) — useful for Russell/Devon during development
- Domains per zone: 30 combined

**Sources:** [Cloudflare Email Service docs](https://developers.cloudflare.com/email-service/), [Email Routing limits](https://developers.cloudflare.com/email-routing/limits/), [Email for Agents announcement](https://blog.cloudflare.com/email-for-agents/)

---

### EM-2: Email Service is in Beta — quota starts conservative, and initial sends may fail silently

- **Feature:** Email Infrastructure
- **Severity:** serious
- **Phase:** Auth Worker (first plan that sends email in production)

**What goes wrong:**  
Cloudflare Email Service starts new accounts with an undisclosed conservative daily quota. If the quota is hit (e.g., during a demo where you test the flow multiple times), subsequent magic-link requests succeed from the Worker's perspective (`send()` returns no error) but the email is never delivered. The user sees "link sent" and receives nothing. This is especially dangerous if the failure is silent at the API level.

**Warning signs:**  
User reports not receiving magic-link emails after the first few during a session. Worker logs show successful `EMAIL.send()` calls but no email arrives. Cloudflare dashboard shows delivery failures.

**Prevention:**  
(1) Add structured logging to the email send call — log success/failure with the Cloudflare delivery result, not just `try/catch`. (2) In development, send only to verified destination addresses (which don't count toward quota). (3) Before v0.3 launch, submit a Limit Increase Request to Cloudflare. (4) Implement a client-visible "Email sent. Allow 2 minutes before retrying." message with a cooldown that prevents rapid test-clicking from exhausting quota.

---

### EM-3: SPF/DKIM misconfiguration causes magic-link emails to land in spam

- **Feature:** Email Infrastructure
- **Severity:** serious
- **Phase:** Infrastructure planning / Auth Worker

**What goes wrong:**  
Starting July 2025, Cloudflare Email Routing (inbound) requires SPF or DKIM on the sending domain or it refuses to forward messages. For outbound Email Service, Cloudflare manages DKIM automatically — but you must add the Cloudflare-provided DNS records to your domain. If the sending domain is a `workers.dev` subdomain (no DNS control), DKIM cannot be configured and deliverability suffers. For Engram, the sending domain must be a custom domain where DNS records can be added.

**Warning signs:**  
Magic-link emails land in spam. Email headers show `dkim=fail`. Cloudflare dashboard shows DKIM not configured.

**Prevention:**  
(1) Decide on the sending domain before writing any email code. Recommended: `noreply@engram.app` (or whatever custom domain is used) — not a `workers.dev` address. (2) Add Cloudflare's DKIM DNS record to the domain when setting up Email Service. (3) Add DMARC `p=quarantine` initially, upgrade to `p=reject` once the first few deliveries are confirmed. (4) Test deliverability with mail-tester.com before demo. (5) Enforce DMARC is also required per new Cloudflare authentication requirements (July 2025 changelog).

---

### EM-4: Email Routing "reply" path does not work as a magic-link mechanism

- **Feature:** Email Infrastructure
- **Severity:** annoying (design confusion, not a production incident)
- **Phase:** Architecture planning

**What goes wrong:**  
An appealing design would be: user emails `magic@engram.domain.com`, the Email Routing Worker receives it, generates a session token, and replies with a sign-in link. This technically works — Email Routing can receive inbound and the Worker can reply via Email Service — but it creates operational complexity: the user must own an email address that the Engram Worker can validate is actually theirs (no verification step), and routing rules must be live before first use. The simpler and more standard flow is user-provides-email → Worker-sends-link → user-clicks-link.

**Prevention:**  
Use the standard flow: user submits email via `/auth/magic/request` POST, Worker sends email via Email Service. Do not use inbound Email Routing as the trigger for the magic-link flow in v0.3.

## 3. Identity Convergence Pitfalls

The most architecturally important class for v0.3. The KV identity store (`ENGRAM_IDENTITIES`) maps OAuth `sub` → `{ workspace_id, user_id }`. The magic-link flow creates a **web session** that must map to the same record. Any divergence here causes a user to read/write a different workspace than the one Claude Desktop is using, or creates a phantom workspace.

### IC-1: Magic-link session creates a second KV identity record, diverging from the MCP OAuth sub

- **Feature:** Identity Convergence
- **Severity:** catastrophic
- **Phase:** Auth Worker — the identity-convergence design must be locked before any code is written

**What goes wrong:**  
The existing MCP OAuth path issues a JWT whose `sub` claim is the Cloudflare OAuth subject (e.g., `oauth2|<hash>`). The `kv:bootstrap` script maps that `sub` to `{ workspace_id: "russell-personal", user_id: "russell" }`. If the magic-link auth flow creates its own identity record keyed by **email** (e.g., `identity:russell@example.com` → `{ workspace_id: "russell-personal-web", ... }`), there are now two identity records with two different workspace IDs for the same human. The web UI reads workspace A; Claude Desktop reads workspace B. No data is shared between them.

This is the v0.3 equivalent of the OAuth sub/account collision documented in OAuth identity linking literature: "Without proper linking, users signing in through different methods risk creating duplicate accounts."

**Warning signs:**  
Two distinct KV keys for the same user's email and OAuth sub. The UI shows an empty inbox/memory browser while Claude Desktop has populated data. A new workspace ID appears in the DO namespace that was never bootstrapped.

**Prevention:**  
(1) The magic-link flow must **never create a new workspace** — it must **look up or create an identity record that points to an existing workspace**. The lookup key should be the verified email address, not the magic-link token. (2) The canonical flow: User requests magic link → Worker sends link → User clicks → Worker verifies token → Worker looks up `identity:email:russell@example.com` in `ENGRAM_IDENTITIES` → if found, issue web session pointing to that workspace_id → if NOT found (first-time web user), walk user through workspace creation and write `identity:email:...` pointing to the newly created workspace. (3) The MCP OAuth path and the web auth path must use the **same workspace_id** for the same human. Enforce by: (a) allowing the web auth to link to an existing OAuth sub via an "I already connected Claude Desktop" flow, or (b) requiring the magic-link flow to write a new KV record with the same workspace_id as the OAuth path, validated by email match. (4) Add a CI test: bootstrap via `kv:bootstrap` with sub X and email Y; sign in via magic link with email Y; assert web session returns workspace_id matching sub X's workspace_id.

### IC-2: KV propagation lag causes "identity not found" on the first web request after magic-link verification

- **Feature:** Identity Convergence
- **Severity:** serious
- **Phase:** Auth Worker

**What goes wrong:**  
Phase 7 dogfooding documented exactly this failure: KV propagation can take up to 60 seconds across regions. If the magic-link verification Worker writes the session/identity record to KV, and the next request (the UI's first API call, which validates the session) hits a different Cloudflare edge colo, it reads from a stale KV replica that doesn't yet have the new record. The UI call fails with "session not found" or "workspace not found" even though sign-in appeared to succeed.

**Warning signs:**  
User signs in successfully (magic-link page shows "Success"), but the inbox/memory browser page shows a 401 or "no workspace found" immediately after. Retrying a few seconds later works.

**Prevention:**  
(1) **Do not use KV for session storage** — use a Durable Object or a signed JWT cookie instead. The JWT cookie approach: on verification, issue a signed JWT (using `crypto.subtle` + a KV-stored or Worker-secret signing key) as an `HttpOnly Secure SameSite=Lax` cookie. The JWT contains `{ workspace_id, user_id, email, exp }` and is verified by the Worker on each request without a KV lookup. This eliminates the propagation-lag class entirely for session reads. (2) If KV is used for sessions, implement a retry loop in the UI: on 401, wait 2 seconds, retry once, then show "sign-in failed" with a "try again" button. (3) The `kv:bootstrap` script already handles this with a polling loop (from ENG-11 §1); apply the same pattern here. (4) KV is appropriate for the identity mapping (it's write-once, read-many, eventually consistent is acceptable once propagated); KV is inappropriate for per-request session validation.

### IC-3: Web session can read/write another user's workspace if workspace_id validation is missing in the UI Worker

- **Feature:** Identity Convergence / Write-Path
- **Severity:** catastrophic
- **Phase:** UI API Worker — every route that proxies to WorkspaceDO

**What goes wrong:**  
The existing `assertOwnsWorkspace()` check in WorkspaceDO is the first line of every DO RPC — this is the security invariant. But the UI introduces a new request path: Browser → UI Worker → WorkspaceDO. If the UI Worker constructs the `workspace_id` from a URL parameter (`GET /workspace/:workspace_id/inbox`) and passes it directly to the DO stub without validating it against the session's `workspace_id`, any authenticated user can append any workspace_id to the URL and read another user's inbox.

This is a horizontal privilege escalation — the attacker has a valid session, just for workspace A, and accesses workspace B.

**Warning signs:**  
The UI API route handler calls `env.WORKSPACE.get(env.WORKSPACE.idFromName(params.workspace_id)).fetch(...)` where `params.workspace_id` comes from the URL path without a check against `session.workspace_id`.

**Prevention:**  
(1) The UI Worker must validate `params.workspace_id === session.workspace_id` on **every proxied request** before constructing the DO stub. This is a second ownership check in addition to `assertOwnsWorkspace()`. (2) Do not expose `workspace_id` in URL paths at all — derive it from the session cookie exclusively. The inbox URL should be `/inbox`, not `/workspace/russell-personal/inbox`. (3) Add a test: create two sessions for two workspace IDs; assert that session A cannot access workspace B's inbox via any URL manipulation.

### IC-4: Race between web signup and OAuth bootstrap creates a window where both write the same workspace_id

- **Feature:** Identity Convergence
- **Severity:** serious
- **Phase:** Auth Worker

**What goes wrong:**  
If a new user simultaneously connects Claude Desktop (which triggers the OAuth bootstrap path) and uses the web magic-link sign-up, two concurrent writes may race to create the workspace. The OAuth path calls `kv:bootstrap` with `workspace_id=X`; the web path creates `workspace_id=X` from the same email but writes a different DO instance because `idFromName()` is called separately in each path. In the worst case, both paths succeed but they write to different DOs because of a timing window in the KV write.

**Warning signs:**  
Two DO instances exist for the same `workspace_id` string. The `ENGRAM_IDENTITIES` KV has two keys pointing to the same workspace_id written within seconds of each other.

**Prevention:**  
(1) Use `idFromName(workspace_id)` consistently and atomically — the same string always produces the same DO ID. This is actually safe in Cloudflare's implementation; two calls to `idFromName("russell-personal")` always return the same DO ID. The race does not create two DOs. (2) The real race is the KV write: use a Durable Object as a workspace-creation lock. The workspace-creation request (whether from web or OAuth bootstrap) goes through the WorkspaceDO constructor — if the DO already has data, it is not a new workspace, and the second caller gets the existing workspace. (3) Make the workspace creation idempotent: if `ENGRAM_IDENTITIES:email:X` already exists, return it rather than creating a new entry. Use a `putIfAbsent` pattern via a Durable Object lock rather than a raw KV put.

### IC-5: Web session cookie shared across workers.dev subdomains, leaking session to other Workers

- **Feature:** Identity Convergence
- **Severity:** serious
- **Phase:** Auth Worker / Infrastructure

**What goes wrong:**  
All Workers on `workers.dev` share the `*.workers.dev` domain. If the session cookie is set with `Domain=.workers.dev` or without the `__Host-` prefix, another Worker on the same workers.dev account (Russell's dev tools, a test Worker, etc.) can read the Engram session cookie. This is the subdomain cookie-tossing attack.

**Warning signs:**  
Session cookie set as `engram-session=...; Domain=workers.dev` or `engram-session=...; Domain=.russellkmoore.workers.dev`. No `__Host-` prefix on the cookie name.

**Prevention:**  
(1) Name the session cookie `__Host-engram-session` — the `__Host-` prefix forces the browser to enforce `Secure; Path=/; no Domain attribute`, preventing any cross-subdomain leak. (2) Alternatively (and recommended for production), deploy the UI Worker on a custom domain (`app.engram.app`) so the cookie domain is not workers.dev. `__Host-` prefix is still recommended as defense-in-depth. (3) Set `SameSite=Strict` to prevent the cookie from being sent on cross-site navigations. For v0.3 with a single custom domain, this is fine — users navigate directly to the Engram UI.

## 4. Write-Path Pitfalls

The inbox UI is the first thing in Engram that lets a human mutate the DO's `inbox` and `conflicts` tables. The MCP path already writes, but through a validated token. The UI write path is new and must be hardened separately.

### WP-1: CSRF — attacker tricks user into accepting/dismissing inbox items via a cross-site form

- **Feature:** Write-Path
- **Severity:** serious
- **Phase:** Inbox UI implementation plan

**What goes wrong:**  
The inbox UI exposes `POST /inbox/:id/accept` and `POST /inbox/:id/dismiss` endpoints. If those endpoints are protected only by a session cookie (no CSRF token), an attacker can embed a `<form action="https://engram.app/inbox/ITEM_ID/accept" method="POST">` on a third-party site. If the user is logged into Engram and visits that page, the browser sends the session cookie automatically, and Engram mutates data without the user's intent.

**Warning signs:**  
The endpoint handler checks the session cookie but does not check a CSRF token or Origin header. The action endpoints accept POST from any origin.

**Prevention:**  
(1) For API endpoints (JSON request/response), validate the `Origin` or `Referer` header against the known UI origin. `Origin` is not spoofable by JS in a browser. (2) For form-based endpoints, require a CSRF token stored in the session JWT and echoed in a hidden form field. Use the double-submit cookie pattern: `__Host-CSRF=<token>; SameSite=Strict` cookie + same token in the POST body. (3) Set `SameSite=Strict` on the session cookie as above — this is sufficient CSRF protection for same-site navigations on a custom domain, but defense-in-depth is still recommended. (4) Cloudflare's own guidance: CSRF token cookie pattern `__Host-CSRF_TOKEN={token}; HttpOnly; Secure; Path=/; SameSite=Lax; Max-Age=600`. The `__Host-` prefix prevents subdomain attacks.

---

### WP-2: Double-accept / double-resolve — idempotency absent, clicking "accept" twice creates a duplicate block

- **Feature:** Write-Path
- **Severity:** annoying → serious (data integrity)
- **Phase:** Inbox UI implementation plan

**What goes wrong:**  
If the inbox "Accept" button triggers a POST that removes the item from `inbox` and writes to `blocks`, and the user double-clicks or the network retries the request, the `blocks` table can get a duplicate entry. The same conflict suggestion is accepted twice, creating two identical memory blocks and confusing later recall queries.

**Warning signs:**  
The `accept` endpoint does `INSERT INTO blocks ... ; DELETE FROM inbox WHERE id = ?` without checking whether the block already exists. The `blocks` table can contain multiple rows with the same content.

**Prevention:**  
(1) The `accept` DO RPC must be idempotent: `INSERT INTO blocks (id, ...) VALUES (?, ...) ON CONFLICT(id) DO NOTHING; DELETE FROM inbox WHERE id = ?`. Use the inbox item's `id` as the block's `id` to make idempotency automatic. (2) Return a 200 even if the block already exists (idempotent consumer pattern). (3) In the UI, disable the "Accept" button and show a spinner immediately on first click — prevent the double-click at the UI layer, but do not rely on this alone. (4) Add an `inbox_item_state` column (`pending | processing | accepted | dismissed`) and use a `WHERE state = 'pending'` guard in the UPDATE/INSERT transaction.

---

### WP-3: Missing workspace-ownership check on web writes — bypasses assertOwnsWorkspace

- **Feature:** Write-Path / Identity Convergence
- **Severity:** catastrophic
- **Phase:** Inbox UI implementation plan — must be explicit in the phase checklist

**What goes wrong:**  
The existing `assertOwnsWorkspace()` in WorkspaceDO is called at the top of every DO RPC method — it checks that the requesting worker's `workspace_id` binding matches the DO's own `workspace_id`. For the MCP path, the Worker validates the JWT and constructs the DO stub with the correct workspace_id from the token. But if the UI Worker proxies inbox write requests and constructs the DO stub using a `workspace_id` derived from the URL (not the session), `assertOwnsWorkspace()` is NOT bypassed (the DO still enforces it), but the DO's `workspace_id` argument comes from the Worker-controlled call, which is also tainted. The attack surface is in the UI Worker itself, before the DO call.

This is a layered check: the DO enforces its own ownership, but the UI Worker must not pass a wrong workspace_id to the DO stub in the first place.

**Warning signs:**  
A UI Worker route handler like:

```typescript
const workspaceId = c.req.param('workspace_id'); // from URL path — DANGER
const stub = env.WORKSPACE.get(env.WORKSPACE.idFromName(workspaceId));
await stub.acceptInboxItem(itemId);
```

**Prevention:**  
(1) Derive `workspace_id` exclusively from the validated session JWT — never from the URL path, query parameters, or request body for write operations. (2) In every UI Worker route handler that proxies to WorkspaceDO, the first three lines must be: (a) validate session cookie and extract JWT claims, (b) extract `workspace_id` from claims, (c) construct DO stub from that `workspace_id`. (3) Write a test that sends a valid session for workspace A + a `workspace_id` override pointing to workspace B in the URL, and asserts a 403 response.

---

### WP-4: Optimistic UI desync — inbox item shows as accepted in the UI but DO transaction failed

- **Feature:** Write-Path
- **Severity:** annoying
- **Phase:** Inbox UI implementation plan

**What goes wrong:**  
The UI removes an inbox item from the list before the API call confirms success (optimistic update). If the DO write fails (e.g., SQLite constraint violation, network timeout, DO cold-start during the write), the UI and the backend are out of sync. The item appears gone in the UI but is still in the `inbox` table. On next page load, it reappears, confusing the user.

**Warning signs:**  
UI performs `state.items = state.items.filter(i => i.id !== itemId)` before `await fetch('/inbox/accept', ...)` resolves.

**Prevention:**  
For v0.3 (inbox is a low-traffic, single-user management surface), use **pessimistic updates**: disable the button, await the API call, then update the list on success. The extra ~200ms round-trip is invisible on a management screen. Reserve optimistic updates for high-frequency surfaces (messaging, note-taking) where the latency is visible and user-tolerance is low. The inbox is not that surface.

---

### WP-5: Conflict resolution write wakes all related memories — unexpected DO fan-out

- **Feature:** Write-Path
- **Severity:** serious
- **Phase:** Inbox UI implementation plan

**What goes wrong:**  
When the user resolves a conflict (accepting one version, dismissing the other) via the inbox UI, the WorkspaceDO `resolveConflict()` method may need to update the `conflicts` table, optionally delete a block, and possibly queue a re-embedding for the winning block. If this is done synchronously in the HTTP handler, and the re-embedding path triggers a Vectorize call inside the DO, the DO is blocked for 1-3 seconds (blocking MCP traffic). If the conflict resolution triggers cascading updates to related blocks, the DO can be blocked for the duration of the fan-out.

**Warning signs:**  
`resolveConflict()` calls `env.VECTORIZE.upsert()` or `env.AI.run()` inline, inside the DO handler. MCP `recall()` latency spikes when conflicts are being resolved via the UI.

**Prevention:**  
(1) Conflict resolution via the UI must follow the same progressive-enrichment pattern as triage: the DO handler does the minimal SQLite mutation (update `conflicts.resolved_at`, delete losing block) and returns immediately. (2) If re-embedding is needed (the winning block's embedding may be stale if the conflict modified the content), enqueue a `MemoryEvent` to the triage queue — let the Triage Worker handle the re-embedding asynchronously. (3) Never call `env.AI.run()` or `env.VECTORIZE.upsert()` inside a WorkspaceDO handler that is on the MCP hot path. This is an existing architecture invariant; the UI must honor it.

## 5. Durable Object + UI Pitfalls

The UI adds a new request pattern: browser → UI Worker → WorkspaceDO. This path differs from the MCP path in access frequency (page loads, list views, pagination) and in whether the DO is likely to be warm.

### DU-1: Chatty per-row DO calls from an inbox list view — hits DO throughput ceiling

- **Feature:** DO + UI
- **Severity:** serious
- **Phase:** Inbox UI implementation plan

**What goes wrong:**  
If the inbox UI renders a list of items and each item fires a separate RPC call to the DO to get details (e.g., `GET /inbox/:id` per row × 25 rows = 25 concurrent DO calls), the DO processes them serially at ~200-500 req/sec for simple operations and ~50-200 req/sec for SQLite queries. 25 serial SQLite reads at 5ms each = 125ms just for reading — and this is the WorkspaceDO shared with all MCP traffic. The Cloudflare "Rules of Durable Objects" documentation (December 2025) explicitly warns: "the throughput limit is approximately 500-1,000 requests per second for simple operations, dropping to 200-500 req/sec for complex operations."

**Warning signs:**  
Network tab shows 20+ XHR calls fired simultaneously on inbox page load. WorkspaceDO request queue depth increases during UI sessions. MCP `recall()` latency spikes during inbox page loads.

**Prevention:**  
(1) Implement a `listInbox(limit, cursor)` DO RPC method that returns a page of inbox items in a **single** SQL query with `LIMIT` and `OFFSET`. One DO call for the whole page. (2) Similarly, `listConflicts(limit, cursor)` and `listBlocks(query, limit, cursor)` should be single-call methods. (3) Do not implement per-row individual fetch in the UI — all data for a page comes in one batched call. (4) Add a `MAX_PAGE_SIZE=50` constant to prevent accidental O(N) page loads.

---

### DU-2: Cold-start latency on first web page load — 1-3 second blank screen for a hibernated WorkspaceDO

- **Feature:** DO + UI
- **Severity:** annoying → serious (first impression)
- **Phase:** UI Worker implementation plan

**What goes wrong:**  
The WorkspaceDO hibernates after 10 seconds of inactivity. If Russell hasn't used Engram (MCP or UI) for a while and loads the inbox, the first DO call triggers the constructor, which runs `blockConcurrencyWhile()` for schema migrations, then runs the SQLite query. From the browser's perspective, this is a 1-3 second white screen for the first load. The official Cloudflare lifecycle doc confirms: "the constructor will run again" on wake from hibernation.

**Warning signs:**  
Network tab shows the first API call taking 2-5s. Subsequent calls take 50-200ms.

**Prevention:**  
(1) Add a lightweight `ping()` RPC method to WorkspaceDO that just returns `{ ok: true }`. The UI Worker calls `stub.ping()` as the first thing on page load, pre-warming the DO while the UI renders the shell. (2) Alternatively, add a "pre-warm on Worker startup" hook in the UI Worker's `fetch()` handler that fires a background `stub.ping()` using `ctx.waitUntil()`. (3) Show a skeleton loader (content placeholder) rather than a blank screen during the cold-start window. (4) For the MCP path, this is already mitigated by regular Claude Desktop use keeping the DO warm. The UI path needs explicit handling for infrequent access.

---

### DU-3: UI Worker shares CPU time with MCP Worker — hot MCP path blocked by UI list views

- **Feature:** DO + UI
- **Severity:** serious
- **Phase:** Infrastructure architecture decision (must be locked before any UI Worker code is written)

**What goes wrong:**  
If the inbox UI, memory browser, and admin dashboard are served by the **same Worker** as the MCP server (`engram-mcp-server`), a slow inbox list query or analytics dashboard refresh holds the Worker's CPU budget and increases latency for Claude Desktop's `recall()` and `remember()` calls. Cloudflare Workers share CPU time per isolate. A 200ms list query + 200ms rendering pipeline in the UI path competes directly with the MCP path.

This is not hypothetical — the existing architecture note in `CLAUDE.md` states the MCP server should remain a thin router. Adding HTML rendering and pagination to the same Worker contradicts that principle.

**Warning signs:**  
UI and MCP endpoints are defined in the same `packages/mcp-server/src/index.ts`. The Worker handles both `GET /inbox` (HTML page or list JSON) and `POST /mcp` in the same request handler.

**Prevention:**  
Deploy the UI as a **separate Worker** (`engram-ui-worker`). This is the correct architectural choice: (a) separate deployability, (b) separate CPU budgets, (c) mcp-server stays a thin router as designed. The UI Worker can import shared types from `shared/types` but should never import from `packages/mcp-server`. The two Workers communicate via DO stubs targeting the same `WorkspaceDO` instances — they share data through the DO, not through Worker-to-Worker calls. This architecture decision must be in the first UI infrastructure plan.

---

### DU-4: Memory browser makes an unbounded query to WorkspaceDO — returns O(N) rows

- **Feature:** DO + UI
- **Severity:** serious
- **Phase:** Memory browser implementation plan

**What goes wrong:**  
The memory browser's search/filter view calls a `searchBlocks(query, filters)` DO RPC with no pagination. For Russell's current ~500 blocks × ~5 chunks/block = ~2,500 rows, this is manageable. But at v0.4 with team memory and connectors ingesting Slack/Drive, the blocks table may have 50,000+ rows. An unbounded `SELECT * FROM blocks WHERE content LIKE ?` returns 50K rows in a single DO call, saturates the DO's memory, and returns a 10MB+ JSON payload to the browser. The DO's SQLite query limit and Workers' 128MB memory limit will surface before then.

**Warning signs:**  
`searchBlocks()` DO RPC runs `SELECT * FROM blocks` or a filtered variant without `LIMIT`. Response payload > 500KB for a list view.

**Prevention:**  
(1) All `searchBlocks` / `listBlocks` DO RPCs must include `LIMIT` and cursor-based pagination from day one. No exceptions. (2) Default page size: 25 items. Max: 100. (3) For the memory browser, Vectorize-backed semantic search (`recall()`) is the right underlying primitive — not a raw SQLite `LIKE` query. The UI's "search" box should call the `recall()` MCP logic through a UI-accessible API, not a raw DO method. (4) The memory browser is the highest-risk page for unbounded queries — add a test that asserts the `listBlocks` RPC always includes a `LIMIT` clause.

---

### DU-5: Admin eval-budget dashboard issues N Analytics Engine queries per page refresh

- **Feature:** DO + UI / Analytics
- **Severity:** annoying → serious (potential cost accumulation)
- **Phase:** Admin dashboard implementation plan

**What goes wrong:**  
The `eval-budget-summary.mjs` script issues a fixed set of SQL queries against the Analytics Engine SQL API. If the admin dashboard UI re-runs those queries on every page load (or worse, polls every 30 seconds), and each query counts as one billable read, the dashboard itself becomes a non-trivial cost center. Analytics Engine billing is based on "read queries" and the free tier is limited.

**Warning signs:**  
Dashboard component fires 5+ `fetch()` calls to the Analytics Engine SQL API on mount, with no caching.

**Prevention:**  
(1) Cache Analytics Engine query results in KV with a 5-minute TTL. The dashboard displays slightly stale data, which is acceptable for an eval-budget view. (2) Implement the dashboard as a server-side rendered Worker response, not a client-side SPA fetch — so the KV cache is consulted once per page load, not once per client component mount. (3) Keep the query count low: one query per metric tile, not one per data point. For an eval-budget dashboard, 3-5 queries total is the ceiling.

## 6. SPA / Static Assets Pitfalls

The v0.3 UI is the first browser-delivered surface in the project. Cloudflare's static-asset + SPA routing system has several non-obvious behaviors.

### SA-1: SPA routing fallback intercepts OAuth callback navigation request — Worker code never runs

- **Feature:** SPA / Static Assets
- **Severity:** catastrophic
- **Phase:** UI Worker implementation plan (routing architecture must be set up correctly from day one)

**What goes wrong:**  
When `assets.not_found_handling = "single-page-application"` is configured, Cloudflare intercepts navigation requests (those with `Sec-Fetch-Mode: navigate`) and serves `index.html` with a 200 — before the Worker script runs. This is correct for client-side routes like `/inbox` and `/memory`. But it is wrong for the OAuth/magic-link callback: if the user clicks the magic-link and their browser navigates to `/auth/magic/verify?token=…`, the SPA fallback intercepts it, serves `index.html`, and the callback token is never validated by the Worker. The official Cloudflare docs note: "navigation requests bypass your Worker script, which breaks traditional OAuth callback patterns expecting query parameters."

**Warning signs:**  
After clicking the magic link, the user lands on a blank app shell or the home screen instead of being signed in.

**Prevention:**  
(1) Use `run_worker_first: ["/auth/*"]` in `wrangler.jsonc` to ensure the Auth Worker (or the UI Worker's auth routes) runs before asset serving for all `/auth/` paths. This overrides the SPA navigation bypass for those routes. (2) Alternatively, handle the callback client-side: the `index.html` shell reads the `?token=` parameter from the URL, POSTs it to the API via `fetch`, and handles the session. This works but is more complex. (3) The cleanest architecture: the Auth Worker is a separate Worker (not the UI Worker) deployed at `/auth/*`, and `run_worker_first` ensures it runs before the SPA fallback. Routes: `/auth/magic/request`, `/auth/magic/verify`, `/auth/logout` → Auth Worker. Everything else → SPA.

---

### SA-2: Secret leakage into the client bundle via Vite VITE_* prefix convention

- **Feature:** SPA / Static Assets
- **Severity:** serious
- **Phase:** UI Worker implementation plan

**What goes wrong:**  
Vite's convention is that `VITE_*` environment variables are injected into the client bundle at build time. Any secret inadvertently prefixed with `VITE_` (e.g., `VITE_AUTH_SECRET`, `VITE_KV_NAMESPACE_ID`) is included in the compiled JavaScript bundle and visible to any user who inspects the network tab. This is compounded by CVE-2025-59427 (Cloudflare Vite plugin, versions < 1.6.0): the dev server exposed `.dev.vars` and `.env` files over HTTP when `--host 0.0.0.0` was used. Even with the patch, the `VITE_*` design remains a footgun.

**Warning signs:**  
`VITE_` prefixed variables in `.env` or `wrangler.jsonc`. Cloudflare Vite plugin version < 1.6.0. The client bundle contains plaintext secrets when inspected with browser dev tools.

**Prevention:**  
(1) Ensure Cloudflare Vite plugin is ≥ 1.6.0 (patched for CVE-2025-59427). (2) Never prefix secrets with `VITE_` — only prefix values intended for the browser (e.g., `VITE_API_URL`, `VITE_APP_NAME`). (3) All secrets (signing keys, KV namespace credentials, Analytics Engine tokens) stay in Worker-side `env` bindings, never in Vite build-time env. (4) Add a build step that scans the compiled JS bundle for known secret patterns (UUID-format tokens, 64-char hex strings) as a pre-deploy CI gate.

---

### SA-3: Cache-busting absent — users run stale UI after a Worker deployment

- **Feature:** SPA / Static Assets
- **Severity:** annoying
- **Phase:** UI Worker implementation plan

**What goes wrong:**  
Cloudflare's Workers static assets have a default cache TTL. If the UI is deployed with a bug fix but users have a cached version of `main.js`, they continue running the old (broken) UI. This is a standard asset-caching problem, amplified by Cloudflare's edge CDN caching the static assets aggressively.

**Warning signs:**  
Users report seeing the old UI after a deployment. Network tab shows `Cache-Control: public, max-age=86400` on JS bundles without content hashes.

**Prevention:**  
(1) Use content-hashed filenames for all JS/CSS assets (Vite does this by default: `main-[hash].js`). The `index.html` is not cached aggressively (or is served with `Cache-Control: no-cache, must-revalidate`) and always points to the latest hashed bundles. (2) Configure Workers static assets with `Cache-Control: public, max-age=31536000, immutable` for hashed assets and `Cache-Control: no-cache` for `index.html`. (3) In `wrangler.jsonc`, set `assets.html_handling = "none"` or configure appropriate cache headers.

---

### SA-4: CORS between UI Worker and MCP Worker — cookie-bearing cross-origin requests fail

- **Feature:** SPA / Static Assets
- **Severity:** serious
- **Phase:** UI Worker implementation plan

**What goes wrong:**  
If the UI is served from `app.engram.app` (UI Worker) and the inbox/memory API is on `engram-mcp-server.russellkmoore.workers.dev` (MCP Worker), the UI's `fetch()` calls are cross-origin. Browsers block cross-origin requests that include cookies unless the server responds with both `Access-Control-Allow-Origin: <exact-origin>` (not `*` with credentials) and `Access-Control-Allow-Credentials: true`. If the UI Worker tries to send the `__Host-engram-session` cookie to the MCP Worker's API, the browser may refuse.

**Warning signs:**  
Browser console shows `CORS error: The request with credentials requires 'Access-Control-Allow-Origin' to not be a wildcard.` Session cookie not sent on API calls from the UI.

**Prevention:**  
(1) Architecture decision: the UI Worker should proxy to WorkspaceDO directly (not through the MCP Worker). Both Workers share `WorkspaceDO` stubs — the UI Worker gets its own binding to the same DO class. This avoids cross-Worker calls entirely. (2) If a shared API layer is needed (e.g., for the recall-powered memory browser search), route those calls through the UI Worker's own service bindings to WorkspaceDO, not through the MCP Worker's HTTP interface. (3) Never use `*` with `credentials: "include"`. Always set `Access-Control-Allow-Origin` to the exact UI origin.

---

### SA-5: run_worker_first routing conflict — API paths are also valid SPA client routes

- **Feature:** SPA / Static Assets
- **Severity:** annoying
- **Phase:** UI Worker implementation plan

**What goes wrong:**  
When `run_worker_first: true` is set globally (instead of pattern-limited like `["/api/*"]`), ALL requests hit the Worker first, including SPA client-side routes like `/inbox` and `/memory`. The Hono router in the Worker must then have a catch-all `app.get('*', c => c.env.ASSETS.fetch(c.req.raw))` to fall through to static assets for those routes — if that catch-all is missing or misconfigured, SPA routes return 404. Cloudflare's documentation explicitly requires this catch-all when using `run_worker_first: true`.

**Warning signs:**  
`/inbox` returns 404 after deploying with `run_worker_first: true`. Network tab shows a Worker response (no `Cache-Control` from CDN) for static asset paths.

**Prevention:**  
(1) Prefer `run_worker_first: ["/api/*", "/auth/*"]` (pattern-limited) over `run_worker_first: true` (global). This runs the Worker for API and auth paths, lets static-asset serving handle SPA routes without the catch-all footgun. (2) If global `run_worker_first` is used, add the catch-all in the Hono router as the final route and add a test that confirms `GET /inbox` returns the SPA `index.html` (200, text/html, content includes the Vite app entry point).

## 7. Analytics Engine Dashboard Pitfalls

The admin eval-budget dashboard is a translation of `eval-budget-summary.mjs` into a live browser view over the Analytics Engine SQL API.

### AD-1: Sampling corrupts budget totals — SUM(double1) reports wrong spend

- **Feature:** Analytics Dashboard
- **Severity:** serious (incorrect budget numbers mislead investment decisions)
- **Phase:** Admin dashboard implementation plan

**What goes wrong:**  
At high write volumes, Analytics Engine automatically downsamples data. The `_sample_interval` column indicates how many actual events each sampled row represents. A naive `SUM(double1)` query underreports actual spend because it sums only the sampled rows, not the full population. For an eval-budget dashboard showing "AI tokens consumed this week," this produces numbers that are 2-10× lower than actual spend.

**Warning signs:**  
`SELECT SUM(double1) FROM ...` used without `_sample_interval` adjustment. Budget numbers seem plausible but consistently underestimate observed Cloudflare bill charges.

**Prevention:**  
(1) All aggregation queries against Analytics Engine must use `SUM(_sample_interval * double1)` for sums and `SUM(_sample_interval * double1) / SUM(_sample_interval)` for averages. The existing `eval-budget-summary.mjs` should be audited for this before the dashboard is built. (2) Include a "data quality" indicator in the dashboard that shows the maximum `_sample_interval` value for the current query window — if it exceeds 1, the displayed numbers are estimates. (3) This is only relevant at high event write rates. For Russell's current single-workspace usage, sampling is unlikely, but it must be coded correctly from day one.

---

### AD-2: Timezone handling — toStartOfInterval bucketing uses UTC, dashboard shows wrong day boundaries for local time

- **Feature:** Analytics Dashboard
- **Severity:** annoying
- **Phase:** Admin dashboard implementation plan

**What goes wrong:**  
`toStartOfDay(timestamp)` and `toStartOfInterval(timestamp, toIntervalHour(1))` in the Analytics Engine SQL API operate in UTC by default. If Russell is in Pacific Time (UTC-7), a "today's spend" query bucketed by UTC day rolls over at 5pm local time — yesterday's evening events appear in today's bucket. The `eval-budget-summary.mjs` script may not surface this because it runs infrequently; a live dashboard makes it obvious.

**Warning signs:**  
Dashboard's "today" chart shows activity from the previous afternoon mixed with this morning's events. Time-bucketed bars don't align with local time.

**Prevention:**  
(1) Pass timezone explicitly to all Analytics Engine time functions: `toStartOfDay(timestamp, 'America/Los_Angeles')`. (2) For a general-purpose dashboard, derive the timezone from the user's browser and pass it as a query parameter to the API Worker, which injects it into the SQL. (3) Alternatively, display all charts in UTC and label them as UTC explicitly — a single-user engineering dashboard where UTC is expected is more honest than silently converting.

---

### AD-3: 90-day data retention cliff — budget history longer than 3 months silently disappears

- **Feature:** Analytics Dashboard
- **Severity:** annoying
- **Phase:** Admin dashboard implementation plan

**What goes wrong:**  
Analytics Engine retains data for 90 days. A query like `WHERE timestamp > NOW() - INTERVAL '6 months'` silently returns data only for the last 90 days without error — there is no indication that older data is absent. The dashboard shows a partial history, which may be misinterpreted as "low spend in those months" rather than "no data."

**Warning signs:**  
Dashboard queries do not limit their time range. The default "all time" view appears to show correct data but silently truncates at 90 days.

**Prevention:**  
(1) Cap dashboard queries at `WHERE timestamp > NOW() - INTERVAL '90 days'` explicitly and label the dashboard "Last 90 days (Analytics Engine retention limit)." (2) For long-term budget tracking, export monthly summaries to R2 (or a simple KV key with `{ month: "2026-04", total_neurons: N }`) as a scheduled Cron Worker. The dashboard reads KV for historical months and Analytics Engine for the current month.

---

### AD-4: Analytics Engine SQL API requires a bearer token — exposing it to the browser leaks account-level analytics access

- **Feature:** Analytics Dashboard
- **Severity:** serious
- **Phase:** Admin dashboard implementation plan

**What goes wrong:**  
The Analytics Engine SQL API is queried via HTTP with a Cloudflare API token (`Authorization: Bearer <TOKEN>`). If the admin dashboard is a client-side SPA that calls the Analytics Engine SQL API directly from the browser (issuing `fetch('https://api.cloudflare.com/client/v4/accounts/.../analytics_engine/sql', { headers: { Authorization: 'Bearer ...' } })`), the token is exposed to any user who opens the browser's network tab. That token has read access to all analytics data on the account — potentially exposing information about other Workers or properties.

**Warning signs:**  
The dashboard's JS bundle contains the Analytics Engine API token. Network tab shows calls to `api.cloudflare.com` from the browser.

**Prevention:**  
(1) The admin dashboard must be **server-side proxied**: the UI Worker forwards analytics requests to a dedicated admin API endpoint in the same Worker (or the UI Worker itself), which holds the API token as a Worker secret (`wrangler secret put AE_API_TOKEN`). (2) The browser never sees the Cloudflare API token. (3) The admin API endpoints should be access-controlled by the session cookie (only the workspace owner can view their analytics). (4) This is the same pattern as `eval-budget-summary.mjs` — it runs server-side for a reason.

## 8. Scope Creep Pitfalls

v0.3 is explicitly "wide scope" — four surfaces in one milestone. This section documents the patterns that reliably blow up timelines for exactly this milestone shape.

### SC-1: Auth surface grows — "just add password reset" / "add team invites" during the auth phase

- **Feature:** Scope Creep
- **Severity:** serious (timeline)
- **Phase:** Auth Worker planning

**What goes wrong:**  
Once the magic-link auth surface exists, every auth-adjacent feature request is "just add it here" — password recovery, email change, team member invitations, OAuth provider linking. Each is a separate security surface with its own pitfall class. For v0.3, the auth surface must be limited to: (a) magic-link sign-in for existing single-user workspace owner (Russell), (b) extending to one additional user (Devon) via the same flow. No team management, no SSO, no email change.

**Warning signs:**  
REQUIREMENTS.md or a PLAN.md for the auth phase includes any of: "invite team member," "add Google OAuth," "change email," "forgot password" (magic links ARE the password recovery — there is no separate flow needed).

**Prevention:**  
(1) Scope the auth phase to: `POST /auth/magic/request` + `GET /auth/magic/verify` + session cookie issuance. That is the entire surface for v0.3. (2) Devon's onboarding = Russell runs the `kv:bootstrap` equivalent manually for Devon's email, or the magic-link request page doubles as the first-run registration page (if no identity record exists, the magic-link flow prompts for workspace creation). (3) Document explicitly in the auth phase CONTEXT.md: "Team invites, OAuth provider linking, and email management are v0.4 or v1.0 scope."

---

### SC-2: Memory browser becomes a full-featured memory editor — CRUD surfaces added during browsing phase

- **Feature:** Scope Creep
- **Severity:** serious (timeline)
- **Phase:** Memory browser implementation plan

**What goes wrong:**  
The memory browser is specified as read-only ("view/search stored memories"). But once the UI exists, the natural instinct is to add "edit memory," "delete memory," "add tag," "update properties" directly in the browser. Each mutation surface requires: CSRF protection, ownership validation, idempotency, conflict resolution (if two surfaces try to edit the same block simultaneously). This doubles or triples the implementation cost of the memory browser phase.

**Warning signs:**  
Memory browser implementation plan includes any `PUT /blocks/:id`, `DELETE /blocks/:id`, or `PATCH /blocks/:id` endpoints.

**Prevention:**  
(1) v0.3 memory browser = read-only. The MCP `forget()` tool handles deletion. The MCP `remember()` tool handles editing. (2) The only mutation from the memory browser: "add to favorites" / "bookmark" — implemented as a tag write, which is low-risk. Everything else deferred to v0.4. (3) State this constraint explicitly in the memory browser phase CONTEXT.md.

---

### SC-3: Eval-budget dashboard expands to a full observability platform — latency metrics, error rates, request traces added

- **Feature:** Scope Creep
- **Severity:** annoying → serious (timeline)
- **Phase:** Admin dashboard implementation plan

**What goes wrong:**  
The v0.3 eval-budget dashboard has a clear, narrow scope: translate `eval-budget-summary.mjs` into a browser view showing Workers AI neuron spend. Once the Analytics Engine query infrastructure exists, it is tempting to add latency histograms, error-rate charts, per-workspace request counts, and real-time traces. Each chart requires additional `writeDataPoint()` calls in the hot path (potentially slowing `recall()`) and additional SQL queries in the dashboard.

**Warning signs:**  
Admin dashboard implementation plan includes more than 5 distinct Analytics Engine metrics. The plan proposes adding new `writeDataPoint()` calls to the mcp-server or triage-worker during the dashboard phase.

**Prevention:**  
(1) v0.3 admin dashboard = exactly two views: (a) Workers AI neuron spend over time (the `eval-budget-summary.mjs` equivalent), (b) workspace identity/member management (read-only list from `ENGRAM_IDENTITIES` KV). (2) Any observability instrumentation (latency, error rates, traces) deferred to v0.4 as a monitoring phase. (3) Use the existing `writeDataPoint()` calls already in the codebase — do not add new instrumentation during the dashboard phase. Dashboard phases should read existing data, not add new sensors.

## v0.3 Must-Mitigate List

The following items cannot be deferred — v0.3 cannot ship without addressing all of them.

| ID | Pitfall | Minimum Required Action | Phase |
| --- | --- | --- | --- |
| ML-1 | Mail scanner consumes single-use token | POST-gate confirmation before token consumption | Auth Worker (Phase 1 of auth) |
| ML-2 | Token entropy too low / plain-text storage | 256-bit token, SHA-256 stored, 15min TTL | Auth Worker |
| ML-3 | Open redirect on callback | Server-side allowlist, `new URL()` validation | Auth Worker |
| EM-1 | Email Routing is inbound-only | Use Cloudflare Email Service (`[[send_email]]` binding), confirm beta access | Infrastructure planning (before coding) |
| IC-1 | Magic-link creates divergent workspace identity | Email-keyed lookup of existing identity record; never auto-create workspace from web login | Auth Worker (identity design must be locked first) |
| IC-2 | KV propagation lag invalidates first session read | JWT cookie for session (not KV lookup per request) | Auth Worker |
| IC-3 | Web session reads wrong workspace via URL path | Derive workspace_id from session JWT exclusively | ALL UI API routes |
| WP-1 | CSRF on inbox write endpoints | `__Host-CSRF` double-submit cookie + Origin check | Inbox UI |
| WP-3 | Missing workspace ownership check on web writes | Session JWT workspace_id → DO stub construction; DO `assertOwnsWorkspace()` as second layer | ALL UI write routes |
| DU-1 | Chatty per-row DO calls from list views | Single paginated `listInbox()` DO RPC returning full page | Inbox UI |
| DU-3 | UI shares CPU with MCP Worker hot path | Separate `engram-ui-worker` deployment | Infrastructure (before any UI code) |
| SA-1 | SPA fallback swallows OAuth callback navigation | `run_worker_first: ["/auth/*"]` in wrangler.jsonc | Infrastructure (before auth code) |
| SA-2 | Secret leakage via VITE_* into client bundle | Vite plugin ≥ 1.6.0; audit all VITE_* vars; no secrets prefixed VITE_ | First UI build setup |
| IC-5 | Session cookie leaks to other workers.dev Workers | `__Host-engram-session` cookie name; deploy on custom domain | Auth Worker |
| AD-4 | Analytics Engine API token exposed to browser | Server-side proxy; token in Worker secret only | Admin dashboard |
