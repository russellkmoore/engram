<objective>
Build the `conflictPipeline` orchestrator that composes Plan 02-01's `vectorizeNeighbors` helper, the existing `detectConflict()` inference (untouched per CON-01), Plan 02-05's `insertConflictAsInbox` RPC, and the triage-worker's `writeAnalytics` pattern into a single fire-and-forget routine. Called by Plan 02-07 via `ctx.waitUntil(conflictPipeline(env, newBlock))`.

CON-02 flow:
1. Cosine prefilter — `vectorizeNeighbors(env, workspace_id, newBlock.embedding, { topK: 3, type: newBlock.type, scope: newBlock.scope, threshold: 0.7 })`.
2. CON-06 dupe-ceiling — drop matches at ≥0.92 cosine (PITFALLS CD-4).
3. Hydrate neighbor blocks via cross-Worker `WORKSPACE.getBlocksByIds` RPC (existing pattern).
4. Bounded-parallel CON-07 — `Promise.all` over up to 3 `detectConflict()` calls. The `topK=3` prefilter ceiling IS the concurrency cap; no `p-limit` needed.
5. For every `category === "contradiction"` verdict, call `insertConflictAsInbox` RPC with the CON-04 shape (Plan 02-05 contract).
6. D-20 analytics — emit `writeDataPoint` in `finally` so the row lands even on error.

Verdict enum: `"contradiction" | "benign_update" | "unrelated" | "skipped-dupe" | "error"`. The verdict is computed AFTER the parallel detect resolves; it's the "highest-severity-seen-so-far" — `error` overrides everything; `contradiction` overrides `benign_update`; `unrelated` is the no-op-but-not-skipped baseline; `skipped-dupe` indicates the dupe filter blocked all candidates; `unrelated` covers "no neighbors above threshold" too.

CON-08 architectural lock: NO `EMAIL`, `WEBHOOK`, `PUSH`, `NOTIFY`, `SLACK`, or any push-notification primitive is imported or invoked anywhere in this file. The only output sinks are: the WorkspaceDO inbox table (via RPC) and the Analytics Engine.

The orchestrator runs INSIDE the `ctx.waitUntil` callback (wired in Plan 02-07). RESEARCH §Pitfall 6 is the load-bearing rule: `writeAnalytics` MUST be inside the function body (which runs inside waitUntil) so the lifetime guarantee holds. Errors are CAUGHT LOCALLY — never re-thrown — because a throw inside waitUntil marks the parent invocation as failed.
</objective>
