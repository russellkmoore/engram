# Phase 4: Core Tools + Envelope - Context

**Gathered:** 2026-05-26
**Status:** Ready for planning (after spike — see D-01)

<domain>
## Phase Boundary

The 5 v0.1 MCP tools (`remember`, `recall`, `search`, `forget`, `ingest`) ship real handler bodies that route via `getAgentByName(env.WORKSPACE, this.props.workspace_id)` to the WorkspaceDO query helpers from Phase 2. Every response is wrapped in the `EngramResponse<T>` envelope (`result`, `context.{related, entities, timeline?, conflicts?}`, `meta.{confidence, coverage, last_updated, gaps}`, `suggestions?.{actions, queries}`); failures throw `McpError` with proper JSON-RPC codes (no ad-hoc `{error: "..."}` envelopes); every serialized success response stays under the 8K-token budget (MCP-08); `forget` is transactional + complete (TOL-04); a cross-workspace penetration test (TOL-07) confirms the JWT → `props.workspace_id` → DO `assertOwnsWorkspace` chain holds.

Lexical (`SQL LIKE`) backing is locked for `recall` / `search` — semantic search via Vectorize lands in Phase 5 (AI-04). Workers AI extraction / synthesis / entity extraction / memorability scoring all ship in Phase 5 (AI-03 / AI-05 / AI-06) — Phase 4 ships **honest stubs** (D-04) so Phase 5 POPULATES envelope fields rather than RESTRUCTURING them. The `ingest` Queue producer lands in Phase 6 (PIP-01 / PIP-02); Phase 4 ships the contract with a synthetic `job_id` (D-05) so the call shape is stable across the Phase-6 swap.

Phase 4 covers requirements **TOL-01..08, MCP-07, MCP-08** (10 total). Real Vectorize / Workers AI / Queue side effects are out of scope.

</domain>

<decisions>
## Implementation Decisions

### Synthesis contract + spike + `verbosity` escape hatch

- **D-01:** **Workers AI extraction-quality spike runs BEFORE Phase 4 planning** (~1 day via `/gsd:spike`). 30 real samples spanning 3 type buckets (10 job postings from Russell's job-search agent corpus, 10 meeting / decision notes, 10 research notes). Models: `@cf/meta/llama-3.1-8b-instruct` (extraction) + `@cf/baai/bge-base-en-v1.5` (embeddings). Score against hand-extracted ground truth on (a) field-level recall, (b) field-level precision, (c) summarization fidelity. **Decision gate:**
  - **≥85% precision/recall** → synthesis-only thesis survives; ship envelope as-designed; `verbosity` default stays `"synthesis"`.
  - **70–85%** → ship envelope as-designed BUT flip `verbosity` default to `"both"` (raw chunks always returned alongside synthesis).
  - **<70%** → re-open envelope architecture before Phase 4 planning resumes (hybrid envelope vs stronger model).
  Output: a single-page findings doc + `/gsd:spike-wrap-up` to capture findings as a project skill that the Phase 4 planner reads.

- **D-02:** **`verbosity` parameter on `recall` only**, default `"synthesis"`. Enum: `"synthesis" | "chunks" | "both"`. `synthesis` = honest-stub `null` in v0.1, real CF AI synthesis in Phase 5. `chunks` = pre-synthesis lexical hits with their match-column metadata (works in v0.1 with `lexicalSearchBlocks` results; in Phase 5, with Vectorize-ranked chunks). `both` = synthesis + chunks side-by-side. Default flips to `"both"` only if D-01 spike returns 70–85% gate. **Not added** to `search`, `remember`, `forget`, `ingest` — they have no synthesis to escape from. `reflect()` (v0.3) inherits the same enum.

- **D-03:** **Zod schema diff (D-02):** add `verbosity: z.enum(["synthesis", "chunks", "both"]).optional().default("synthesis")` to `RecallInputSchema` in `packages/mcp-server/src/schemas.ts`. The structural-defense-in-depth invariant (no `workspace_id` field on any schema) is unchanged.

### v0.1 envelope stub semantics (honest stubs, not heuristics)

- **D-04:** **Honest stubs posture.** Every `EngramResponse<T>` field is PRESENT and TYPED correctly, but fields that require AI ship as `null` or empty arrays. Phase 5 then POPULATES those fields without changing the envelope shape — the Phase 5 diff is a body change, not a contract change. Phase 4 explicitly rejects "minimal deterministic heuristics" (templated `synthesis` strings, computed `meta.coverage`, etc.) because Russell's job-search agent (TOL-08) and any future MCP client risks building reliance on heuristics that Phase 5 replaces with semantically different signals.

- **D-05:** **`ingest()` v0.1 contract = synthetic accepted.** Returns `EngramResponse<{ status: "accepted", job_id: string }>` where `job_id` is a real UUID generated by the handler. No Queue side effect (`env.INGEST_QUEUE.send(...)` is not yet wired — PIP-01/02). `meta.gaps` includes `"Async enrichment pipeline lands in Phase 6 — job is recorded but not yet processed."` Phase 6 swaps in `ctx.waitUntil(env.INGEST_QUEUE.send(memoryEvent))` underneath the same return shape — no schema or envelope change.

- **D-06:** **`remember()` honest-stub output:**
  - `result.id` = real UUID (the row PK written via `WorkspaceDO.insertBlock`).
  - `result.classified_type` = `args.type ?? null` (pass-through; no AI inference happened in v0.1).
  - `result.extracted_fields` = `{}` (Phase 5 / AI-05 populates via Triage Worker entity extraction).
  - `result.confidence` = `null` (no AI classification = no confidence score).
  - `context.conflicts` = `[]` per D-08.
  - `context.entities` = `[]` (Phase 5 / AI-05).
  - `meta.confidence` = `null`, `meta.coverage` = `null`, `meta.gaps` includes `"AI synthesis lands in Phase 5"` + (when applicable) the D-05 ingest gap + the D-08 conflict-detection gap.

- **D-07:** **`recall()` honest-stub output:**
  - `result.memories` = `LexicalSearchHit[]` from `WorkspaceDO.lexicalSearchBlocks` (D-02 verbosity controls inclusion of pre-synthesis chunks).
  - `result.synthesis` = `null` when `verbosity === "synthesis"` (no AI ran; honest stub). Phase 5 populates with real CF AI synthesis without changing the field shape.
  - `result.chunks` (new optional field) = pre-synthesis chunk list when `verbosity ∈ {"chunks", "both"}`; in v0.1 a chunk is `{ id, content_excerpt, score: null }` derived from the lexical hit; in Phase 5 it's the Vectorize-scored chunk.
  - `context.related` = `[]` (no semantic adjacency without Vectorize).
  - `context.entities` = `[]` (Phase 5 / AI-05).
  - `meta.last_updated` = `max(result.memories[].created_at)` when memories non-empty, else `null`.
  - `meta.coverage` = `null` in v0.1 (no AI to estimate completeness).

### Lexical conflict detection (TOL-01 SC#1)

- **D-08:** **`context.conflicts` is empty in v0.1** — `remember()` always returns `context.conflicts = []` AND emits `meta.gaps` containing `"Conflict detection lands in Phase 5 (semantic similarity via Vectorize)."` Matches the honest-stubs posture (D-04); zero false positives; SC#1's "when lexical overlap is detected" is vacuously satisfied (no overlap detected because no detection runs). Phase 5 / AI-02 populates this field without breaking the shape. No `lexicalConflictCheck()` helper is added to `WorkspaceDO` in Phase 4.

### Token budget enforcement (MCP-08)

- **D-09:** **Tokenizer = `gpt-tokenizer`** (pure-JS, ~50KB, works cleanly in workerd + `@cloudflare/vitest-pool-workers`). The 8K-token cap is a SAFETY ceiling, not a precision metric — over-counting versus Claude's true tokenizer (which `gpt-tokenizer` tends to do, since GPT-4 BPE encodes English ~5% denser than Claude's BPE) gives Russell margin. Portability wins; `tiktoken`'s WASM init cost on cold starts is not worth the fidelity for a safety ceiling.

- **D-10:** **Cap strategy = schema-level limit + post-trim.**
  - **Schema-level:** `RecallInputSchema.limit` and `SearchInputSchema.limit` (when added — currently the latter has no `limit`) constrained to `z.number().int().positive().max(25)` (down from the current `max(100)`). The 100-cap was set in Phase 3 when no token-budget analysis existed; 25 is the size-budget-derived ceiling.
  - **Post-trim:** before the handler returns, run the serialized envelope through `gpt-tokenizer` and assert ≤ 7,500 tokens (margin under 8K). If over, trim in priority order: (1) drop `result.memories[i].content` (keep `summary`), (2) drop `result.memories[i].summary` (keep snippet metadata only), (3) drop trailing `result.memories[]` entries until under budget. Never drop `meta` or `context.conflicts` (load-bearing signals); never drop `result.id` on `remember()`.
  - **MCP-08 unit test:** constructs a worst-case `recall()` response (25 memories each with 4KB content + 1KB summary + maximally populated `context.related`/`entities`/`conflicts`) and asserts the post-trim envelope is < 8,000 tokens. Test lives in `packages/mcp-server/src/__tests__/token-budget.test.ts`.

### Claude's Discretion

The following are implementation details downstream agents (planner, executor) will fill using prior phases' patterns. Documented here so they're visible during planning:

- **Cross-workspace penetration test (TOL-07 / SC#9):** vitest integration test using `@cloudflare/vitest-pool-workers`. Spin up two workspaces (`workspace_A`, `workspace_B`); call `remember()` against A using a JWT with `props.workspace_id = workspace_A`; then call `recall()` / `forget()` against A's DO ID but with a JWT carrying `props.workspace_id = workspace_B`. Phase 2 STO-07's `assertOwnsWorkspace` guard MUST fire (`McpError(-32600 InvalidRequest)`). Test lives in `packages/mcp-server/src/__tests__/cross-workspace-pentest.test.ts`. The structural test from Phase 3 (no `args.workspace_id` reads outside comment lines) stays in place.
- **TOL-08 smoke (Russell's job-search agent):** v0.1 satisfies this via a LOCAL smoke (`wrangler dev` + MCP Inspector or a small node script that calls the MCP over the OAuth-bridge) — NOT a full agent reconfig. Full reconfig is DEP-04 in Phase 7. Smoke script lives in `scripts/smoke-job-agent.mjs` (or similar) and is referenced from the Phase 4 verification artifact.
- **`forget(cascade)` semantics:** v0.1 ships exactly what Phase 2's `WorkspaceDO.deleteBlock({ workspace_id, id, cascade? })` already does — block + cascade to relations rows, NOT to related blocks. Vectorize vector delete is Phase 5 / AI-08 (the TOL-04 contract already promises "Vectorize vectors will be deleted too" — that promise activates with Phase 5). No transactionSync() wrap in Phase 4 — Phase 2 RESEARCH documented that two-statement cascade is "atomic individually, NOT atomic as a pair" at v0.1 scale; revisit only if an invariant violation surfaces.
- **`McpError` mapping:** centralize via `mapToMcpError(err: unknown): McpError` already in `packages/mcp-server/src/error-mapping.ts` (Phase 3 D-04). All 5 Phase 4 handlers wrap their try/catch through this single mapper. `NotFoundError` (from `@engram/workspace-do`) → `McpError(InvalidParams, "memory not found")` (`-32602`). `assertOwnsWorkspace`'s `McpError(InvalidRequest)` passes through unchanged. Anything else → `McpError(InternalError, sanitized message)` (`-32603`) — no stack traces, no env values, no DB internals.
- **Wave layout suggestion** (the planner will refine): **Wave 0:** test infra updates (vitest fixtures for two-workspace pentest setup, `gpt-tokenizer` dep + worst-case fixture, schema diff for `verbosity` + `limit ≤ 25`) — RED tests. **Wave 1:** envelope helper module (`packages/mcp-server/src/envelope.ts` — constructs honest-stub `EngramResponse<T>` for each tool's success shape). **Wave 2:** the 5 tool handler bodies — implementable in parallel given the envelope helper + existing `error-mapping.ts` (`remember → insertBlock`, `recall → lexicalSearchBlocks`, `search → lexicalSearchBlocks` with filters layered on top, `forget → deleteBlock`, `ingest → synthetic accepted`). **Wave 3:** TOL-07 pentest + MCP-08 token-budget test. **Wave 4:** TOL-08 local smoke + DEP-05 README amendment + Phase 5 hand-off note (which envelope fields Phase 5 will populate).
- **`recall.chunks` shape (D-07):** typed as `Array<{ id: string; content_excerpt: string; score: number | null }>` in v0.1; Phase 5 widens the type when Vectorize scores land. New optional field on the `recall()` result type — define in `shared/types` or a `packages/mcp-server/src/result-types.ts` per planner preference.
- **`meta.gaps` content discipline:** every honest-stub `null` field that downstream Claude/clients might rely on gets a corresponding human-readable string in `meta.gaps`. Strings are TEMPLATED but FROZEN at v0.1 (planner picks final wording during plan-phase) so MCP-08 token-budget tests can reproduce exact byte counts.
- **`suggestions` field:** `undefined` in v0.1 for all 5 tools (the field is optional in the envelope). Phase 5 / v0.2 may populate it; honest-stubs posture says leave it absent.

<specifics>
## Specific Ideas

- "Do it RIGHT, not FAST" applies hardest here: this is the phase that freezes the EngramResponse envelope on 5 production tools. Russell's job-search agent (TOL-08) will be the first consumer; once it relies on a shape, changing that shape is a breaking-change-with-real-users problem. The spike (D-01) is the explicit "earn the right to freeze" gate.
- The honest-stubs posture (D-04) means a Phase 5 grep for `// TODO: AI` is unnecessary — every Phase 4 honest-stub field that Phase 5 will populate is already typed correctly AND has a `meta.gaps` note pointing forward. Phase 5's diff is a body change, not a contract change.
- The `verbosity = "both"` default (which fires only if the spike scores 70–85%) is the design's insurance policy. If we'd over-trusted CLAUDE.md and shipped synthesis-only, a 71% extraction quality would have meant either (a) shipping a known-broken contract or (b) emergency schema changes mid-v0.1.
- The 25-cap on `limit` (D-10) is derived from the 8K budget, not picked arbitrarily. Each `LexicalSearchHit` is ~300-400 tokens worst-case (content excerpt + summary + metadata); 25 hits + envelope overhead ≈ 7-8K tokens. `gpt-tokenizer`'s tendency to over-count vs Claude's BPE means real-world calls are likely 10-15% under the assertion threshold.
- `ingest()`'s synthetic accepted contract (D-05) is the cleanest example of "ship the contract, swap the implementation later" — Phase 6's diff against `ingest`'s handler is exactly one line: replace the `void 0` queue stub with `ctx.waitUntil(env.INGEST_QUEUE.send(memoryEvent))`. Test ergonomics: Phase 6 vitests assert the queue side effect; Phase 4 vitests assert the envelope shape; both pass independently.

</specifics>
