From @cloudflare/workers-oauth-provider (verified against RESEARCH.md sourcing):
The `defaultHandler` is a standard Cloudflare Workers `ExportedHandler<Env>` object. The `OAuthProvider` dispatches all non-`/mcp` requests to it. The library injects an `OAUTH_PROVIDER: OAuthHelpers` binding into env at runtime — this exposes `parseAuthRequest`, `lookupClient`, and `completeAuthorization`. The library also stores grant/token state in a KV namespace bound as `OAUTH_KV` (declared in wrangler.jsonc by Plan 05). The library reads `COOKIE_ENCRYPTION_KEY` from env (wrangler secret).

Env interface (final shape, per Plan 05 wrangler-types regeneration; Plan 04 can declare locally):
```typescript
interface Env {
  WORKSPACE: DurableObjectNamespace;        // typed <WorkspaceDO> after wrangler types
  MCP_OBJECT: DurableObjectNamespace;        // typed <EngramMcp> after wrangler types
  ENGRAM_IDENTITIES: KVNamespace;
  OAUTH_KV: KVNamespace;                     // library-owned
  OAUTH_PROVIDER: OAuthHelpers;              // library-injected at runtime
  COOKIE_ENCRYPTION_KEY: string;             // wrangler secret
}
```

OAuthHelpers shape (consumed within defaultHandler):
- `parseAuthRequest(request: Request): Promise<{ clientId: string; ... }>`
- `lookupClient(clientId: string): Promise<unknown>` (validates the client is registered)
- `completeAuthorization(args: { request, userId, metadata, scope, props }): Promise<{ redirectTo: string }>`

KV record shape (Plan 01's kv-bootstrap.mjs writes these):
```json
{ "workspace_id": "rmoore-personal", "user_id": "rmoore" }
```
Key = the OAuth `sub` claim. Value = the JSON-serialized identity record.

Phase 3 D-08 public routes (no auth):
- GET `/` → `{ name: "engram-mcp-server", version: "0.1.0", mcp: "/mcp", oauth: "/.well-known/oauth-protected-resource", docs: "..." }`
- GET `/health` → `{ status: "ok", version: "0.1.0", commit: <build-time or "dev">, timestamp: Date.now() }`

The `/.well-known/oauth-protected-resource`, `/.well-known/oauth-authorization-server`, `/token`, `/jwks`, and `/register` routes are LIBRARY-OWNED — they are NOT served by defaultHandler. defaultHandler ONLY sees /, /health, /authorize, and the 404 fall-through (per RESEARCH.md Pitfall 4 — apiRoute and defaultHandler are mutually exclusive on /mcp; library well-knowns intercept before defaultHandler runs).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → /authorize | First-token issuance dance. Browser (driven by mcp-remote) arrives with OAuth request parameters; library parses; defaultHandler is the consent + KV-lookup step. |
| KV → completeAuthorization props | The ONLY trusted source of `props.{workspace_id, user_id}`. KV writes are restricted to the `wrangler kv` CLI (account-scoped, no Worker code writes here in v0.1). |
| /health, / → public | These bypass OAuth (D-08). No auth conveyance; no sensitive data. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-JWT | Spoofing | OAuthProvider routing (library) | mitigate | OAuthProvider validates JWT signatures before dispatching to apiHandler (the /mcp path). defaultHandler in this plan never receives a /mcp request. The library's validation is RFC 6749/9728 compliant — verified by RESEARCH.md §Standard Stack (line 91). No custom code needed; the threat is mitigated structurally by using the library. |
| T-03-PROPS | Spoofing / Elevation of Privilege | packages/mcp-server/src/oauth.ts /authorize handler | mitigate | The /authorize handler sources `props.{workspace_id, user_id}` EXCLUSIVELY from `await env.ENGRAM_IDENTITIES.get(sub)` — never from request body, query params, or headers. completeAuthorization() is invoked with literal `{ workspace_id: identity.workspace_id, user_id: identity.user_id }` from the parsed KV value. oauth.test.ts asserts this by mocking ENGRAM_IDENTITIES and verifying completeAuthorization receives ONLY KV-sourced props. |
| T-03-KV-LEAK | Information Disclosure | /authorize handler 403 path | mitigate | When KV lookup returns null, the 403 response body contains ONLY the literal string `Unknown OAuth subject: ${sub}. Bootstrap via npm run kv:bootstrap.` — never the KV value content (which would be empty anyway since the key is missing). The `sub` itself IS echoed (it's already known to the requester — it's their own dynamically-registered client id), so this is not a leak. oauth.test.ts asserts no JSON.stringify(identity) or .value access appears in the 403 path. |
| T-03-PARSE | Tampering | JSON.parse on KV value | mitigate | KV values are written ONLY by the trusted `scripts/kv-bootstrap.mjs` script (Plan 01) via `wrangler kv key put`.
