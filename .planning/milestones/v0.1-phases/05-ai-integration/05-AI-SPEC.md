## 1. System Classification

**System Type:** RAG (Retrieval-Augmented Generation infrastructure layer — semantic recall via vector similarity, hydrated from per-workspace SQLite)

**Description:**
Engram's Phase 5 turns the lexical (`LIKE`-based) tool surface that shipped in Phase 4 into a semantic memory layer. `remember()` synchronously generates a 768-dimension embedding via Cloudflare Workers AI (`@cf/baai/bge-base-en-v1.5`), stamps the embedding model + version onto the SQLite row, and upserts the vector into the single global Cloudflare Vectorize index `engram-memories` under a namespace equal to the caller's `workspace_id`. `recall()` embeds the query with the same model, queries the workspace namespace top-K, and hydrates full block records from the `WorkspaceDO`'s SQLite store. The Triage Worker (Phase 6 consumer, contract locked here) extracts entities and scores memorability via `@cf/meta/llama-3.1-8b-instruct` with structured JSON output and 429-aware retry. `forget()` cascades the SQLite delete to the Vectorize vector in the same namespace. "Good" means: a memory written in one Claude conversation is semantically findable in another conversation by the same user against the same workspace, with sub-second p50 latency on the synchronous write+embed path and no cross-workspace leakage.

**Critical Failure Modes:**
1. **Cross-workspace vector leakage.** A query in `workspace_B`'s namespace returns a vector that was upserted under `workspace_A`. This breaks tenant isolation at the AI layer and is non-recoverable once it occurs in production (vectors are not auditable post-hoc). Mitigated by Vectorize namespace enforcement plus a behavioral isolation test.
2. **Embedding/query model drift.** `remember()` and `recall()` end up calling different embedding models or different model versions, silently destroying recall quality because the vector space no longer matches. STO-04's `embedding_model` + `embedding_version` columns on `blocks` exist specifically to detect this; AI-03 stamps them on write and AI-04 must read the same model identifier.
3. **`forget()` leaves orphan vectors.** SQLite row is deleted but the Vectorize vector lingers in the workspace namespace, so a future `recall()` returns a 404-hydrated phantom. This is the irreversible Phase 4 contract (`forget` promises "gone everywhere") finally being honored at the vector layer; AI-08 must verify with a round-trip `remember → forget → recall` test that returns zero matches.
4. **Workers AI 429 → full batch fail.** A Workers AI rate-limit response is treated as a hard error rather than a transient retry, so a single throttle event drops every event in the consumer batch. AI-07 enforces explicit `message.retry({delaySeconds: 30})` over thrown exceptions.
5. **Synchronous `remember()` blocks the user.** The inline embed+upsert exceeds the latency budget (target ~150–430ms p50), making the tool feel broken in interactive Claude conversations. The Triage Worker's AI calls (entity extraction, memorability) MUST stay on the async Queue path — only the embedding runs synchronously.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Developer tooling / personal knowledge infrastructure (MCP server for AI assistants)

**User Population:** v0.1 is single-tenant (Russell, internal use) feeding Russell's job-search agent and his Claude Desktop sessions. v0.3+ expands to small teams. The "user" the AI surface serves is Claude (and other MCP clients), not a human directly — the human consumes synthesis through Claude.

**Stakes Level:** Medium for v0.1 (internal, single user, recoverable failures); High for v1.0 (multi-tenant, paying customers, irrecoverable cross-tenant leakage would be a security incident).

**Output Consequence:** When recall returns wrong or missing memories, Claude either fabricates an answer or tells the user "I don't have that information" — both degrade trust in the memory layer. When recall returns another workspace's memory, that's a tenant-isolation breach.

### What Domain Experts Evaluate Against

| Dimension | Good (expert accepts) | Bad (expert flags) | Stakes | Source |
|-----------|----------------------|---------------------|--------|--------|
| Semantic recall precision@5 | Top 5 results include the intended memory for ≥90% of phrased-differently queries | Top 5 misses the memory despite clear semantic overlap | High | Engram acceptance test (Russell stores job posting → recalls one hour later with different wording) |
| Embedding/query consistency | Same model + version on both write and read paths (`bge-base-en-v1.5` v1) | Model drift between write and read; recall quality degrades silently | Critical | STO-04 + AI-03 columns + AI-04 read path |
| Namespace isolation | Query in workspace B never returns workspace A vectors | Any cross-namespace vector returned | Critical | AI-02 isolation test |
| Classification accuracy (Triage AI) | `@cf/meta/llama-3.1-8b-instruct` returns valid JSON matching schema ≥95% of the time | Malformed JSON breaks the consumer | High | AI-05 structured output contract |
| Memorability calibration | `>0.8` → store, `0.4–0.8` → inbox, `<0.4` → discard; thresholds produce roughly 60/30/10 split on real Russell content | All scores cluster at one end (everything inbox, or everything auto-stored) | Medium | AI-06 (memorability scoring) |
| Forget completeness | `remember → forget → recall` returns 0 semantic matches | Vector orphans surface as ghost recalls | Critical | AI-08 round-trip test |
| 429 retry correctness | Workers AI 429 → `message.retry({delaySeconds: 30})`, no batch-fail | 429 throws and drops the batch | High | AI-07 |

### Known Failure Modes in This Domain

- **Embedding model drift across pipeline halves** — the canonical RAG bug. Engram preempts via the `embedding_model` + `embedding_version` stamp from Phase 2.
- **Tenant ID mishandling at the vector layer** — Vectorize namespaces are passed as a query parameter; a forgotten namespace argument silently queries the global index. Defense-in-depth: every Vectorize call goes through a helper that requires `workspace_id` as a non-optional parameter.
- **Synchronous AI on the hot path** — Workers AI calls can spike to 5–15s p99. Only embedding (~50–150ms typical) is allowed inline; everything else (extraction, scoring, summarization) is deferred to the Queue consumer per ARCHITECTURE.md's data flow diagram.
- **Chunking strategy mismatch with bge-base** — `bge-base-en-v1.5` has a 512-token context window. Memories longer than this need chunking on ingest; v0.1 stores short blocks only and revisits chunking in v0.2.

### Regulatory / Compliance Context

None for v0.1 (internal, single-user, no PII beyond Russell's own job-search data). v1.0 introduces multi-tenant SaaS billing which triggers standard SaaS hygiene (data residency disclosures, GDPR data-export via the v0.3 `export` tool), but those are out of scope here.

## 2. Framework Decision

**Selected Framework:** Cloudflare-native primitives — **Cloudflare Workers AI + Cloudflare Vectorize**, no third-party agent/RAG framework.

**Version:**
- Workers AI binding: `env.AI` (Cloudflare Workers runtime, no separate SDK version)
- Embedding model: `@cf/baai/bge-base-en-v1.5` (768-dimension, cosine; preset-locked)
- Classification/extraction model: `@cf/meta/llama-3.1-8b-instruct` (8B params, structured JSON output)
- Vectorize: latest GA via `wrangler` (single global index `engram-memories` with namespace-per-workspace)
- Runtime: Cloudflare Workers (`workerd`), TypeScript

**Rationale:**
Engram is, by design and per `/Users/rmoore/Workspaces/engram/CLAUDE.md`, a Cloudflare-native MCP server. The entire compute / storage / async / AI surface is one provider, on `workerd`, in TypeScript. The value proposition of a RAG framework like LlamaIndex is a unified retrieval API across multiple vector stores and embedding providers — Engram has *exactly one* vector store (Vectorize), *exactly one* embedding model (`bge-base-en-v1.5`), and *exactly one* inference provider (Workers AI). The framework abstraction here is pure overhead: extra bundle size on `workerd`, an additional dependency surface for a Python-centric ecosystem to be ported to TS, and an extra translation layer between Engram's `EngramResponse` envelope and the framework's retrieval primitives. The synchronous write path (`remember → embed → upsert`) and synchronous read path (`recall → embed → query → hydrate from SQLite`) are each 3-step linear pipelines — there is no graph, no agent loop, no tool router that an orchestration framework would simplify. Engram **is** the MCP tool surface that an external agent (Claude) calls; Engram itself is not an agent.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LlamaIndex (TS port) | Designed to abstract over many vector stores + embedding providers. Engram has one of each. The retriever/query-engine abstraction adds indirection over a direct `env.VECTORIZE.query({namespace, topK, vector})` call and breaks the `EngramResponse` envelope contract. Python-first; the TS port lags features. Adds bundle weight on `workerd`. |
| LangChain (LangChain.js) | Same single-provider mismatch as LlamaIndex, plus a larger surface area (chains, memory classes, tool wrappers) Engram does not need. The "memory" abstractions in LangChain are conversational-context layers, not durable per-workspace stores — wrong layer of the stack. Bundle size and dependency churn are notable on `workerd`. |
| LangGraph | Graph/state-machine orchestration. Engram's v0.1 read/write flows are linear; there is no branching, no agentic plan-and-execute loop. Reintroduce only if v0.3+ `reflect()` or v0.4 connectors grow real state-machine flows. |
| CrewAI | Multi-agent orchestration. Engram has no agents internally — Claude is the agent, Engram is the memory tool. Zero fit for v0.1. |
| Claude Agent SDK | Engram is the MCP server *that* Claude (running in the user's client) connects to. Embedding the Claude Agent SDK inside Engram would invert the architecture — Engram is the tool surface, not an agent that uses tools. |
| Vercel AI SDK | Edge-friendly inference SDK aimed at chat UIs and streaming responses. Engram has no UI in v0.1 and does not stream — `remember()`/`recall()` are unary tool calls returning structured envelopes. The Workers AI binding `env.AI.run(...)` is already the canonical Cloudflare interface and matches our deployment target without an extra SDK layer. |
| Pinecone / Weaviate / Qdrant + their SDKs | Off-platform vector stores. Picking any of them re-introduces a cross-cloud hop on every `remember()` and `recall()`, breaks the single-vendor consolidation that justifies the Cloudflare-only architecture, and forfeits the namespace-per-workspace pattern Vectorize gives us natively. |

**Vendor Lock-In Accepted:** Yes — explicitly. Engram's bet (documented in `/Users/rmoore/Workspaces/engram/CLAUDE.md` and the Key Decisions Log) is that Cloudflare-only is the right consolidation for an MCP-native second brain: one provider, one bill, one runtime, one observability stack, sub-100ms cold starts via Workers. The trade-off was made at the architecture phase, not here. Phase 5 inherits and honors it. Re-embedding to a different model or migrating off Vectorize remains possible via STO-04's `embedding_model` + `embedding_version` columns (the migration playbook is deferred to v0.2 per ROADMAP.md "Later Milestones"), so the lock-in is reversible at the data-model level even though the runtime lock-in is permanent.

## 3. Framework Quick Reference

> Fetched from official Cloudflare docs (Vectorize client API, Workers AI bindings, JSON-mode reference) by `gsd-ai-researcher`. Distilled for AI-01..AI-08.

### Installation

No new npm dependencies are required for the AI calls themselves — `env.AI` and `env.VECTORIZE` are runtime bindings, not SDK imports. The setup work is wrangler-side (index creation + binding declaration) plus a Zod helper for response validation.

```bash
# 1. Create the single global Vectorize index (idempotent — AI-01).
#    The preset locks dimensions=768 + metric=cosine to match @cf/baai/bge-base-en-v1.5.
#    Re-running with the same name returns "already exists" without modifying the index.
npx wrangler vectorize create engram-memories \
  --preset=@cf/baai/bge-base-en-v1.5

# 2. (Optional but recommended) Create metadata indexes for hybrid-filter recall.
#    Up to 10 properties per index; declare these once at setup time.
npx wrangler vectorize create-metadata-index engram-memories \
  --property-name=type --type=string
npx wrangler vectorize create-metadata-index engram-memories \
  --property-name=scope --type=string

# 3. Already present in the monorepo from Phase 4 — Zod (for AI-05 structured output validation).
#    Adding zod-to-json-schema to derive response_format.json_schema from the Zod type:
npm install --workspace=packages/triage-worker zod-to-json-schema
```

### Entry Point Pattern

Two canonical flows. Both share the same embedding model; the namespace argument is the AI-02 tenant-isolation guarantee.

**`remember()` — sync embed + upsert (AI-03).** Runs inline on the MCP request hot path. Writes block to SQLite first (Phase 4 path), then embeds + upserts.

```typescript
// packages/mcp-server/src/tools.ts — remember handler body (Phase 5 additions only).
// Phase 4 already wrote the block to SQLite via WorkspaceDO RPC and produced block.id.

const EMBEDDING_MODEL = "@cf/baai/bge-base-en-v1.5";
const EMBEDDING_VERSION = 1;

// 1. Embed the content (single-text call; bge-base-en-v1.5 returns 768d).
const embed = await env.AI.run(EMBEDDING_MODEL, { text: [block.content] });
const vector: number[] = embed.data[0]; // number[768]

// 2. Stamp the model + version on the SQLite row (STO-04 columns set on write).
//    Done in the same WorkspaceDO RPC call that inserted the block — single transaction.
await workspaceDo.stampEmbedding({
  block_id: block.id,
  embedding_model: EMBEDDING_MODEL,
  embedding_version: EMBEDDING_VERSION,
});

// 3. Upsert the vector to Vectorize under the workspace namespace.
//    namespace = workspace_id is the AI-02 isolation contract.
await env.VECTORIZE.upsert([
  {
    id: block.id,
    values: vector,
    namespace: this.props.workspace_id, // <= 64 chars; enforced by helper
    metadata: {
      type: block.type,
      scope: block.scope,
      created_at: block.created_at,
    },
  } satisfies VectorizeVector,
]);
```

**`recall()` — embed query + query Vectorize + hydrate (AI-04).** Replaces Phase 4's `instr()` lexical scan with semantic search.

```typescript
// packages/mcp-server/src/tools.ts — recall handler body (Phase 5 replacement).
// 1. Embed the query string with the SAME model that wrote the vectors.
const embed = await env.AI.run(EMBEDDING_MODEL, { text: [args.query] });
const queryVector: number[] = embed.data[0];

// 2. Query Vectorize in the workspace namespace. topK=25 matches Phase 4's D-10 cap.
//    Metadata-filter when args.types is supplied (spike-findings phase-5-ranking-strategy.md).
const matches = await env.VECTORIZE.query(queryVector, {
  topK: args.limit ?? 25,
  namespace: this.props.workspace_id,
  filter: args.types?.length ? { type: { $in: args.types } } : undefined,
  returnMetadata: "all",
});

// 3. Hydrate full block rows from SQLite by ID (Phase 2 query helper get_block_by_id).
//    Order preserved from Vectorize ranking. Missing IDs (orphans) are dropped + logged.
const ids = matches.matches.map((m) => m.id);
const blocks = await workspaceDo.getBlocksByIds(ids);

// 4. Hybrid re-rank per spike-findings phase-5-ranking-strategy.md (cosine + recency + type + scope).
const ranked = hybridRank(matches.matches, blocks, args, Date.now());
```

**Triage Worker — structured extraction (AI-05 + AI-06).** Runs on the async Queue path, never inline.

```typescript
// packages/triage-worker/src/extract.ts (consumer body excerpt).
const CLASSIFIER_MODEL = "@cf/meta/llama-3.1-8b-instruct";

const TriageOutput = z.object({
  classified_type: z.enum([
    "job_application", "contact", "company", "project",
    "research_note", "decision_log", "meeting_note",
  ]),
  extracted_fields: z.record(z.unknown()),
  entities: z.array(z.object({
    name: z.string().min(1),
    type: z.enum(["person", "company", "role", "date", "url"]),
  })),
  summary: z.string().min(10).max(800),
  memorability: z.number().min(0).max(1),
  confidence: z.number().min(0).max(1),
});

const jsonSchema = zodToJsonSchema(TriageOutput, { target: "openApi3" });

const aiResp = await env.AI.run(CLASSIFIER_MODEL, {
  messages: [
    { role: "system", content: SYSTEM_PROMPT }, // see Section 4
    { role: "user", content: event.content },
  ],
  response_format: {
    type: "json_schema",
    json_schema: jsonSchema, // strict mode is best-effort; always validate with Zod
  },
});

// AI-07: 429 detection on the binding's non-throwing envelope. See Section 4.
if (aiResp && (aiResp as any).success === false) {
  const errs = (aiResp as any).errors ?? [];
  if (errs.some((e: any) => e.code === 7501 || /429|rate/i.test(e.message))) {
    message.retry({ delaySeconds: 30 });
    return; // do not throw; do not ack
  }
  throw new Error(`Workers AI failure: ${JSON.stringify(errs)}`);
}

const parsed = TriageOutput.safeParse(aiResp.response ?? aiResp);
if (!parsed.success) {
  console.error("triage:zod-parse-failed", { id: event.id, issues: parsed.error.issues });
  message.ack(); // permanent failure — DLQ-equivalent log + drop (PIP-05 pattern)
  return;
}

// AI-06 memorability routing.
if (parsed.data.memorability > 0.8) {
  await workspaceDo.updateBlockEnrichment(event.id, parsed.data); // properties + summary
} else if (parsed.data.memorability >= 0.4) {
  await workspaceDo.moveToInbox(event.id, parsed.data);
} else {
  await workspaceDo.discardWithLog(event.id, parsed.data);
}
```

**`forget()` — transactional cascade (AI-08).** Extends Phase 4's TOL-04 with Vectorize deletion.

```typescript
// packages/mcp-server/src/tools.ts — forget handler body addition.
// SQLite delete happens first (Phase 4); on success, delete the vector in the workspace namespace.
await workspaceDo.deleteBlock(args.id, { cascade: args.cascade });

```

### Key Abstractions

| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| `env.AI` (Workers AI binding) | Runtime binding exposing `.run(model, requestBody, options?)`. Returns `Promise<any>` — the response shape depends on the model. For `@cf/baai/bge-base-en-v1.5`, shape is `{ shape: [N, 768], data: number[][] }`. For `@cf/meta/llama-3.1-8b-instruct` with `response_format: {type: "json_schema", ...}`, shape is `{ response: <object> }` (the parsed JSON). | Every embedding call (AI-03, AI-04). Every Triage Worker classification + summarization + memorability call (AI-05, AI-06). |
| `env.VECTORIZE` (Vectorize binding) | Runtime binding exposing `.insert()`, `.upsert()`, `.query()`, `.queryById()`, `.deleteByIds()`, `.getByIds()`. All operations are asynchronous on the index side — upserts and deletes "may take a few seconds to become available for querying" per Cloudflare docs. | `.upsert()` on AI-03 write path. `.query()` on AI-04 read path. `.deleteByIds()` on AI-08 forget path. |
| Vectorize namespace | A per-vector + per-query string tag (max 64 bytes, max 1,000 per index). Vectors written with `namespace: X` are returned ONLY by queries that supply `namespace: X`. Namespace filtering is applied BEFORE vector search — it is structural, not a metadata predicate. | The AI-02 tenant-isolation contract. Every upsert and every query in Engram MUST set `namespace: workspace_id`. |
| Vectorize index preset | `--preset=@cf/baai/bge-base-en-v1.5` locks dimensions (768) and metric (cosine) at index creation. These cannot be changed without dropping + recreating the index, which forces a re-embed. | Index creation only (AI-01). Phase 5 does NOT re-create the index at any point. |
| Workers AI structured output | `response_format: { type: "json_schema", json_schema: <schema> }` on `@cf/meta/llama-3.1-8b-instruct`. Strict-mode is best-effort: the model will *try* to match the schema, but malformed outputs still occur. The response body is the parsed JSON on the `.response` field. | AI-05 entity extraction. AI-06 memorability scoring. Always validate the response with Zod before using it; see Section 4b. |

### Common Pitfalls

1. **Vectorize 429 / Workers AI 429 returns `success: false`, does NOT throw.** The binding envelope on a non-2xx upstream is `{ result: null, success: false, errors: [{ code: 7501, message: "..." }] }`. A naive `try/await env.AI.run(...)` block will never enter the `catch`. AI-07 requires explicit inspection of `success === false` and an `errors[].code === 7501` check (or message text match) before calling `message.retry({delaySeconds: 30})`. Forgetting this is the #1 way the Triage Worker silently drops messages under load.
2. **Forgetting `namespace` on `.query()` silently queries the global index.** Vectorize does not warn — it returns matches from every workspace. The defense-in-depth fix (per Section 1b "Known Failure Modes") is a helper function `vectorizeQuery(env, workspaceId, vector, opts)` where `workspaceId` is a non-optional positional argument; direct calls to `env.VECTORIZE.query()` are banned by lint rule.
3. **Passing `env.AI.run(...)` response directly into `env.VECTORIZE.query()`.** The response is `{ shape: [N, 768], data: number[][] }`; the query method wants `number[]`. Must unwrap to `embed.data[0]`. Cloudflare's own RAG tutorial calls this out explicitly. Symptom: type error in TS; if forced through with `any`, every query returns zero matches.
4. **`response_format: { type: "json_schema", strict: true }` is "best effort."** Even with strict mode the model occasionally emits malformed JSON or schema-violating output (spike findings recorded this for llama-3.1-8b-instruct on synthetic samples). Treat the model response as untrusted — always parse with Zod, log + skip (don't crash the consumer) on failure. Never destructure fields off the response without validation.
5. **Vectorize topK default is 5.** Phase 4's D-10 sets `limit ≤ 25`. The AI-04 helper MUST pass `topK: args.limit ?? 25` explicitly; otherwise recall silently caps at 5 matches and the synthesis layer downstream loses signal.
6. **`returnMetadata: "all"` + large topK is rate-limited differently.** Per Cloudflare docs: "returning all metadata or values limits `topK` to 50." Engram's `limit ≤ 25` keeps us under this cap, but any future raise of D-10 must check Vectorize's current limit page before shipping.
7. **Vectorize upsert + delete are eventually consistent ("seconds").** A `remember → recall` round-trip immediately after the upsert may miss the new vector. AI-08's `remember → forget → recall = 0` acceptance test allows up to 5s of slack. Integration tests must `await sleep(5000)` between phases or poll.
8. **Embedding model rotation by Cloudflare is silent.** If Cloudflare swaps the underlying weights of `@cf/baai/bge-base-en-v1.5` without changing the ID, recall quality could degrade with no signal at the binding layer. STO-04's `embedding_version: 1` column is the version-bump escape hatch — when CF announces a model rotation, increment the version, gate a re-embed migration on it.
9. **Namespace string length cap is 64 bytes.** Russell's IDs like `rmoore-personal` are safe; if v0.3 introduces UUID-shaped workspace IDs, the 36-character UUIDv4 form fits but anything longer (e.g., `team-{uuid}-{uuid}`) will be rejected. The Vectorize helper should `assert(namespace.length <= 64)` before every call.
10. **`McpAgent.serve()` is required — raw MCP SDK transports fail on `workerd`.** This is a Phase 3 invariant (MCP-01/02), reaffirmed here because Phase 5's AI handlers run inside `EngramMcp extends McpAgent`; using `@modelcontextprotocol/sdk` HTTP transports directly will break the deploy and not surface until Cloudflare's runtime rejects `node:http` imports.

## 4. Implementation Guidance

**Model Configuration:**

| Purpose | Model ID | Where | Key Parameters |
|---|---|---|---|
| Embeddings (write + query) | `@cf/baai/bge-base-en-v1.5` | `mcp-server` `remember()` (AI-03) + `recall()` (AI-04) | Input: `{ text: string[] }` (1 string per call on hot path; batched up to ~50 only for offline re-embed migrations). Output: `{ shape: [N, 768], data: number[][] }`. Dimensions=768, metric=cosine — both **locked by the index preset**, not by call. No temperature, no max tokens. |
| Entity extraction + summarization + memorability | `@cf/meta/llama-3.1-8b-instruct` | `triage-worker` Queue consumer (AI-05, AI-06) | `messages: [{role:"system", content: SYSTEM_PROMPT}, {role:"user", content: event.content}]`. `response_format: { type: "json_schema", json_schema: <derived from Zod> }`. `temperature: 0.2` (low for structured output stability — Phase 5 default; tune empirically on Russell's corpus). `max_tokens: 1024` (explicit — Section 4b cost discipline). |

Engram does NOT call any third-party model in v0.1. There is no fallback model, no router. If Workers AI is unavailable, the Triage Worker retries; the MCP server's sync `remember()` falls back to writing the SQLite row without embedding (block becomes "lexical-only" until a backfill job re-embeds it — Phase 6 work, not Phase 5).

**Core Pattern:**

The synchronous RAG write/read pair is two 3-step linear pipelines, plus an async enrichment Queue consumer. The contract diagram:

```
remember(content, type?, project?, tags?, source?, expires?)            [SYNC, MCP hot path]
  │
  ├─► WorkspaceDO.insertBlock(...)                                       [Phase 4 — SQLite write]
  │   returns block { id, content, type, scope, created_at, ... }
  │
  ├─► env.AI.run("@cf/baai/bge-base-en-v1.5", { text: [content] })       [AI-03 — embed]
  │   returns { shape: [1, 768], data: [number[768]] }
  │
  ├─► WorkspaceDO.stampEmbedding(id, model, version=1)                   [STO-04 — same tx as insertBlock ideally]
  │
  ├─► env.VECTORIZE.upsert([{ id, values, namespace: workspace_id,       [AI-03 — index]
  │                            metadata: {type, scope, created_at} }])
  │
  ├─► ctx.waitUntil(env.INGEST_QUEUE.send({ id, content, ... }))         [PIP-02 — Phase 6; out of scope here]
  │
  └─► buildRememberResponse({ id, classified_type: type ?? null, ... })  [Phase 4 envelope]


recall(query, types?, project?, scope?, limit?, since?, until?)         [SYNC, MCP hot path]
  │
  ├─► env.AI.run("@cf/baai/bge-base-en-v1.5", { text: [query] })         [AI-04 — embed query]
  │   returns { shape: [1, 768], data: [number[768]] }
  │
  ├─► env.VECTORIZE.query(queryVec, {                                    [AI-04 — semantic search]
  │     topK: limit ?? 25,
  │     namespace: workspace_id,
  │     filter: types?.length ? { type: { $in: types } } : undefined,
  │     returnMetadata: "all",
  │   })
  │   returns { matches: [{ id, score, metadata }, ...] }
  │
  ├─► WorkspaceDO.getBlocksByIds(matches.map(m => m.id))                 [Phase 2 helper — hydrate from SQLite]
  │
  ├─► hybridRank(matches, blocks, args, now)                             [spike-findings phase-5-ranking-strategy.md]
  │   score = 1.0·cosine + 0.15·recency + 0.2·type_match + 0.15·scope_match
  │
  ├─► env.AI.run("@cf/meta/llama-3.1-8b-instruct", { ... synthesis ... }) [optional per verbosity arg]
  │   D-01 (Phase 5 CONTEXT.md): SKIPPED on default recall (verbosity="chunks"). Runs ONLY when verbosity ∈ {"synthesis", "both"}. Default recall returns synthesis=null + meta.gaps + suggestions.actions discoverability triad.
  │
  └─► buildRecallResponse({ memories: ranked, synthesis, context: {...} })


triage-worker queue consumer                                            [ASYNC, post-remember]
  │
  ├─► env.AI.run("@cf/meta/llama-3.1-8b-instruct", {                     [AI-05 — structured extract]
  │     messages: [system, user],
  │     response_format: { type: "json_schema", json_schema },
  │     temperature: 0.2,
  │     max_tokens: 1024,
  │   })
  │
  ├─► detect429(aiResp) → message.retry({delaySeconds: 30}); return     [AI-07 — 429 envelope]
  │
  ├─► TriageOutput.safeParse(aiResp.response)                            [Section 4b — Zod gate]
  │   parse fail → message.ack() + log; do not crash batch
  │
  ├─► route by memorability:                                             [AI-06]
  │     > 0.8 → WorkspaceDO.updateBlockEnrichment(id, parsed)
  │     0.4..0.8 → WorkspaceDO.moveToInbox(id, parsed)
  │     < 0.4 → discardWithLog(id, parsed)
  │
  └─► message.ack()


forget(id, cascade?)                                                    [SYNC, MCP hot path]
  │
  ├─► WorkspaceDO.deleteBlock(id, { cascade })                           [Phase 4 — SQLite cascade]
  │
  └─► env.VECTORIZE.deleteByIds([id])                                    [AI-08 — Vectorize cascade,
                                                                          eventually consistent ~seconds]
```

The two non-obvious facts that drive the whole design:

- **Workers AI binding returns response objects, not throws.** A 429 yields `{ success: false, errors: [{ code: 7501, message: "..." }], result: null }`. The executor must inspect the body before assuming success. See Section 3 pitfall #1.
- **Vectorize namespace is BOTH a write-time and query-time tag.** It is NOT a metadata predicate. Setting `namespace` on upsert pins the vector to that bucket; setting `namespace` on query restricts the search to that bucket. Mismatched namespaces produce zero matches with no error — debugging this requires inspecting the upsert call site.

**Tool Use:**

Engram itself does not call MCP tools — it IS the MCP tool surface. The "tools" inside Engram are runtime bindings:

| Tool | Configured Where | Used By |
|---|---|---|
| `env.AI` (Workers AI binding) | `mcp-server/wrangler.jsonc` + `triage-worker/wrangler.jsonc`: `"ai": { "binding": "AI" }` | `mcp-server` (`remember`, `recall`); `triage-worker` (entity extraction, memorability, optional synthesis) |
| `env.VECTORIZE` (Vectorize binding) | Both wrangler configs: `"vectorize": [{ "binding": "VECTORIZE", "index_name": "engram-memories" }]` | `mcp-server` (`remember`, `recall`, `forget`); `triage-worker` only if conflict-detection scan lands in Phase 5 (otherwise deferred) |
| `env.WORKSPACE` (Durable Object stub) | `triage-worker/wrangler.jsonc` `durable_objects.bindings[]` pointing at `WORKSPACE_DO` class in `workspace-do` package | `triage-worker` to write extracted fields + summary back via `getAgentByName(env.WORKSPACE, workspace_id)` (Phase 5 must address how the consumer authenticates — STO-07's `assertOwnsWorkspace` must hold for triage-worker callers, see Phase 5 handoff doc) |

**State Management:**

Engram has no "AI state" in the conversational sense — every `remember()` / `recall()` is stateless from the AI binding's perspective. Persistent state lives in:

| State | Persisted In | Read Path | Write Path |
|---|---|---|---|
| Block content + metadata | SQLite in `WorkspaceDO` | `getBlocksByIds(ids)` after Vectorize query (AI-04 hydration) | `insertBlock()` inside the same WorkspaceDO RPC that stamps embedding model/version (AI-03) |
| Embedding model + version stamp | `blocks.embedding_model TEXT` + `blocks.embedding_version INTEGER` columns (STO-04) | Read at re-embed migration time only — v0.1 code never reads these on the hot path | Written in `stampEmbedding(id, model, version)` during `remember()` |
| Vector | Vectorize index `engram-memories`, namespace = `workspace_id` | `env.VECTORIZE.query(vec, {namespace, topK, filter, returnMetadata})` | `env.VECTORIZE.upsert([{id, values, namespace, metadata}])` |
| Enrichment status | `blocks.ingest_status TEXT` column (`pending` / `enriched` / `failed`) — added by PIP-06 (Phase 6); Phase 5 may pre-populate to `pending` on insert | Inbox UI v0.4 | Triage Worker on AI-05 success transitions `pending → enriched`; on AI-05 permanent failure (Zod parse fail or non-retryable AI error) → `failed` |
| Inbox entries (low-memorability captures) | `inbox` SQLite table in `WorkspaceDO` | v0.4 inbox UI | Triage Worker `moveToInbox()` when 0.4 ≤ memorability ≤ 0.8 (AI-06) |
| Conflict records | `conflicts` SQLite table in `WorkspaceDO` | `recall()` envelope `context.conflicts` field | Triage Worker semantic-similarity scan (deferred to Phase 5 plan; reverse-references AI-02 conflict detection per Phase 5 handoff doc) |

Each `WorkspaceDO` instance runs schema migration once at boot (`_schema_migrations` table — STO-02) inside `blockConcurrencyWhile()` with no network I/O. Phase 5 introduces zero new DO migrations; it consumes the columns Phase 2 created.

**Context Window Strategy:**

Embedding model `@cf/baai/bge-base-en-v1.5` has a **512-token** context window. Memories longer than ~2KB of text (~512 tokens at ~4 chars/token English) will silently truncate on the embedding side, degrading recall quality. v0.1 strategy:

- **Short-blocks-only assumption.** Per Section 1b "Known Failure Modes", v0.1 stores short blocks (job postings, decisions, contacts, notes) that fit comfortably under 512 tokens. The MCP `remember()` handler should reject (or warn + truncate) inputs over ~1,800 chars and surface the limit in `meta.gaps`. Chunking strategy is a v0.2 concern.
- **No prompt-tail context.** The embedding call passes ONLY the raw block content — no system prompt prefix, no metadata blob. The 512-token budget belongs entirely to user content.
- **Triage Worker prompt budget.** `@cf/meta/llama-3.1-8b-instruct` has a 128K-ish context (depends on Cloudflare's serving config — verify in docs at implementation time). v0.1 prompts run well under 8K input + 1K output; budget is not a constraint here. System prompt is ~500 tokens; user content is the block content (≤2KB); output is JSON-mode response capped at `max_tokens: 1024`.
- **Synthesis tail (recall verbosity).** When `verbosity ∈ {"synthesis", "both"}`, the synthesis call inputs the top-K hydrated blocks (up to 25). Token-budget the synthesis call: cap input at ~6K tokens (≈ 15 short blocks worth of content) before sending. Phase 4's `trimToBudget` in `envelope.ts` covers the OUTPUT side (worst-case ≤ 7,500 tokens); Phase 5 must add an input-side trim for the synthesis call. Per Phase 5 handoff: "synthesis is included in the trim algorithm: drop trailing memories first, never drop synthesis, never drop `meta.gaps`."

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. Cross-cutting patterns every developer building AI systems needs — independent of framework choice. Engram is TypeScript-on-`workerd`, so "Pydantic" maps to **Zod**.

### Structured Outputs with Zod (Pydantic-equivalent)

The Triage Worker's extraction call (AI-05) is the only structured-output surface in v0.1. The validator gates the boundary between the LLM and the rest of Engram — past this gate, every downstream consumer (WorkspaceDO writers, envelope builders) can rely on a fully-typed `TriageOutput`.

```typescript
// packages/triage-worker/src/schema.ts
import { z } from "zod";
import { zodToJsonSchema } from "zod-to-json-schema";

export const SYSTEM_MEMORY_TYPES = [
  "job_application", "contact", "company", "project",
  "research_note", "decision_log", "meeting_note",
] as const;

export const Entity = z.object({
  name: z.string().min(1).max(200),
  type: z.enum(["person", "company", "role", "date", "url"]),
});

export const TriageOutput = z.object({
  classified_type: z.enum(SYSTEM_MEMORY_TYPES),
  extracted_fields: z.record(z.unknown()),          // shape varies by type; downstream validates
  entities: z.array(Entity).max(50),                 // hard cap to prevent runaway hallucination lists
  summary: z.string().min(10).max(800),
  memorability: z.number().min(0).max(1),
  confidence: z.number().min(0).max(1),
});
export type TriageOutput = z.infer<typeof TriageOutput>;

// Derive the JSON schema for Workers AI response_format. zod-to-json-schema with target
// "openApi3" produces the shape llama-3.1-8b-instruct accepts via the OpenAI-compatible
// json_schema mode.
export const TRIAGE_JSON_SCHEMA = zodToJsonSchema(TriageOutput, {
  target: "openApi3",
  $refStrategy: "none",
});
```

**Framework integration.** Workers AI's `response_format: { type: "json_schema", json_schema: TRIAGE_JSON_SCHEMA }` is the structured-output path on `@cf/meta/llama-3.1-8b-instruct`. The model receives the schema as a hint and attempts to comply. The Zod schema serves two roles: (a) it generates the JSON schema sent to the model, and (b) it is the actual runtime gate on the response. Same source of truth on both sides.

**Validation pattern + retry logic.**

```typescript
async function extractAndScore(env: Env, event: MemoryEvent, message: Message): Promise<TriageOutput | null> {
  const aiResp = await env.AI.run("@cf/meta/llama-3.1-8b-instruct", {
    messages: [
      { role: "system", content: SYSTEM_PROMPT },
      { role: "user", content: event.content },
    ],
    response_format: { type: "json_schema", json_schema: TRIAGE_JSON_SCHEMA },
    temperature: 0.2,
    max_tokens: 1024,
  });

  // 1. Detect Workers AI 429 (binding returns success:false, does NOT throw).
  if (aiResp && (aiResp as any).success === false) {
    const errs = (aiResp as any).errors ?? [];
    if (errs.some((e: any) => e.code === 7501 || /429|rate/i.test(e.message))) {
      message.retry({ delaySeconds: 30 });  // AI-07
      return null;
    }
    throw new Error(`Workers AI non-429 failure: ${JSON.stringify(errs)}`);
  }

  // 2. Zod gate. llama JSON mode is "best effort" — parse failures are expected at low rate.
  //    Per Phase 5 success criteria target ≥95% valid JSON; the failing ≤5% must NOT crash the consumer.
  const candidate = (aiResp as any).response ?? aiResp;
  const parsed = TriageOutput.safeParse(candidate);
  if (!parsed.success) {
    // Retry ONCE on parse failure — gives the model a second roll with the same prompt.
    // After one retry, log + permanently skip (the block remains "pending" enrichment and
    // is visible to the v0.4 inbox UI for manual triage).
    if (!message.attempts || message.attempts < 2) {
      console.warn("triage:zod-parse-failed-retrying", { id: event.id, attempts: message.attempts ?? 0 });
      message.retry({ delaySeconds: 5 });
      return null;
    }
    console.error("triage:zod-parse-failed-permanent", {
      id: event.id,
      issues: parsed.error.issues,
      sample: JSON.stringify(candidate).slice(0, 500),
    });
    // PIP-05 pattern: permanent failures ack + log (DLQ-equivalent).
    return null;
  }

  return parsed.data;
}
```

**Retry policy summary:**

| Failure | Action | Where |
|---|---|---|
| Workers AI 429 (success:false, code 7501) | `message.retry({ delaySeconds: 30 })`, exit early | AI-07 |
| Zod parse failure, attempts < 2 | `message.retry({ delaySeconds: 5 })`, exit early | Section 4b |
| Zod parse failure, attempts ≥ 2 | Log + return null + outer caller `message.ack()` (DLQ-log only — Engram has no live DLQ in v0.1) | PIP-05 |
| Workers AI non-429 failure | `throw` (Queue runtime retries up to `max_retries`, then to DLQ) | Section 4b |
| Network/runtime exception | `throw` (same as above) | default |

### Async-First Design

`workerd` is async by default — every binding call returns a `Promise`. There is no `asyncio.run()`-equivalent footgun because the event loop is the runtime's, not yours. The framework-specific mistakes that DO bite:

1. **Don't `await` inside a `Promise.all` map without a concurrency cap.** Workers AI rate limits are global to the account, not per-Worker. Fanning out 100 simultaneous `env.AI.run()` calls during a batched Queue consumer will trigger 429s in the second half of the batch. Cap concurrency to ~5-10 for the v0.1 Triage Worker; revisit when Workers AI raises the per-account ceiling.
2. **`env.VECTORIZE.upsert()` and `env.VECTORIZE.deleteByIds()` are async on the index — promise resolution does NOT mean visibility.** Per Cloudflare docs, "may take a few seconds to become available for querying." Integration tests must allow up to ~5s between phases. Production code should not assume read-your-writes.
3. **Stream vs. await.** Engram does NOT stream in v0.1 — MCP tool responses are unary. The Workers AI binding supports streaming via `{ stream: true }`, but every Phase 5 call uses await (full response). Synthesis output specifically must NOT stream because the Zod gate (when synthesis grows a schema in v0.2) requires the full payload before validation; streaming would force speculative client behavior that we don't want yet.
4. **`ctx.waitUntil()` is the post-response async escape hatch.** Use it to fire-and-forget non-critical work AFTER the MCP response returns. The Phase 6 `INGEST_QUEUE.send(memoryEvent)` will live inside `ctx.waitUntil` precisely so the sync `remember()` latency does not include the Queue send. Phase 5 does NOT add to `ctx.waitUntil` — leave that wiring for Phase 6.

### Prompt Engineering Discipline

The Triage Worker is the only Phase 5 surface that runs a prompted LLM call (embeddings are not prompted). Engram's prompts must be:

- **System vs. user separated, always.** The `SYSTEM_PROMPT` constant in `packages/triage-worker/src/prompts.ts` contains the role, the task, the JSON-schema-expectation, and the 5 drop-category guidance from spike-findings `engram-response-synthesis-contract.md` §6 (dates, sources, technical identifiers, numeric values, decision-rejection naming). User content is the raw `event.content` ONLY — no metadata injected, no instructions concatenated.
- **No few-shot examples inline (v0.1).** v0.1 ships zero-shot for two reasons: (1) the spike validated structured-output quality at zero-shot ≥85% on synthetic samples, and (2) few-shot examples inflate input tokens by 2-5x per call. If real-corpus F1 (the carry-forward gate from Phase 4) lands < 75%, re-evaluate with a 3-shot inline prompt; if it lands ≥75%, ship zero-shot.
- **`max_tokens: 1024` is mandatory.** Never call llama-3.1-8b-instruct without an explicit `max_tokens`. Default ceilings can be generous; runaway outputs blow the cost budget and stall the Queue consumer. 1024 is comfortable for the TriageOutput JSON (typically 200-400 tokens of actual content).
- **`temperature: 0.2` is the Phase 5 default for structured output.** Higher temperatures destabilize JSON-mode adherence; spike findings recorded 0.2 as the band where the model stayed inside the schema most reliably.
- **System prompts are versioned in code, never edited live.** A prompt is data, but it's load-bearing code. Treat `SYSTEM_PROMPT` like a schema: any change goes through PR review and re-runs the eval reference dataset (Section 5).

### Context Window Management

This is a RAG system; the rules are:

- **bge-base-en-v1.5 = 512 tokens.** Long blocks silently truncate. v0.1 mitigates by storing short blocks (job postings, decisions, contacts ≤ ~1,800 chars). The MCP `remember()` handler MUST surface a `meta.gaps` entry — `"Content over 1,800 chars truncated for embedding; full content stored in SQLite but only the first ~512 tokens are semantically searchable."` — when truncation occurs.
- **Recall hydration window.** `topK ≤ 25` is the D-10 cap. After hydration, the synthesis call (if `verbosity ∈ {"synthesis","both"}`) receives the top-K block contents concatenated. Cap the synthesis input at ~6K tokens; drop trailing memories first (they are the lowest-ranked by hybrid score) and surface the drop in `meta.gaps`.
- **Envelope output trim is Phase 4's `trimToBudget` (≤ 7,500 tokens worst-case).** Phase 5 extends it: NEVER drop `result.synthesis`, NEVER drop `meta.gaps`. Drop trailing memories first. See `04-PHASE-5-HANDOFF.md` §"Wave 0 RED Tests" for the token-budget extension task.
- **Phase 5 does NOT introduce chunking.** Chunking with overlap (50-token windows on a 512-token model) is a v0.2 task. v0.1 stores blocks as-is. If real-corpus testing during AI-04 surfaces frequent truncation, surface to v0.2 scope but do NOT silently add chunking in v0.1.
- **No conversation summarization.** Engram is not a conversational AI — it has no chat history of its own. The "conversation" lives in the calling Claude session; Engram is stateless across calls. The `synthesis` field is a single-shot summary of the current `recall()` result set, not a rolling summary.

## 7. Production Monitoring

**Tracing Tool:** **Cloudflare Workers Analytics Engine** (`env.ANALYTICS`). One `writeDataPoint` per AI call site. Per Cloudflare docs, writes are non-blocking — they batch and flush asynchronously, so the call itself is effectively zero-latency on the hot path. Inspectable via SQL through the analytics dataset binding from a tiny `analytics-query-worker` (or directly from the Cloudflare dashboard's Analytics Engine SQL editor).

**Dataset schema (one row per AI/Vectorize operation):**

| Field | Type | Example | Purpose |
|---|---|---|---|
| `blobs[0]` | string | `"mcp-server"` or `"triage-worker"` | Worker source |
| `blobs[1]` | string | `"@cf/baai/bge-base-en-v1.5"` or `"@cf/meta/llama-3.1-8b-instruct"` or `"vectorize-query"` | Operation kind |
| `blobs[2]` | string | `"sha256(workspace_id)"` (first 16 hex chars) | Workspace dimension WITHOUT logging the raw ID (privacy + Section 1b "Regulatory" forward-compat) |
| `blobs[3]` | string | `"success"` / `"retry-429"` / `"zod-parse-fail"` / `"throw"` | Outcome class |
| `doubles[0]` | number | `127.4` | Latency ms (end-to-end wall clock for the binding call) |
| `doubles[1]` | number | `42` | Input length (chars for AI calls; vector dim for embeddings — always 768) |
| `doubles[2]` | number | `0` or `1` or `2` | Retry attempt count (0 = first try) |
| `doubles[3]` | number | `0` or `1` | `1` if `success: false` returned by binding, `0` otherwise (separate from outcome class so we can compute 429 rate cleanly) |
| `indexes[0]` | string | `"engram-prod"` | Environment tag (`prod` / `staging` / `dev`) — used as the sampling index per Cloudflare's Analytics Engine model |

**Key Metrics to Track (queryable SQL on the dataset):**

1. **`remember()` p50/p95/p99 latency per day** — must stay within the Section 4b 150–430ms p50 budget.
2. **`recall()` p50/p95/p99 latency per day** (split by `verbosity` arg via a separate blob if needed) — 150–400ms p50 for non-synthesis; 2–5.5s p50 for synthesis.
3. **429 rate per hour** (Workers AI only — Vectorize 429 is rare in v0.1 volume) — alerts if >5% in any 1-hour window.
4. **Zod parse failure rate per day** (Triage Worker) — alerts if >5% (the inverse of dimension #4's 95% pass target).
5. **Vectorize zero-match recall rate per day** — recalls that returned 0 memories despite the workspace having a non-empty corpus. Above 10% (excluding genuinely empty workspaces) is a red flag for either embedding drift (failure mode #2) or namespace mishandling (failure mode #1).

**Sample SQL queries** (run against the analytics dataset; canonicalized in `packages/mcp-server/scripts/analytics-queries.sql`):

```sql
-- p50/p95/p99 latency by model, last 24h
SELECT
  blob1 AS model,
  quantileWeighted(0.50, double1, _sample_interval) AS p50_ms,
  quantileWeighted(0.95, double1, _sample_interval) AS p95_ms,
  quantileWeighted(0.99, double1, _sample_interval) AS p99_ms,
  count() AS n
FROM engram_ai_analytics
WHERE timestamp > NOW() - INTERVAL '1' DAY
GROUP BY model;

-- 429 rate per hour, last 7 days
SELECT
  toStartOfHour(timestamp) AS hour,
  sum(double3) / count() AS rate_429,
  count() AS n
FROM engram_ai_analytics
WHERE timestamp > NOW() - INTERVAL '7' DAY
  AND blob1 LIKE '@cf/%'
GROUP BY hour
ORDER BY hour;

-- Zero-match recall rate per day, last 30 days
SELECT
  toDate(timestamp) AS day,
  sum(if(blob3 = 'zero-match', 1, 0)) / count() AS zero_match_rate
FROM engram_ai_analytics
WHERE timestamp > NOW() - INTERVAL '30' DAY
  AND blob1 = 'vectorize-query'
GROUP BY day;
```

**Alert Thresholds:**

| Trigger | Threshold | Channel | Severity |
|---|---|---|---|
| 429 rate per hour | >5% of any 1-hour window | Cloudflare Email Routing → Russell | High (transient throttle = capacity issue or batch-storm bug) |
| Zod parse failure rate per day | >5% | Email | Medium (prompt regression candidate) |
| `remember()` p50 latency per day | >430ms (Section 4b budget) | Email | Medium (perf regression candidate; budget violation) |
| Vectorize zero-match recall rate per day | >10% on non-empty workspaces | Email | High (likely namespace mishandling or embedding drift — both critical failure modes) |
| Reference-corpus F1 (weekly batch) | drops >5pp from previous week's baseline | Email | High (model rotation by Cloudflare, or hidden ingest regression) |
| Reference-corpus F1 (pre-release) | <75% absolute | Block deploy via CI exit code | Critical (carry-forward gate from `04-PHASE-5-HANDOFF.md`) |

v0.1 uses Cloudflare Email Routing → Russell's `russellkmoore@mac.com` for all alert delivery. v1.0 multi-tenant migrates to a proper alerting integration (PagerDuty / Slack via webhook); not needed at single-user scale.

**Smart Sampling Strategy** — Logpush dumps full event logs to R2 bucket `engram-evals-archive` for offline review. Three sampling rules:

1. **Always-sample (100%):** every interaction where (a) recall returned 0 memories despite a non-empty workspace, OR (b) Zod parse failed (any attempt), OR (c) latency exceeded 2× the corresponding Section 4b budget. These are the "concerning signals" per `ai-evals.md` §"Smart Sampling". For each, the full request body, the full `EngramResponse` envelope, the Workers AI raw response, and the Vectorize matches array are persisted — Russell reviews these monthly as part of the dimension #5 cadence.
2. **Random 5%:** baseline production traffic, stratified across the three memorability bands. Feeds the dimension #5 calibration review.
3. **Russell's tag:** any interaction Russell explicitly tags via a future `feedback()` MCP tool (v0.2 scope — surface tagged via `meta.tags: ["needs-review"]` in the envelope, then Logpush filters on the tag). Not enforced in v0.1; reserved here as a forward-compat hook so monitoring infra can grow with the product without redesign.

Sampled interactions older than 90 days are deleted from R2 to keep storage bounded; rolled-up aggregates (F1 weekly, parse rate, latency percentiles) live forever in the analytics dataset.
